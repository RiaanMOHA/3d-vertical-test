## Problems encountered and how they were solved

### Problem 1: Material array approach broke front facade rendering

**Symptom.** After my first 2-layer wall edit (using BoxGeometry with 6-element material array), the front facade showed 4 brown wall segments separated by vertical CREAM channels at each window position. The sill/lintel boxes built by addWinFlex appeared as cream instead of the expected brown cladding.

**Root cause.** Unclear definitively. Both makeWall and addWinFlex used the same material-array approach with the same face index logic, but only makeWall rendered correctly. Possibly related to three.js r128 BoxGeometry's group setup interacting differently with thin boxes vs full-thickness boxes, or a subtle scope/closure issue. Did not invest in deep debug.

**Fix.** Reverted all 4 material-array edits. Adopted 2-thin-slab approach instead: each outer wall built as 2 boxes (outer slab with cladding + inner slab with wallMat) at WT/2 thickness each, offset by WT/4 along the wall normal direction. Each box has single material. Bulletproof.

**Lesson.** Material arrays on BoxGeometry are tricky in three.js r128 for our use case. When in doubt, prefer multiple single-material meshes over one mesh with face arrays. The `outerSign` concept (which side is outside) is still useful — just translates to position offset instead of face index.

### Problem 2: Brown panel pre-existing bug surfaced as cream channels

**Symptom.** Even after reverting my failed material-array edits, the front 1F LEFT showed 4 brown wall segments separated by cream channels at window positions. User asked "wtf".

**Root cause.** addWinFlex built sills/lintels with `wallMat` (cream) hardcoded, while the wall segments around them got `matLowerExt` (brown) via the wallX call's mat parameter. The two materials were never reconciled. From outside, the wall segments showed brown but the sill/lintel area at each window showed cream — creating visible cream channels.

**Fix.** Added `frameMat` parameter to addWinFlex. Passed `matLowerExt` for F1_WIN_FRONT, `matUpperExt` for back/sides/2F. Now sill+lintel match the wall they're embedded in.

**Lesson.** When a function builds parts of a wall (sills/lintels around windows), its material parameter must match what the surrounding wall is using. Hardcoding wallMat fails when the surrounding wall is cladded.

### Problem 3: Brown panel proportions wrong (full-height + too wide)

**Symptom.** User shared photos of the building, asked me to compare. My brown panel was full F1H height and stretched to x=4.95 (door's left edge). Photos showed brown panel as a contained INSET — cream wraps above it AND between brown's right edge and the door.

**Root cause.** Initial implementation matched the prior session's interpretation (panel reaches the wet-room east boundary at x=4.95). But that boundary was the door, not the wet-room east edge per blueprint (x=4.50). And the panel didn't reach 1F ceiling per the photo.

**Fix.** Implemented brown panel as a contained inset at x=0..4.50 (= wet-room east edge per blueprint), y=0..2.10 (~85% of F1H per photo measurement). Cream wraps above (y=2.10..F1H, x=0..4.50) and to the right (x=4.50..W with door gap at 4.95..5.85).

**Lesson.** "Brown panel" doesn't mean "the entire wet-room front exterior". It's a specific cladding feature that's smaller than the wet-room footprint. Always cross-check photos AND blueprint extents — they're independent constraints.

### Problem 4: Removing walk-btn HTML broke all scene initialization

### `frameMat` for window sills/lintels must match wall cladding

The addWinFlex function builds sill (below window) + lintel (above window) + glass. Originally hardcoded wallMat for sill/lintel. When the surrounding wall has cladding (matLowerExt brown or matUpperExt cream), the cream sill/lintel creates visible discontinuities at the window position. Pass cladding material via `frameMat` parameter for outer walls.

### 2-thin-slab beats material-arrays for two-faced walls in three.js r128

Material arrays on BoxGeometry are unreliable in three.js r128 for thin boxes (sills/lintels) — the array assignment didn't apply correctly in my testing. The 2-thin-slab approach (build 2 boxes at WT/2 thickness each, offset by WT/4 along wall normal, each with single material) is bulletproof. Use this pattern for any "outer face = one material, inner face = another" wall.

### Walk-mode button HTML can't be removed without null guards

The walk-btn is referenced at 4 JS sites (`walkBtn.addEventListener`, three `walkBtn.style.display` setters). Removing the element silently breaks scene init via TypeError. Either keep the element + use `!important` CSS to hide it, or null-guard every reference.

The blueprint says wet-room east edge is at x=4.50 (toilet's east wall). The photo shows brown ending closer to x=4.30-4.40. The 0.10-0.20m discrepancy is within photo-perspective margin. Going with x=4.50 (blueprint) is defensible per source-of-truth hierarchy.

## Architecture and design notes

### 2-thin-slab pattern for two-faced walls

When a wall needs cladding outside + plaster inside, build it as two boxes:
- Outer slab: `mat=cladding`, thickness `WT/2`, position offset from wall centreline by `+WT/4 * outerNormal`
- Inner slab: `mat=wallMat`, thickness `WT/2`, position offset by `-WT/4 * outerNormal`

The outer-normal direction in world coords for a wall rotated by `yaw=-atan2(dz,dx)`:
- For `outerSign=+1`: outerN = (-dz/len, 0, dx/len)
- For `outerSign=-1`: outerN negated

This avoids three.js BoxGeometry material array fragility while preserving wall thickness. Each box has single material — bulletproof rendering.

### addWinFlex sill/lintel material must match wall

When window opening is in a cladded outer wall, the sill (below glass) and lintel (above glass) must also use the cladding material from outside. Otherwise the wall reads correctly but a cream stripe appears at the window x range, breaking the cladding. addWinFlex now takes `frameMat` parameter for this.

For 2-layer walls, the sill/lintel should ALSO be 2-thin-slab. addWinFlex auto-detects outerSign from `axisCoord >= D/2` (front) or `>= W/2` (right side), and uses cladding for outer slab + wallMat for inner slab.

### Chip viewpoint = inside the room

The interior scene's `viewpoints` array drives chip-click navigation. Each viewpoint has `pos` + `tgt`. For room navigation, place `pos` INSIDE the room at human eye height (y=1.6 for 1F, y=F1H+1.6 for 2F), one corner of the room. Set `tgt` at the diagonally-opposite area, slightly lower (y=1.0..1.2) for natural floor-down look.

`overview` chip is the only one that stays external — for full-building shape view.

### Per-room build pattern (Phase D)

Each room replaces its placeholder mattress in the interior scene's furniture section. Wrap in `{ ... }` block to scope new const declarations (matIron, matBedding, etc). Use the existing `furn(x1, z1, x2, z2, y1, y2, mat)` helper for AABB pieces. For complex pieces (e.g., bed = headboard + footboard + rails + mattress + pillow), build as multiple furn calls.

Reference materials defined in earlier LDK section (matACUnit, matACGrille, matACVent, matCurtain) can be reused — they're at the same scope level inside the build function.

### Window arrays = single source of truth for window positions

F1_WIN_FRONT, F1_WIN_BACK, F1_WIN_LEFT, F2_WIN_FRONT, F2_WIN_BACK, F2_WIN_LEFT (lines ~808-893) are the canonical window position data. Both exterior scene + interior scene's outer walls reference these arrays. To add/move a window, edit ONE array and both scenes update.
