## Problems encountered and how they were solved

### 1. Blender 5.x dropped NISHITA sky type
**Symptom:** Bake exited in 30s with `TypeError: enum "NISHITA" not found in ('SINGLE_SCATTERING', 'MULTIPLE_SCATTERING', 'PREETHAM', 'HOSEK_WILKIE')`.
**Root cause:** Blender 5.1 renamed Nishita atmospheric scattering to MULTIPLE_SCATTERING. Old scripts targeting `sky.sky_type = 'NISHITA'` break.
**Fix:** try/except in `configure_world()` — try NISHITA first, fall back to MULTIPLE_SCATTERING. Both produce equivalent atmospheric results.
**Why it happened:** The bake script (and the `interior-render-recipe.md`) was written against an older Blender API. Re-running against Blender 5.1.1 surfaced the rename.

### 2. Blender 5.x dropped `dust_density` / `ozone_density` on non-Nishita sky types
**Symptom:** Bake exited with `AttributeError: 'ShaderNodeTexSky' object has no attribute 'dust_density'`.
**Root cause:** MULTIPLE_SCATTERING doesn't expose `dust_density` / `ozone_density` (those were Nishita-only atmospheric components).
**Fix:** `_safe_set(attr, value)` helper that does `hasattr` check before assigning. Now all Nishita-specific params silently skip when unavailable.
**Why it happened:** Same as above — API drift. Worth carrying this pattern forward.

### 3. 8 of 17 bake PNGs were uniform white
**Symptom:** First successful bake produced visually correct images for 9 surfaces and pure-white (mean 255, uniques 1) garbage for 8 others. The failing 8 were the surfaces whose bake-quad vertex winding gave them face normals pointing OUT of the LDK (floor -Y, ceiling +Y, kitchen-wall +Z, alcove +Z, stairwell south +Z, etc.).
**Root cause:** Cycles COMBINED bake shades the front face only — the side the surface normal points toward. With a back-facing target, the bake samples the world sky environment directly, returning saturated white.
**Fix:** Added `flip_normals(obj)` helper using `bmesh.ops.reverse_faces(bm, faces=bm.faces)`. Called on the 12 quads with wrong winding. Kept the 5 quads that already had correct normals (`brick_wall`, `stairs_wall`, `stairwell_part_east`, plus the 2 that happened to have correct windings from the start — actually only 3 since 12 needed flipping, total 17, so 5 were correct).
**Why it happened:** The bake script's `add_quad` helper didn't enforce winding direction. Different vertex orders for different surfaces inadvertently produced different normal directions.
**Lesson:** When writing bake-target quads, normal direction MUST face into the room (visible side). If reusing this script for other rooms, audit windings or add an assertion.

### 4. User said windows were too bright; first dim made walls inconsistent with furniture
**Symptom:** After dropping runtime sun/RAL/sky-proxy by ~30-40%, walls would still look bright (from the lightmap baked at the OLD sun intensity) while furniture (no lightmap) would look comparatively dim.
**Root cause:** Lightmaps capture the GI at bake time. If you change runtime lights without re-baking, walls and floor keep the brighter "baked-in" contribution while furniture drops with the runtime lights.
**Fix:** Coordinated change — drop both runtime (sun 2.2→1.4, RAL 11→6, sky 1.2→0.9) AND bake (sun energy 3.5→2.4, sky strength 1.2→0.9), then re-bake. Verified PNG means dropped 5-15% to match.
**Why it happened:** Recipe didn't make this dependency explicit. Worth flagging as a tuning rule.

### 5. First "ONLY USE FURNITURE IN IMAGES" audit was too superficial
**Symptom:** After cleanup pass 1 (removing outside-stair rail, reducing outlets/downlights/chairs), user said "audit AGAIN — your ONLY SOURCE OF TRUTH IS THIS: [photos folder]".
**Root cause:** I had checked only ~11 photos out of ~177. Missed the major furniture-STYLE errors (TV console + coffee table being industrial, not walnut shaker). Missed the stair partition geometry (boxed, not knee-walls). Missed the slim vertical window.
**Fix:** Re-audited with 10 more frames covering different angles. Found 6 substantial issues this round. Implemented all 6.
**Why it happened:** First-pass audits where I'm matching photos to model are easy to do too quickly. Lesson: when user says "only use what's in photos", actually inventory EVERY visible item — not just the obvious furniture.

### 6. Cylinder shell wraparound chair backs were geometrically broken
**Symptom:** User said chairs were "pointing in the wrong direction" then "SO MUCH WORSE" after my "fix".
**Root cause:** Three.js `CylinderGeometry` uses `x = r·sin(θ), z = r·cos(θ)`, NOT the standard math convention `x = r·cos(θ), z = r·sin(θ)`. So `θ = π/2` is +X direction (not +Z), and `θ = π` is -Z direction (not -X). I wrote `thetaStart = -π/2 - arc/2` thinking the shell midpoint would be at -Z; it was actually at -X (the LEFT SIDE of each chair). My second fix moved `backCenterZ` further in the wrong direction without fixing the underlying theta orientation.
**Fix:** Abandoned cylinder shells entirely. Replaced with a simple padded RoundedBox back slab + 2 small angled shoulder RoundedBoxes at the top corners. Much less geometric ambition, but actually reads as a chair.
**Why it happened:** Forgot Three.js's atypical cylinder theta convention. Also: ambition outran what was needed — the photos show CHAIRS WITH SLIGHTLY CURVED BACKS, not dramatic bucket wraparounds. The simpler approach matches the photos better.
**Lesson:** Three.js cylinder vertex formula: `x = r·sin(θ), z = r·cos(θ)`. For a shell facing -Z direction, use `thetaMid = π`. Save the rule somewhere.

### Three.js CylinderGeometry theta convention
Vertices computed as `x = radius · sin(θ), z = radius · cos(θ)`. So:
- θ = 0 → +Z direction
- θ = π/2 → +X direction
- θ = π → -Z direction
- θ = -π/2 → -X direction
For a partial cylinder shell facing a particular direction, set `thetaMid` accordingly and `thetaStart = thetaMid - thetaLength/2`. Easy to get wrong if you assume the standard math convention.

### Bake-quad face normals must point into the room
Cycles COMBINED bake shades the FRONT face only. Back-facing bake targets sample the world sky directly and return uniform white. Always ensure your add_quad calls produce normals pointing toward the visible side. If unsure, call `bmesh.ops.reverse_faces` after creation.

### Blender 5.x API drift
- `NISHITA` → `MULTIPLE_SCATTERING`
- `dust_density` / `ozone_density` only exist on (old) Nishita node, not on the new MULTIPLE_SCATTERING. Use try/except + `hasattr` for forward-compatibility.
- `World.use_nodes` and `Material.use_nodes` emit `DeprecationWarning: expected to be removed in Blender 6.0`. Not blocking yet but should be migrated when revisiting.

## Architecture and design notes

### Lightmap wiring architecture
Three-tier separation:
1. **`applyLightmap(mat, slug, opts)`** — attaches a baked PNG to a material clone, sets `lightMapIntensity = 1.0`, dampens `envMapIntensity` (default 0.18, brick gets 0.22). Default channel is 1 (uv1).
2. **`LM_UV[slug](x, y, z) → [u, v]`** — maps world coords on the visible face of a wall to the bake's UV space. Each function is hand-derived from the bake script's add_quad vertex→UV mapping. Single source of truth for the runtime↔bake correspondence.
3. **`addLm(mesh, slug, axis, sign)`** — calls `setLightmapUV1(mesh, axis, sign, LM_UV[slug])` then `scene.add(mesh)`. The axis/sign identify which face of a BoxGeometry mesh receives the lightmap (other faces clamp to texture edge via `ClampToEdgeWrapping`).

Floor halves use `channel: 0 + flipV: true` because `PlaneGeometry` is rotated -π/2 about X, which reverses the V axis relative to the bake. (Same as laundry-test's floor.) Everything else uses channel:1 + setLightmapUV1 for explicit per-vertex UVs.
