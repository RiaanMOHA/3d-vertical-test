## Problems encountered and how they were solved

### Problem 1: WebGPU swap gave black screen on first attempt

- **Symptom.** Page draws UI chrome (chips, back arrow) but canvas is fully black.
- **Root cause.** The minified `three.webgpu.min.js` bundle drops the `UniformsLib` export (WebGL-only). `RectAreaLightUniformsLib.js` (a vendored example helper) imports `UniformsLib` from `'three'` → `Uncaught SyntaxError`. ES module import error tore down the whole module graph silently from the user's POV (canvas was created but never received any draw calls).
- **Fix.** Comment out the `RectAreaLightUniformsLib` import (already done in a prior session, just hadn't been pushed). On second attempt, switch to the **unminified** WebGPU bundle which exports everything by name, and use `RectAreaLightTexturesLib` (the WebGPU-era replacement) + `RectAreaLightNode.setLTC()` to wire LTC textures.
- **Lesson.** Minified three.js bundles (any flavour) silently drop unused-by-the-bundle exports. If your codebase imports from a vendored example helper, use the **unminified** bundle. The 1.4 MB extra (over minified) is a one-time cache cost.

### Problem 2: WebGPURenderer doesn't have `renderer.capabilities`

- **Symptom.** `Cannot read properties of undefined (reading 'getMaxAnisotropy')` at `pbrMat()`.
- **Root cause.** WebGLRenderer exposes capabilities via `renderer.capabilities.getMaxAnisotropy()`. WebGPURenderer moved this to `renderer.getMaxAnisotropy()` (top-level method). The bundle has both classes but they don't share APIs.
- **Fix.** Replace all 7 call sites in ozu-test.html: `renderer.capabilities.getMaxAnisotropy()` → `renderer.getMaxAnisotropy()`. The latter works on WebGLRenderer too in r184, so it's a backwards-compatible swap.
- **Lesson.** `renderer.capabilities` is WebGL-specific. Top-level methods are the safer cross-renderer pattern.

### Problem 3: User got "stuck loading" — VS Code port-forward had dropped

- **Symptom.** Page is at `localhost:8080/ozu-test.html` but spinning forever; server log shows zero browser requests.
- **Root cause.** User is on a Mac, project served from a remote Linux box. VS Code's port-forward from Mac:8080 → remote:8080 had become stale.
- **Fix.** Walked user through VS Code Ports tab: stop forwarding port 8080, re-add, click the localhost:8080 link to open via VS Code's tunnel.
- **Lesson.** Always check `tail` of dev server log when user reports "loading forever". Zero requests means the network never reached us.

### Problem 4: Window-wall stripes (wB UVs unnormalized)

- **Symptom.** Vertical stripe seams on the window-wall.
- **Root cause.** `wB` is built from `wallShapeWithHole` (a `ShapeGeometry`). ShapeGeometry's default UVs use the shape's literal coordinates as UV, not normalized 0..1. With `wB`'s shape spanning (0..2.7, 0..2.5) and AO texture's default `RepeatWrapping`, the texture tiled 2.7× horizontally and 2.5× vertically. WebGL had been hiding this with aggressive default mipmapping; WebGPU exposed it.
- **Fix.** Added `setUVsByLocal(wB.geometry, (lx, ly, lz) => [lx / RD, ly / RH]);` to normalize. Also set `wrapS/wrapT = ClampToEdgeWrapping` on AO loader as defensive belt-and-braces.
- **Lesson.** ShapeGeometry default UVs are NEVER normalized. Always explicitly set them.

## Learnings and discoveries

### WebGL → WebGPU is a *staged migration*, not a one-line swap

The "swap-and-fall-back" promise from research overstates how clean it is. The codebase has multiple WebGL-only patterns that need explicit handling:
- `material.onBeforeCompile` (GLSL string injection) → silently no-ops on WebGPU (acceptable trade-off; ports to TSL later)
- `RectAreaLightUniformsLib` → must be replaced with `RectAreaLightTexturesLib` + `RectAreaLightNode.setLTC()`
- `renderer.capabilities` → moved to top-level renderer methods
- `renderer.shadowMap.type = THREE.PCFSoftShadowMap` → still works
- `PMREMGenerator` → works on both
- `HDRLoader` → works on both (verified all symbols in the WebGPU bundle)
- `setAnimationLoop` (already used) → works on both

### Use unminified `three.webgpu.js` for vendored projects

Minified WebGPU bundle (637 KB) drops exports the runtime might still need. Unminified (2 MB) is the safe choice. Cached after first load.

### `three.core.js` is a sibling import

Unminified `three.webgpu.js` references `./three.core.js` — must be vendored alongside. Both come from `https://unpkg.com/three@0.184.0/build/`.

### AgX is the 2026 best practice for warm interior tone mapping

Cross-checked across 3 of the 4 lighting research reports. ACES crushes oranges → yellow on warm pendant scenes; AgX preserves hue at the highlight roll-off. AgX is "flatter" so push exposure ~0.05–0.1 higher to compensate. r184 has `THREE.AgXToneMapping`.

### WebGPU mipmap filtering is stricter than WebGL

Multiple latent issues exposed by the migration:
- Smooth-gradient AO maps banding at low LODs
- Procedural noise textures producing moiré
- Degenerate UV derivatives causing checkerboard

The general fix pattern: `tex.generateMipmaps = false; tex.minFilter = LinearFilter;` for any texture that's not a real PBR diffuse map. Real PBR maps with detail benefit from mipmaps; AO/noise/UI textures don't.

### `feat()` function had a hidden geometric bug

The function placed inset boxes (FEAT=40mm thick) at `BIAS=3mm` from the wall surface, but **centred** the box at that offset. So 20mm of every box was BEHIND the wall surface, intersecting the wall slab. WebGL had been hiding the resulting z-fight; WebGPU exposes it. Fix is one line change; new formula puts the box's inner face exactly at `BIAS` from the wall.

### Photometric values that work in 2026 r184 + AgX

- Bulb mesh emissive: 1.0–2.0 (visible glow without blowout)
- Fabric shade emissive: 0.3–0.6
- PointLight: `.power` 200–800 lm per bulb (= ~16–64 cd)
- HemisphereLight bounce: 0.3–0.5 intensity
- Tone mapping exposure: 0.9–1.0 with AgX (vs 0.55 with ACES)
- Decay: 2 (default, physically correct)
- Distance: 0 (unbounded; default-correct for r155+)

## Architecture and design notes

### Renderer abstraction in r184

Three.js r184 supports WebGPURenderer + a WebGL2 fallback in the same bundle (specifically `three.webgpu.js`). The renderer auto-detects WebGPU support; falls back to WebGL2 backend if not. From the application's perspective, the same `renderer.render(scene, camera)` call works on both. **Key API differences exposed during this migration:**
- Construction is async: `await renderer.init()` is required after `new WebGPURenderer()`.
- `renderer.capabilities` doesn't exist — use `renderer.getMaxAnisotropy()` directly.
- `setAnimationLoop()` is the recommended pattern (works on both renderers).
- `material.onBeforeCompile` silently no-ops (replace with TSL nodes for WebGPU-native effects).
- WebGPU's mipmap LOD calculation is stricter — degenerate UV derivatives, smooth gradients, and noisy textures all produce visible artifacts that WebGL had been masking.

### LTC initialisation pipeline for RectAreaLight on WebGPU

```
1. Import RectAreaLightTexturesLib from 'examples/jsm/lights/'
2. Call RectAreaLightTexturesLib.init() — populates static LTC_FLOAT_1/2/HALF_1/2 fields
3. Call THREE.RectAreaLightNode.setLTC(RectAreaLightTexturesLib) — wires the lib's static fields into the bundle's internal RectAreaLightNode singleton
```

Both steps are required. Step 3 only works if `RectAreaLightNode` is exported from the bundle (= unminified bundle).

### Photometric light units in r184

`PointLight.intensity` is in **candela (cd)**, not the legacy artist-friendly scalar. `PointLight.power` is the lumen-equivalent setter (`power = intensity × 4π`). For a 60 W-equiv warm-white LED bulb (800 lm @ 2700 K): use `light.power = 800` OR equivalently `light.intensity = 64`. Default `decay: 2` and `distance: 0` (unbounded inverse-square) are physically correct for r155+; do NOT cap distance for performance hacks unless you have many lights.

### Per-scene tone mapping

The renderer has ONE active tone mapping. Setting it per-scene happens inside `switchScene`:
```js
if (id === 'room-1') {
  renderer.toneMapping = THREE.AgXToneMapping;
  renderer.toneMappingExposure = 0.9;
} else {
  renderer.toneMapping = THREE.ACESFilmicToneMapping;
  renderer.toneMappingExposure = 1.0;
}
```
This pattern was already in use for exposure; extended to tone mapping for the AgX swap.

### `setUVsByLocal(geometry, uvFn, mainAxis?)` 

Updated helper. Without `mainAxis`, applies the formula to all vertices (legacy behaviour). With `mainAxis = 'x'|'y'|'z'`, only applies the formula to vertices whose normal aligns with that axis (dot product magnitude > 0.5); other vertices get UV `(0.5, 0.5)`. Used to handle BoxGeometry walls where only the ±main-axis faces should sample the AO map; the four "thickness side" faces would otherwise have degenerate UVs.

### `feat()` placement formula

OLD: `c = innerCoord + inward * BIAS` (BIAS=3mm, FEAT=40mm) — centred box at offset, half straddles wall.

NEW: `c = innerCoord + inward * (BIAS + FEAT/2)` — inner face of box at exactly BIAS from wall, full thickness extends into room.

This affects every window glass, mullion, door panel, closet pair, frosted pane. Visual difference: features now sit cleanly in front of walls instead of "embedded" half-into-wall. Did NOT solve the user's reported pixelation, suggesting the band is sourced from somewhere else.
