```js
function roundedBox(w, h, d, radiusOpt = null, segments = 4) {
  const minDim = Math.min(w, h, d);
  const r = radiusOpt !== null
    ? Math.min(radiusOpt, minDim * 0.49)
    : Math.min(0.004, minDim * 0.30);
  return new RoundedBoxGeometry(w, h, d, segments, r);
}
```

## Learnings and discoveries

### About RoundedBoxGeometry (from reading the source)

- Constructor: `RoundedBoxGeometry(width, height, depth, segments, radius)`. Default segments=2, radius=0.1.
- Internally creates a unit BoxGeometry with `segments * 2 + 1` subdivisions on each axis (so segments=5 → 11×11×11 = 1331 vertex segments per face on a non-indexed mesh).
- The rounding loop computes each vertex's normal from `(position - sign(position) * halfSegmentSize).normalize()` then sets `position = box * sign(position) + normal * radius` where `box = (width/2 - radius, height/2 - radius, depth/2 - radius)`.
- For pure planar face vertices (interior of a flat face), normal aligns with the face axis (e.g. -X face: nx=-1).
- For rounded-corner vertices, normal smoothly interpolates between adjacent face axes (e.g. -X-+Y edge: normal ≈ (-0.707, +0.707, 0)).
- Position attribute spans [-W/2, +W/2] × [-H/2, +H/2] × [-D/2, +D/2].
- Normal attribute is generated and accurate.
- UV attribute is generated for each face individually with seams at the corners (per `getUv` helper).

### About three.js lightMap

- `MeshStandardMaterial`/`MeshPhysicalMaterial` natively consume `lightMap` + `lightMapIntensity`. No shader hacks.
- The shader chunk `lightmap_pars_fragment.glsl` reads as: `lightMapIrradiance = texture2D(lightMap, vLightMapUv).rgb * lightMapIntensity; irradiance += lightMapIrradiance;`. So the lightmap is ADDED to the runtime irradiance.
- For a Combined bake (which already includes the diffuse base color), this would double-count if you keep the diffuse map at full strength. The fix used in this session: drop `envMapIntensity` to 0.15-0.20 on lightmap-carrying materials so the runtime IBL doesn't fight the pre-baked solution.
- LightMap uses `uv1` channel by default. Same `texture.channel = 0` trick as aoMap to switch to uv0 if you don't want to manage two UV channels.

### About Cycles "Combined" bake type

- Settings live on `scene.cycles.bake_type = 'COMBINED'` plus `scene.render.bake.use_pass_direct = True; use_pass_indirect = True; use_pass_diffuse = True; use_pass_glossy = False; use_pass_transmission = False`.
- Encodes color (with diffuse) + lighting (direct + indirect) + AO. Output is a sRGB color texture.
- For occluder objects (the ones that should bounce light but not be bake targets), give them a plain diffuse material with the right color — Cycles will let them bounce colored light onto bake targets.
- Combined bake produces **bake noise** at low samples and short ray distances. 512 samples + denoising gave acceptable results in this session.

### About the kitchen-test's lighting recipe (transferable to other interior projects)

The combo that produced "amazing" quality per the user, transferable to similar interior renders:
- Tone-mapping: ACESFilmic at exposure 0.52 (after two rounds of dimming from 0.85)
- HDRI: kloppenheim_06_puresky_2k filtered through PMREMGenerator (compileEquirectangularShader before fromEquirectangular)
- RectAreaLightUniformsLib initialised
- Hemi 0.22 (sky 0xdde8f0 / ground 0x4a4035)
- Window: RectAreaLight 11.2 (warm 0xfff0d8) + DirectionalLight 1.28 (same color, casts shadows, mapSize 2048², bias -0.00015, normalBias 0.02, radius 3) + emissive sky proxy plane (0xfff0d8) outside the window

## Architecture and design notes

### Single-HTML-file pattern preserved

All work fits the project's "one HTML file per project" architecture. Three.js + addons loaded via `<script type="importmap">` mapping `three` to vendored `three.module.min.js`. All other addons imported by relative path. No bundler, no build step.

### Per-surface bake pattern (consistent across kitchen-test + laundry-test)

For both projects, AO/lightmap baking follows the same pattern:
- Each visible surface gets its own image.
- Bake all surfaces in the SAME scene so they bounce color/AO at each other.
- For each bake target, set its image-texture node as `selected = True` AND `nodes.active = node` — both flags required.
- Smart UV mapping per surface (custom hand-authored, not Blender Smart UV Project, since our shapes are parametric).
- Output PNG saved via `image.filepath_raw + image.save()` (NOT `image.save_render`).
- For data textures (AO): `image.colorspace_settings.name = 'Non-Color'`.
- For color textures (lightmap): `image.colorspace_settings.name = 'sRGB'`.

### Lightmap vs AO map decision

For the laundry-test floor + walls, I REPLACED the AO maps with lightmaps because lightmap (Combined bake) is a strict superset:
- aoMap multiplies darkness into the diffuse — purely shadow info
- lightMap adds color-coded irradiance — shadow + color bleeding + indirect light

Drop envMapIntensity to 0.15-0.20 on materials with lightMap so the runtime IBL doesn't fight the pre-baked solution.

The washer's body still uses aoMap (front-face AO bake). It's a separate surface from the room shell so it has its own bake target. Could be upgraded to a lightmap in a follow-up — that would catch the brick wall's color bouncing onto the washer's left side.

### UV1 override pattern for partial bake coverage

When applying a baked texture (AO or lightmap) only to ONE face of a multi-face mesh:
- Override `geometry.uv1` (or `uv0` if `texture.channel = 0`)
- For target-face vertices: compute UV based on local position
- For other vertices: set UV outside [0, 1] (e.g. -1, -1)
- Set `texture.wrapS/T = ClampToEdgeWrapping` so out-of-range UVs sample the edge pixel
- Bake's edge pixels must be uniformly white/neutral (or whatever the "no contribution" sample is)

**RoundedBoxGeometry caveat:** rounded corner vertices have mixed normals AND mixed positions (lx in [-d/2, -d/2 + radius], normals interpolating between adjacent face axes). A loose threshold catches them. Use a STRICT combined position+normal test:
```
if (lx < -d/2 + tolerance && nx < threshold) {
  // pure planar front face
}
```
Where `tolerance ≈ 0.0008` (1mm float tolerance) and `threshold = -0.97` (within 14° of pure -X).

### Cycles bake uses Y-up in our scripts (three.js convention)

Blender defaults to Z-up but `bpy.ops.mesh.primitive_cube_add(location=...)` and `from_pydata(verts, ...)` accept whatever coordinate values you give. The bake operates on local geometry — axis-up convention doesn't affect AO results since it's purely geometric.

Our scripts pass three.js-style (X right, Y up, Z forward) coordinates directly. Blender's renderer treats them as (X, Y_blender_horizontal, Z_blender_vertical), which means the rendered preview in Blender is rotated, but bake outputs are correct.
