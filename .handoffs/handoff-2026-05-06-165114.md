## Problems encountered and how they were solved

### Problem 1: User's browser couldn't reach localhost:8080

- **Symptom:** kitchen-test.html, ozu-test.html, AND a plain-HTML sanity page all showed "nothing" / blank in Chrome. Same in private/incognito. Browser console showed no errors.
- **Root causes (two layered):**
  - **Layer 1:** user is on a Mac, SSH'd into the GPU server. Chrome runs on the Mac; `localhost:8080` in Chrome refers to the Mac, not the server. Discovered via `SSH_CLIENT`/`SSH_CONNECTION` env vars + `DISPLAY=` empty.
  - **Layer 2:** user had VS Code Remote-SSH port forwarding for 8080 already set up, but the forward had become **stuck** — connections hung indefinitely instead of erroring out. (Probably stale state after the underlying Python server had been bind-failing earlier.)
- **Fix:** in VS Code PORTS tab, right-click port 8080 → "Stop Forwarding Port", then "Forward a Port" → 8080. After that, `localhost:8080/sanity.html` returned the blue page immediately.
- **Why it happened:** VS Code's port forwarding is auto-detected and persistent across server restarts, but it can desync when the remote server has been restarted multiple times or had bind-conflict errors. There's no visible "broken" state — the forward just stops actually proxying. **Tell tale sign: page hangs forever loading instead of erroring out.**

### Problem 2: I scoped kitchen-test as a minimal sandbox instead of a full kitchen build

- **Symptom:** user reaction "this looks NOTHING LIKE THE KITCHEN IN THE PROJECT" after loading kitchen-test.html.
- **Root cause:** I interpreted user's "do this on the side" + "you can decide" + the "-test" suffix as permission to scope down to a feature-validation demo (one fridge, neutral platform). The user's actual mental model: the slug `kitchen-test` mirrors `ozu-test` and `room-1` — a faithful build of the matching source folder, with the hotspot system on top.
- **Fix:** documented the rule in `feedback_test_suffix_means_full_reconstruction.md`. Future sessions: when asked for `*-test`, default to full reconstruction.
- **What's still wrong:** the actual kitchen-test.html still ships a single fridge. Needs a follow-up session to build out cabinets, sink, dish dryer, microwave, surfaces, cooktop area, etc.

### Problem 3: "Address already in use" on `npm run dev`

- **Symptom:** every time the user ran `npm run dev`, Python http.server failed with `OSError: [Errno 98] Address already in use`. User assumed this was the issue.
- **Root cause:** an old `python3 -m http.server 8080` process from an earlier session was still running (PID 457869). It WAS still serving correctly — `curl http://localhost:8080/...` returned 200. The new `npm run dev` couldn't start a second server on the same port.
- **Fix:** told user the old server was fine and they didn't need to restart. Did not kill the process — would have required either a fresh `npm run dev` from them or me starting the server (which is project-prohibited per CLAUDE.md).
- **For next session:** if a clean restart is needed, kill PID with `kill <pid>` then `npm run dev`. The PID can be found with `ss -tlnp | grep 8080` or `lsof -i :8080`.

### Problem 4: Couldn't read screenshot the user shared

- **Symptom:** user shared a path `/var/folders/7c/.../Screenshot 2026-05-06 at 4.45.33 PM.png`.
- **Root cause:** path is on the user's Mac filesystem; Claude Code is running on the Linux GPU server. Filesystems aren't shared.
- **Fix:** asked the user to drag the image into the chat window or paste it (Cmd+V), not paste the path. They moved on without sharing the image — the verbal answer ("localhost:8080" in Local Address column) was enough.

### Problem 5: Window error handler didn't catch module load failures

- **Symptom:** when I added an error catcher with `window.addEventListener('error', ...)`, it didn't show anything when the page hung — even though clearly *something* was wrong.
- **Root cause:** the page wasn't actually erroring — it was hanging on the network fetch (Problem 1, Layer 2). No error fires for a stalled connection.
- **Mitigation:** added a watchdog setTimeout that fires after 4s if `window.__moduleStarted` was never set, plus a `<script nomodule>` fallback. These would have caught a genuine module failure but were powerless against a network hang. The user-visible loading pill (`#loadbox`) staying at "loading…" was the actual signal.

## Learnings and discoveries

### About this user / project

- **`*-test` suffix means full reconstruction, not minimal sandbox.** The naming pattern matches `ozu-test`, not "test page." When the user's source folder has multiple items, build all of them. Confirmed via the kitchen-test pushback. Saved as feedback memory.
- **User is fully non-technical.** They use VS Code Remote-SSH on a Mac, connecting to a Linux GPU server. They don't know what an SSH tunnel is, don't want to type IP addresses, and explicitly refuse complex setup steps ("I DONT WANT THAT http://172.30.30.3"). Default to the GUI path (VS Code panels) over CLI.
- **Walkthrough style works.** When I gave numbered, plain-language steps with concrete buttons/keys to press, the user followed them (e.g. opening DevTools, resetting port forward). When I gave abstract instructions, they bounced.
- **Frustration cues are direct (ALL CAPS, short replies).** "NOTHING JUST LOADING", "I DONT WANT THAT". When seen, simplify and reduce decision points immediately. Don't ask follow-up clarifying questions; act.

### About the dev environment

- **VS Code Remote-SSH port forwarding can silently hang.** The PORTS tab shows the port as forwarded with `localhost:8080` as Local Address, but actual connections stall. Reset by removing + re-adding the port. **This is the single most useful diagnostic to remember for this user.**
- **The GPU server (Moha-GPU, 172.30.30.3) is headless.** No DISPLAY, no Wayland, no Chrome. All browser work happens on the user's Mac via VS Code's port forwarding. SSH client comes from 172.20.10.50.
- **Old `python3 -m http.server` processes can survive across sessions.** PID 457869 was running from before this session started and was still serving correctly. The "Address already in use" error from a fresh `npm run dev` is harmless if the old server is healthy.

### About three.js r184 in this project

- The vendored set is minimal: only `OrbitControls`, `RectAreaLightUniformsLib`, `RectAreaLightTexturesLib`, `HDRLoader`, `RGBELoader`. **No `CSS2DRenderer`, no `RoomEnvironment` — would need to be added if used.**
- The importmap pattern works in inline scripts: `<script type="importmap">{ "imports": { "three": "./vendor/three/build/three.module.min.js" } }</script>` followed by `<script type="module">import * as THREE from 'three';</script>`.
- `compileEquirectangularShader()` exists and works in r184 (used by ozu-test) — verified via `grep` in the bundled module.
- The inline OrbitControls in ozu-test has a Mac-trackpad phantom-zoom guard (ignores wheel events for 400ms after mouseup) — important to mirror in any new sandbox or trackpad scrolling will trigger jumpy zooms.

## Architecture and design notes

### Project shape

- Single HTML file per project, self-contained except for vendored three.js. Pattern matches existing `ozu-test.html` and `test.html`.
- `<script type="importmap">` lets inline modules say `import * as THREE from 'three'` while resolving to `./vendor/three/build/three.module.min.js`. Same pattern as ozu-test.
- Per-project asset folder mirrors the file: `kitchen-test/` next to `kitchen-test.html`. Source-of-truth product data stays in `appliances-and-furniture/` (cross-project reference).

### Hotspot system architecture

- **No CSS2DRenderer dependency.** Manual screen-space projection: `worldPos.clone().project(camera)` → NDC → pixel coords → DOM `transform: translate()`. Updated each frame inside `tick()`. Works on any version of three.js, doesn't add a vendored example file.
- **Visibility test:** if projected `v.z >= 1`, the world point is behind the camera; the button is set to `visibility: hidden`. Otherwise positioned. (Doesn't yet handle occlusion — a hotspot on the back of an object will still show through. Acceptable for v1; raycast-based occlusion is a future improvement.)
- **DOM separation:** `#hotspots-layer` is a single fixed-positioned overlay with `pointer-events: none`. Individual `.hotspot` buttons re-enable `pointer-events: auto`. This keeps the canvas underneath orbitable everywhere except directly on a dot.
- **Popover positioning:** computed each frame while open (so it follows camera moves). Top/bottom flip; left/right clamping; arrow x clamped independently so it always points at the hotspot even when the popover edge is anchored.
- **Focus management:** opening the popover calls `closeEl.focus()` (close button gets focus). Closing returns focus to the originating hotspot button. No focus-trap (popover is `aria-modal="false"` implicitly).

### Why procedural environment instead of HDRI

- Kept kitchen-test self-contained: no dependency on `ozu-test/hdri/kloppenheim_06_puresky_2k.hdr` (which is large and lives under another project's asset folder).
- A simple cube-of-colors PMREM is enough for stainless reflections to look believable in a sandbox. If the kitchen scene grows, swapping to an HDRI is a one-line change.

### Decisions made on user delegation

The user said "you can decide" for: v1 scope, CSS2DRenderer vs manual projection, JSON file vs inline data. My picks were:

| Question | I chose | Rationale | Verdict |
|---|---|---|---|
| v1 scope | fridge only | minimal hotspot validation | **WRONG — see learnings** |
| Projection | manual | no new vendor file, simpler debug | OK; works fine |
| Data format | inline | matches single-file principle | OK; easy to expand |

For future delegations of this kind: when uncertain, default to the more thorough/complete option, not the more minimal one.
