## Learnings and discoveries

### The room-1 map.md is the canonical room-spec template

Read both `room-map.md` (177 lines) and `room-map-photos.md` (45 lines) for room-1. Together they establish a strict convention for how every room in this project should be specified before being built in 3D. The convention:

- **Walls named by feature**, never by direction or coord. `window-wall`, `entrance-wall`, `cabinet-wall`, `ac-wall`. The features are: external walls named after their dominant feature (window-wall, ac-wall, frosted-window-wall, etc); internal walls named after what's on them (entrance-wall = has the door to the corridor; cabinet-wall = has the closet).
- **Opposite-pair model.** Every rectangular room has two pairs of opposite walls. The map declares which two are paired. (cabinet-wall/ac-wall opposite; entrance-wall/window-wall opposite.) Adjacency is derivable from the pairs.
- **Corners = alphabetical wall-pair**. `corner-cabinet-entrance`, never reversed. Each corner has exactly one canonical name.
- **Photos = panorama sweep from each named corner**, clockwise from above, numbered 01..NN. Folder name = corner id. Each per-corner sweep covers two adjacent walls + glimpses of the opposite walls mid-sweep.
- **Photo→wall index** (`room-map-photos.md`) — companion doc that catalogues which photo numbers from which corner show which wall. Used for texture mapping and verification.
- **Furniture anchored to corners**, not coordinates. "Bed head at corner-ac-window."
- **Local coord system** declared at the bottom of the map. Origin at one named corner, +x along one named wall, +z along the perpendicular. Local first; global placement is a separate concern.
- **Top-down ASCII layout** for quick spatial reference.
- **Unverified items section** — explicit list of assumptions (e.g. "exact ceiling height 2.5 m assumed, not on blueprint").
- **Rename script** at the bottom — the maps include the bash to rename letter-coded folders (a, b, c, d) to corner-feature-feature names.

## Architecture and design notes

### Room-map.md as the canonical room spec

The room-1 map.md establishes a structured format that any future Claude session must follow when authoring a new room. Key invariants:

- Every wall has a **feature name**. Two walls cannot share a feature name. Walls are not named by coords or compass directions.
- Walls are paired into **two opposite pairs**. The pairing is declarative (in the map) and must match the 3D model's geometry.
- Corners are derived: corner-X-Y where X and Y are the two wall feature names in alphabetical order. There are exactly 4 corners per rectangular room.
- Photos are organized **one folder per corner**, with files named `<room>-<corner>-NN.webp`. Sweep is clockwise from above, numbered 01..NN.
- Photo→wall index (`room-map-photos.md`) is a separate file that says "photos 02..05 from corner-cabinet-window cover entrance-wall."
- Furniture is anchored by corner ("bed head at corner-ac-window"), not coords. Coords are derived from the local coord system declared in the map.
- The map declares a **local coord system**: origin at one named corner, +x along the wall to one adjacent corner, +z along the wall to the other adjacent corner. The 3D code can use this to model the room locally, then the building-global placement is a separate transform.
- The map ends with **unverified items** — an honest list of what was assumed.

### Why this template matters for F2

When F2 starts (per-room rebuild), each room phase reads its map.md, builds the 3D in local coords following the map's adjacency + corner-anchor model, samples colors from the photos via the photo→wall index, then transforms into the building-global coords. The map removes ambiguity. No more "kitchen counter on z=0 wall" mistakes — the kitchen room map will explicitly say "counter against ldk-bath-wall" and the build code will reference that wall's feature name.

- **Layer 2 — Project entry** (`ozu-test.html`): exterior + chips. ONE URL.
