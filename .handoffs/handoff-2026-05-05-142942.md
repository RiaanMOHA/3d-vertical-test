## Learnings and discoveries

- **`window.devicePixelRatio * 2` for renderer pixelRatio breaks GPU precision.** Don't go above devicePixelRatio (capped at 2) for the renderer. Beyond that, the canvas drawing buffer hits driver limits and produces wavy/curved-edge artifacts.

- **EffectComposer `_pixelRatio = 1` default with custom rt is a real bug to know.** When passing a multisample render target to EffectComposer in r128, you MUST follow up with `composer.setPixelRatio(renderer.getPixelRatio())` or buffers render at logical resolution.

- **EffectComposer in r128 has fundamentally inferior AA vs browser hardware MSAA.** This is the most important finding of the session. If you're seeing persistent jagged edges that survive every AA pass tweak, the answer is to STOP using composer for that scene. Confirmed via four three.js forum threads. Composer should only be used when post-effects (bloom, DoF, vignette, color grading, etc.) are essential to the scene's design — and you accept the AA quality tradeoff.

- **Sub-pixel-thin geometry CANNOT be cleanly anti-aliased.** A 3 cm metal rail viewed at 2 m distance = ~5 pixels wide on screen. AA softens edges but the feature still reads as jagged-thin. Fix the geometry, not the AA.

- **PCF shadow stipple looks like aliasing to the naked eye.** PCFSoftShadowMap with low `shadow.radius` (e.g. 4) produces stippled patterns on flat surfaces. To fix: bump `shadow.mapSize` (finer texels reduce per-pixel stipple) or switch to VSMShadowMap (smooth gradient, no stipple — but global setting risk).

- **SSAA's CopyShader cannot read multisample render targets.** Don't override `ssaa.sampleRenderTarget` with a `WebGLMultisampleRenderTarget`. The fsQuad copy uses sampler2D which requires a resolved (non-multisample) texture.

- **TAARenderPass without `accumulate = true` is just SSAA.** Default `accumulate = false` falls through to `super.render()` (SSAARenderPass). For temporal accumulation, set `accumulate = true`, but then OrbitControls damping/jitter will cause ghosting on still scenes.

- **OrbitControls in this project have NO damping.** Every mouse delta directly translates to camera movement at 0.005 rad/pixel. This causes continuous sub-pixel motion that interacts poorly with any temporal AA technique.

- **Existing PBR texture asset folder I keep missing across sessions:** `ozu-test/room-1-textures/painted_plaster_wall/`, `wood_floor/`, `dark_wood/` — three full PBR map sets (diff + rough + nor_gl) downloaded but never wired up. Phase 3a of the cutting-edge plan is mostly wiring, not researching.

- **Three CanvasTextures in room-1 lacked anisotropic filtering** at lines 5099 (buildingsTex), 4944 (ceiling), 5427 (linen lamp shade). All three now have `anisotropy = max + LinearMipmapLinearFilter` applied. Important pattern for any future canvas-derived texture in this project.

## Architecture and design notes

**The AA pipeline pivot (this session's most important architectural decision):**

After ~10 iterations of fighting jagged edges through composer-based AA tweaks, web research confirmed the fundamental issue: **EffectComposer in three.js r128 cannot match the renderer's native browser MSAA quality**. This is a documented limitation in the three.js ecosystem.

Decision: bypass EffectComposer entirely for room-1. All scenes (exterior, interior, room-1) now use plain `renderer.render(scene, camera)` with `antialias: true`. Browser hardware MSAA does the AA work uniformly across all scenes.

**Trade-offs of this decision:**
- ✅ Edge quality is now uniform across all scenes (matches the user's existing experience with exterior/interior).
- ✅ Performance significantly improved (no SSAA brute-force, no oversample, no multi-pass composer).
- ❌ Lost bloom halo on lamps. Lamps still glow via emissive material but without the soft post-process halo.
- ❌ Future post-effects (DoF, vignette, color grading) are now harder — need composer back, with documented quality tradeoff.

**For room-1's planned cinematic effects (Phase 2c god-rays, future DoF/vignette), one of these paths:**
1. Build the effect as in-scene geometry (e.g. additive cone mesh for god-rays — already in the plan) rather than as a post-pass. Keeps renderer.render path.
2. Re-introduce composer ONLY when an effect is active (e.g. composer when lamps are on for bloom; renderer.render when lamps off). Complex but viable.
3. Accept the AA tradeoff and use composer permanently — but only after user has explicitly seen the difference and chosen.

**Geometry-thickness rule established this session:**
> Any 3D feature thinner than ~5 cm at typical viewing distance will show visible aliasing regardless of AA settings. If a feature must remain photo-faithfully thin, it WILL look slightly rough. The decision is: photo-faithful + slight roughness, or thicker + clean.

Applied to bedposts, mullion, window frame this session. May need to be applied to: doorknob, intercom button, light switch, frosted glass pane (depth), curtain rings.

**EffectComposer + custom render target + pixel ratio recipe (for future reference, IF composer is ever needed again):**
```js
const w = window.innerWidth, h = window.innerHeight;
const dpr = renderer.getPixelRatio();
const rt = new THREE.WebGLMultisampleRenderTarget(w, h);  // LOGICAL dims
rt.samples = 8;
const composer = new THREE.EffectComposer(renderer, rt);
// CRITICAL: with custom rt, composer defaults _pixelRatio = 1.
// Force it to match the renderer or buffers will be sized at logical
// resolution and the canvas will browser-stretch the result to retina.
composer.setPixelRatio(dpr);
// composer.setSize(w, h) takes LOGICAL dims; effective dims = w * dpr.
```
