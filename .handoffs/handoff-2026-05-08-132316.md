## Problems encountered and how they were solved

### Problem 1: Page wouldn't render at all (black screen) due to broken three.js import
- **Symptom:** After applying the 4 photo-fix changes, page reloaded to a black screen. JS was syntactically valid (`node --check` clean). HDRI file existed.
- **Root cause:** `ozu-test.html:408` imports `RectAreaLightUniformsLib` from `vendor/three/examples/jsm/lights/RectAreaLightUniformsLib.js`. That file at line 1 does `import { UniformsLib } from 'three'`. The vendored three.js is the **minified** ESM build (`three.module.min.js`), which does NOT export `UniformsLib`. The minifier strips it because it's not in the public API surface. Result: `Uncaught SyntaxError: The requested module 'three' does not provide an export named 'UniformsLib'`.
- **Fix:** Commented out the import at `ozu-test.html:408` and the `RectAreaLightUniformsLib.init()` call at line 446. The `RectAreaLight` at `~line 4175` (room-1 scene's window sunbeam) will fall back to default un-LUT'd behaviour. Acceptable because room-1 is locked per memory rule.
- **Lesson:** The minified ESM build doesn't re-export internal symbols that addons depend on. Either the unminified build needs to be vendored, OR addons that depend on internal symbols can't be used. This was a pre-existing bug, not from this session's work — but had been hiding the entire scene for an unknown duration.

### Problem 2: Brown plank visible on rooftop (Phase 3d)
- **Symptom:** After changing the wood-plank ceiling color from cream to distressed brown-tan to match photos, the brown was visible from outside the building (orbit-from-above view).
- **Root cause:** The interior scene has no roof. Each `makeCeiling` creates an isolated `BoxGeometry` with the same material on all 6 faces. From an orbit camera above the building, the camera sees the TOP face of every ceiling box. The brown stood out against the surrounding cream ceilings.
- **Fix:** Changed the plank ceiling from a `makeCeiling()` call to a manual `Mesh` build with a 6-material array. Top face (index 2) uses plain `matCeiling` (no plank, just cream); bottom + sides use `matPlankCeiling` (with plank texture). From below the user sees the plank pattern; from above they see plain cream.
- **Lesson:** When the scene has no roof, ceiling top faces ARE visible from orbit. Per-face material arrays on `BoxGeometry` are the clean fix for this kind of "different appearance from each side" requirement.

### Problem 3: 5 mm step exposed side faces with stretched-UV texture
- **Symptom:** After bumping the F1_ROOMS y-offset from 1mm to 5mm to defeat z-fighting, "white seam lines" appeared on wood floors across multiple rooms.
- **Root cause:** The 5mm step exposed the side face (5mm tall) of the upper box at room boundaries. `BoxGeometry`'s side faces use the same texture as the top with the texture's repeat applied across all faces — but the side face is 5mm tall × box-width, so the texture is heavily compressed vertically, reading as a thin near-white strip.
- **Fix:** Reverted the step entirely. Tried polygonOffset (Attempt 2) and base slab (Attempts 4-5), all of which introduced their own issues. Final state: back to the original 1mm step.
- **Lesson:** Vertical steps between coplanar floor regions expose the side face of `BoxGeometry`. The side face renders with stretched UVs that almost always look wrong. Better to keep floors coplanar and resolve depth via something other than geometric step.

### Problem 4: polygonOffset isn't reliable at orbit distance
- **Symptom:** Used `polygonOffset: true, factor: -1, units: -1` on coplanar floor boxes. Worked at first but later caused alternating-stripe z-fighting in the central corridor and around the stair shaft.
- **Root cause:** polygonOffset's effective bias = `factor × max_z_slope + units × min_resolvable_increment`. At orbit distance ~15m with depth-buffer precision around 1mm, the bias is right at the precision edge and intermittently fails to win the depth test.
- **Fix:** Reverted to original 1mm physical step on 1F. For 2F, opted to merge same-material boxes instead of using polygonOffset.
- **Lesson:** polygonOffset is great for nearby coplanar surfaces but unreliable at orbit distance with default bias values. Higher `factor`/`units` values help but compound visible distortion. Physical separation is more reliable for orbit-camera scenes.

### Problem 5: 1mm base slab caused 1F regression
- **Symptom:** Dropped the 2F base slab to `F1H - 0.001`, which the user said would "physically separate" base from per-room. But the user reported "1F is much worse now. LDK wood is visible underneath through the 1mm gap."
- **Root cause:** The 2F base slab's depth precision at orbit distance was still ambiguous with the per-room boxes (top faces only 1mm apart in y), causing visible bleed-through. ALSO — and this is the fundamental architectural issue the user pointed out — having the LDK as a full-footprint base on 1F means every other room's floor sits ON TOP of LDK wood. Any depth precision failure causes LDK wood to show through. The user views this base-under-everything pattern as wrong.
- **Fix:** Reverted everything. User's architecture rule: "Each room should own its own floor, sized exactly to its footprint. Seams between adjacent same-material rooms should be closed by extending the room boxes themselves to share an edge, not by adding a base underneath."
- **Lesson:** The "full-footprint base layer" pattern (used by LDK on 1F) is not a clean solution — it's a workaround that exposes its base material through any depth precision failure. The user's preferred architecture is each-room-owns-its-footprint with adjacent-extend rather than base-catch-all.

### Problem 6: I misdiagnosed the original z-fighting issue as 1F-specific
- **Symptom:** When the user first reported "Floor rendering is glitching in interior view", I assumed they meant 1F (because the existing y=0.001 setup was the only place I saw "overlapping floors at the same height" in code). ## Learnings and discoveries

### The `RectAreaLightUniformsLib` import was hiding the entire scene
The minified three.js ESM build (`vendor/three/build/three.module.min.js`) doesn't export `UniformsLib`. Any addon that depends on `UniformsLib` (e.g. `RectAreaLightUniformsLib`, possibly others) will throw at import time. The page won't render at all. Until a non-minified three is vendored, addons depending on internal symbols must be commented out.

This is a **persistent bug**, not from this session. Likely entered when someone added the import without testing the minified-build constraint. Worth documenting in master-plan or vendor README.

### The "full-footprint base layer" pattern is a footgun
1F uses LDK as a full-footprint base slab with other rooms layered on top at y=0.001. This works visually most of the time, but the moment depth precision fails, the LDK wood bleeds through into rooms that should have non-wood floors (bathroom, washroom, toilet, kitchen). The user's view: this pattern is architecturally wrong. Each room should own its footprint.

Future floor work should AVOID this pattern. Better to clip each room's box to its actual footprint and accept hairline gaps at boundaries (catch them via merges or tiny extends rather than a universal base).

### 1F looks clean = LDK base catches gaps in wood color; 2F seams = 1F ceiling cream bleeds through
This is the actual mechanism for the "white seam" reports on 2F:
- 1F has the LDK base (wood-colored) catching every gap → gaps invisible
- 2F has no base; under the 2F floor at y=2.45 sits the 1F ceiling top (cream `0xf3efe6`) → gaps expose cream

This insight came from the discovery phase (Phase 4a). The user found it persuasive enough to choose the same-material-merge approach.

### Texture-scale mismatch at room boundaries
Each F2_ROOMS box gets `texture.repeat = (density × dx, density × dz)`. Different room sizes → different repeat counts → different texture-grain scale at adjacent boundaries. Even when adjacent boxes share a material, the wood-grain pattern abruptly jumps in scale at the boundary, which reads as a "seam".

The fix (lever #2 in the discovery proposal) is **world-aligned UVs**: set `texture.offset = (density × x0, density × z0)` and `texture.repeat = (density × dx, density × dz)`. This makes the texture a single continuous pattern across all boxes (using world coordinates as UV space). The user did NOT pick this lever this session — went with merges first — but it's the next obvious improvement.

### Asking the user "which floor / which area" earlier saves cycles
This session burned 5 attempts on the floor seam issue. The first 2-3 would have been avoided if I'd asked "is this on 1F or 2F or both?" before touching `F1_ROOMS`. Per memory rule `feedback_review_before_continuing`.

## Architecture and design notes

### User's floor architecture rule (new this session)
The user articulated a clear architectural rule for floor geometry:
1. **Each room owns its own floor**, sized exactly to its footprint.
2. **No full-footprint base slab pattern.** The LDK on 1F is the only existing instance and the user views it as wrong.
3. **Adjacent same-material rooms** should be MERGED into single boxes when their union is rectangular, OR extended to share an edge (slight overlap) when not.
4. **Adjacent different-material rooms** are inherently distinct; their boundaries may show seams which need separate treatment (tiny extends, or accept).

Future floor work — including any 1F refactor to remove the LDK base — should follow this rule.

### Per-face material array on `BoxGeometry` ceiling
The plank ceiling at the stair shaft is built manually with a 6-material array (`[matPlankCeiling, matPlankCeiling, matCeiling, matPlankCeiling, matPlankCeiling, matPlankCeiling]`) so the top face (index 2) renders as plain cream and the bottom + sides render with the plank pattern. This pattern is reusable for any "different appearance from above vs below" requirement in a roofless scene.

`BoxGeometry` face order is `[+X, -X, +Y, -Y, +Z, -Z]` → index 2 = top, index 3 = bottom.

### Why polygonOffset isn't reliable at orbit distance
Three.js `polygonOffset: true, factor: -1, units: -1` works well for nearby coplanar surfaces (close camera) but at orbit distance ~15m the effective bias is right at depth-buffer precision, so it intermittently fails to win. Higher factor/units values reduce the failure rate but compound visible distortion. **Physical separation in y is more reliable for orbit-camera scenes** — but a vertical step exposes side faces on `BoxGeometry` (with stretched UV that reads as a thin strip). The clean solution for coplanar floor-vs-floor is to NOT have coplanar faces — geometry-level merge or extend instead.

### Levers for the 2F floor seam problem
Three independent levers identified during discovery, each addressing a different symptom:
1. **Geometric seams** (gaps between boxes exposing 1F ceiling cream below) — fix via same-material merges + tiny extends
2. **Texture-scale jumps at boundaries** (wood-grain pattern abruptly changing scale across rooms) — fix via world-aligned UVs (`texture.offset = density × box_origin`)
3. **Tint differences between rooms** (different floor tones) — intentional, leave alone

These levers can be applied independently. Lever #1's first move (same-material closet merges) was applied this session. Lever #2 and lever #1's second move (tiny extends) are pending user direction.
