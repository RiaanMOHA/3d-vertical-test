### Problem 2: Cylinder rotation math for handrails

- **Symptom (caught before writing):** Initial draft of the lower-flight handrail had `rail.rotation.x = -Math.PI / 2 + Math.atan2(dy, dz)`. Verified with a test point: this would orient the cylinder in the WRONG direction (negative Z extent instead of positive).
- **Root cause:** Wrong derivation. Three.js's CylinderGeometry has its default axis along +Y. To align the cylinder along a target direction (dy, dz) in the y-z plane (rotating around X axis), the correct formula is `rotation.x = Math.atan2(dz, dy)`.
- **Fix:** Re-derived from first principles. Rotation around X by θ takes (0, 1, 0) → (0, cos θ, sin θ). Setting equal to (dy_n, dz_n) gives cos θ = dy_n and sin θ = dz_n, so θ = atan2(dz, dy). Sanity-checked: dz=0 → θ=0 (vertical, matches +Y); dy=0 → θ=π/2 (horizontal along +Z). ✓
- **Same logic for upper flight** in x-y plane (rotating around Z): `rotation.z = Math.atan2(-dx, dy)`. The negative sign on dx comes from the rotation-around-Z formula `+Y → (-sin φ, cos φ)`.
- **Lesson:** Don't trust intuition for axis-rotations on three.js Object3D. Default cylinder axis is +Y. Derive rotation explicitly from the target direction vector. Validate with at least one sanity-check value before writing the edit.

### Problem 3: ExtrudeGeometry orientation for the lower-flight wedge

- **Symptom (caught before writing):** First sketch tried `wedge.rotation.y = Math.PI / 2`. Sanity-checked vertex (4.50, 0, 0) → world (0, 0, −4.50). That's the wrong sign for z.
- **Root cause:** Three.js Y-rotation by +π/2 sends mesh-local +X to world +Z and mesh-local +Z to world −X. I needed the opposite: mesh-local +Z (depth direction) → world +X.
- **Fix:** Use `rotation.y = -Math.PI / 2` and `position.set(LX0, 0, 0)`. Verified: vertex (4.50, 0, 0) → world (0, 0, 4.50), then translated to (LX0, 0, 4.50). Vertex (4.50, 0, LW) → world (LW, 0, 4.50), then translated to (LX0+LW, 0, 4.50) = (LX1, 0, 4.50). ✓ extrusion goes from x=LX0 to x=LX1 in world.
- **Lesson:** When using ExtrudeGeometry with rotation, derive a single test vertex's transform manually before committing. The sign of the rotation matters because three.js uses right-hand-rule.

### Codebase patterns (Phase 5-specific)

- **ExtrudeGeometry for stair geometry:** the cleanest way to make a triangular prism wedge in three.js is `new THREE.Shape()` defining the 2D triangle, then `ExtrudeGeometry(shape, { depth, bevelEnabled: false })`. Default extrusion is along +Z. To orient the prism in different planes, rotate the resulting mesh: rotation.y = ±π/2 swaps X↔Z, rotation.x = ±π/2 swaps Y↔Z. Plus a position.set(...) to anchor the front face at the desired world location.
- **Cylinder along arbitrary direction:** default axis is +Y. To align with direction (dx, dy, dz):
  - In y-z plane (constant x): `rotation.x = Math.atan2(dz, dy)`
  - In x-y plane (constant z): `rotation.z = Math.atan2(-dx, dy)`
  - General 3D: use `quaternion.setFromUnitVectors(new Vector3(0, 1, 0), targetDir.normalize())`.

### Codebase patterns (Phase 6-specific)

- **F2_WIN_FRONT/BACK/LEFT/RIGHT pattern:** the interior 2F walls are built as `wallX/wallZ` calls that consume `F2_WIN_*.map(w => [w.a, w.b])` for the gaps, plus a `for (const w of F2_WIN_*) addWinFlex(...)` loop for the glass + frame + sill + header. Adding a new exterior window on a wall that already has the array means just push a new entry to F2_WIN_* — NO other code changes needed in the interior scene.
- **F2_WIN_RIGHT was missing entirely** before this session. Created it. Now the pattern is symmetric: FRONT/BACK/LEFT/RIGHT all exist as parallel arrays.
- **Exterior scene is more verbose:** windows on exterior walls require manual solidWall(...) breakup for the wall around the aperture (pre-window, sill, header, post-window) PLUS a paneSide(...) or paneFront(...) call for the glass + trim. The exterior scene doesn't have an addWinFlex equivalent — sills/headers must be hand-rolled with solidWall.

### Blueprint annotations decoded

- Window callout pattern: `FL+{height_mm} {型|トーメイ} {WWWHH} {window-type}` where:
  - `型` = pebble-glass (frosted) — used for 縦すべり, 横すべり
  - `トーメイ` = transparent — used for 引違 (sliding)
  - `WWWHH` = standard size code, ww00hh format. 02609 = 260 wide × 900 tall mm. 11909 = 1190×900. 15009 = 1500×900. 16020 = 1600×2000 (full-height). 16009 = 1600×900. 02607 = 260×700. 06003 = 600×300. 03603 = 360×300.
  - `FL+1900` etc = top of frame at floor + 1900 mm. The bottom = top − height.
- Cabinet annotation: `L=2550` next to cabinet name = total length 2550 mm. Likely a length not a height.
- Stair annotation: `蹴上230以下　踏面225（廻り部150）幅750以上` = riser ≤ 230, tread 225, winder portion 150, width ≥ 750. The 廻り部 phrase is the indicator that the L-stair has WINDER STEPS at the corner.

## Architecture and design notes

### Stair geometry pattern (Phase 5)

The boxed-stair upgrade pattern is now: keep the per-step tread + riser as boxes, replace the per-step "body" stack with a single ExtrudeGeometry triangular prism wedge per flight (smooth diagonal underside), add a closed-string side board on the open side, add a handrail (wall-mounted with brackets, OR stringer-mounted with newel posts depending on what's available).

Materials reused:
- `treadMat` / `riserMat` / `carriageMat` — pre-existing.
- `stringerMat` (NEW) — slightly darker than carriageMat for visual differentiation.
- `handrailMat` (NEW) — even darker, semi-glossy.
- `handrailBracketMat` (NEW) — chrome-like for the wall brackets.

The wedge approach is preferable to the per-step stack because (a) it produces a smooth slope visible from below, (b) it's a single geometry instead of N geometries, (c) it generalizes to any stair shape including the upper flight where the wedge floats above the lower flight's landing.

### F2_WIN_RIGHT pattern (Phase 6a + Fix 1)

The interior scene now has a complete set of 4 exterior-window arrays (FRONT, BACK, LEFT, RIGHT) — symmetric. Adding a new 2F exterior window on any side is now a one-line array push + the corresponding solidWall + paneSide call in the exterior scene. The architecture supports the full 9-window blueprint count.

### Genkan cabinet wraparound pattern (Fix 2)

The cabinet body is one continuous box that visually penetrates the genkan-corridor partition wall. Inside the cabinet's volume (x=5.85..6.20, y=0.05..2.40, z=4.65..7.20), the wall slab at z=6.30 is fully engulfed — the cabinet completely hides it. This works visually because:
1. No surface coplanarity between cabinet body and wall slab (cabinet faces all OUTSIDE the wall slab's bounding box) → no z-fighting.
2. The wall slab is interior to the cabinet, never exposed to the camera.

This is a workaround. The "structurally correct" version would either:
- Remove the wall fragment at z=6.30, x=5.85..6.20 (extend the genkan-corridor doorway gap to include the cabinet's x range), OR
- Build the cabinet as two separate pieces (corridor portion + genkan portion), each abutting the wall but not crossing it.

Per the photo, real Japanese 玄関収納 + 物入 typically appear as continuous closets even though they may technically be separate fixtures on either side of an internal partition. The wraparound rendering matches the visual reality even though it cheats on the underlying structure.

### Audit-vs-execute mode

This session demonstrated the value of switching from execute mode to audit mode mid-session. Phase 6 was completed in execute mode (room-4 frosted added). Then the user requested a blueprint↔code audit. The audit caught the room-1 frosted (missed by the master plan and by my Phase 6 execution) and the genkan cabinet length (missed by my Phase 3 execution from prior session). Both required user authorization to fix, but the existence of the bugs was unambiguous because counting blueprint windows is deterministic.

**Pattern to remember:** after a phase that creates new geometry, do a quick blueprint cross-check before declaring it done. Specifically: count windows per floor; check any blueprint annotation strings (L=, FL+) that touch the modified geometry; check general-note strings (蹴上, 踏面, 廻り部 etc.) that affect the modified geometry's dimensions.
