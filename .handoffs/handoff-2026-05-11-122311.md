### Recipe-internal finding — Kumamoto sun direction calc
The recipe gives the sun direction-TO-sun for azimuth 160°/elev 60° as `(0.171, 0.866, -0.470)`. That's correct in the +X-east/+Y-up/+Z-north convention. I verified by hand: sin(160°)·cos(60°)=0.171, sin(60°)=0.866, cos(160°)·cos(60°)=-0.470. Important because the SUN DirectionalLight position must be `sunDir * distance` and the target is the room center — common bug is to invert this.

## Architecture and design notes

### LDK is its own sandbox sibling to laundry-test + kitchen-test
Per the recipe Section 0 ("The room sandbox pattern"), every interior render lives in its own self-contained sandbox. `living-dining-test.html` follows that pattern:
- Single self-contained HTML file (~2500 lines)
- Mirrors `laundry-test.html` structure section-by-section (renderer → controls → HDRI → hemisphere → texture helpers → materials → room shell → windows → lighting → furniture → hotspots → postprocessing → loop)
- Paired folder `living-dining-test/{bake, textures/lightmap, textures/ao}/`
- Index card in `index.html`

This isolation means tuning LDK doesn't affect laundry-test or the master `ozu-test.html`.

### Per-face material clones — the lightmap-readiness pattern
The recipe Section 3 (room shell) shows that each wall face needs its own material clone so future per-face lightmap PNGs can attach independently. I followed this faithfully:
- `matWallStairs` (west), `matWallGarden` (south), `matWallKitchen` (north), `matBrickEast` (east)
- `matWallStairwellS` (south stairwell partition), `matWallStairwellE` (east stairwell partition)
- `matAlcoveBrick` (kitchen alcove back wall — separate from `matBrickEast` since the alcove brick is BEHIND the LDK's east wall, different surface entirely)

The brick-wall and kitchen-wall fragments don't currently call `setLightmapUV1()` because the runtime materials don't have `lightMap` set yet. That wiring happens in the post-bake step.

### Kitchen alcove pattern — backdrop, not a build
The user's scope correction at Phase 7e established a critical principle: **the LDK sandbox does NOT include the kitchen build, even though the pass-through opens into the kitchen.** What's behind the pass-through is a 0.85m-deep BACKDROP — just enough surfaces to read through the opening (brick splash + fridge + range hood + side returns + floor/ceiling continuation). No counters, cabinets, faucet, cooktop, etc. The full kitchen lives in `kitchen-test.html`.

This pattern is worth a memory entry for similar situations: when a sandbox's wall has an opening into another room, model only what's VISIBLE through the opening as a backdrop.

### Daylight rig differs from laundry-test
Laundry-test has a NORTH-facing window (no direct sun, recipe Case A) — uses cool DirectionalLight + RectAreaLight + sky proxy as a 3-piece rig where pieces 1+3 are SEPARATE.

LDK has SOUTH-facing sliders (Case B) + EAST-facing brick window (Case C). At Kumamoto 11 AM, the SUN is high SSE and DIRECTLY enters both. So I used ONE DirectionalLight (the real sun, casts shadows) covering both windows. Each window also gets its own RectAreaLight at the aperture for diffuse fill.

The sky proxies use `multiplyScalar(2.0)` — LOWER than laundry's 2.4 because clear glass shows the proxy directly (no frosted blur), so over-bright would whiteout.

### TV console position is layout-driven, not aesthetic
CON_CX = 2.775 specifically because:
- Stair partition east face at x = STAIR_X1 = 0.90
- Corridor entry door at x = [1.10, 1.90]
- Pass-through at x = [3.65, 6.20]
- TV console sits in the available solid mid-section: x = [1.95, 3.60]
- Center of available width = (1.95 + 3.60) / 2 = 2.775
- CON_W = 1.65 leaves 5cm clearance each side

If user later wants to move corridor entry or pass-through, TV console position needs to move with them. They are coupled.

### Bake-target fragmentation choice
For the kitchen-wall (3 openings would be needed — corridor + pass-through and the north end of stair carve-out which is already handled by the kitchen-wall fragment scope-limit), I split into 6 separate quads instead of using polygon-with-multiple-holes. Trade-off:
- + Simpler triangulation (no special cases)
- + Each fragment can have its own lightmap PNG (more granular control)
- − 6 PNG files instead of 1 (modest disk overhead, ~6MB total at 1024² PNG)
- − 6 separate bake calls instead of 1 (modest setup overhead)

Net win for code clarity. Kept the same 1-hole pattern for garden-wall (split into left + right halves at the mullion since each half has 1 cutout) and brick-wall (1 cutout, 1 polygon).
