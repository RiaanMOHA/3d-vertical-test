## Learnings and discoveries

### `bpy.ops.uv.smart_project` is incompatible with three.js BoxGeometry

Blender's SmartUV creates auto-packed island layouts that include all 6 box faces. Three.js's `BoxGeometry` has its own standard per-face UVs (each face gets [0,1]² independently). The two layouts cannot be reconciled — sampling SmartUV-baked PNGs with default BoxGeometry UVs produces visual garbage.

**Solution pattern:** use planar projection in the bake. All 6 box faces share the same projection along the inside-face normal axis. Hidden faces' UVs overlap but they're not visible at runtime. The runtime mirrors the same projection on the same BoxGeometry's `uv1` attribute (manually built from `geometry.attributes.position`). This produces pixel-perfect lightmap alignment on the visible inside face.

Saved in this session's [bake_room_ao.py](stairs-test/bake/bake_room_ao.py) + [bake_room_lightmap.py](stairs-test/bake/bake_room_lightmap.py) + the `setPlanarUV1` helper in [stairs-test.html](stairs-test.html).

### Three.js `Texture.channel = 1` for aoMap + lightMap

In three.js r184, `aoMap.channel` and `lightMap.channel` default to either 0 or 1 depending on version. Setting `t.channel = 1` explicitly on a Texture object guarantees it samples `geometry.attributes.uv1` (the modern attribute name; `uv2` is the legacy alias).

### A6000 parallel bake pattern

Both A6000 GPUs (~48 GB each, both idle) can run different Blender bakes in parallel. Pattern: spawn both as `run_in_background` Bash calls using `CUDA_VISIBLE_DEVICES=0` and `=1`. Both finish in 15 s for the stair scene. This effectively halves bake time.

### Japanese 4-winder L-bend geometry (key reference for future stair builds)

For 4 winders making a 90° L-bend in a square (W × W):
- Pivot at SE corner of the square (for CW turn: lower flight ascends N, upper flight ascends E)
- 5 boundary lines fanning from pivot at theta = 180° (south wall), 157.5°, 135° (diagonal — hits NW corner), 112.5°, 90° (east wall)
- Each winder is a triangle: apex at pivot, two corners on adjacent boundary lines
- Each radial boundary line at theta hits the WEST wall (x=0) if `tan(180°-theta) > 1`, else the NORTH wall (z=W)
- For W=W (square), the diagonal at theta=135° hits the NW corner exactly
- Helper constants: `TAN22 = Math.tan(Math.PI / 8) ≈ 0.4142`
- Outer endpoints (for runtime): `P_W_157 = [0, WB_Z0 + W*TAN22]`, `P_N_112 = [W - D*TAN22, WB_Z1]`

## Architecture and design notes

### Planar UV bake → planar UV runtime pattern

When baking a per-surface PBR map (AO or lightmap) on a Blender plane/box for use on a three.js `BoxGeometry`, the bake's UV layout MUST be deterministic and reproducible at runtime. Pattern established this session:

**In the bake script (Python):**
```python
def planar_uv_project(obj, axis):
    me = obj.data
    if not me.uv_layers:
        me.uv_layers.new(name='UVMap')
    uv = me.uv_layers.active.data
    verts = me.vertices
    # Project onto plane perpendicular to `axis`
    if axis == 'x':
        a_lo = min(v.co.z for v in verts); a_hi = max(v.co.z for v in verts)
        b_lo = min(v.co.y for v in verts); b_hi = max(v.co.y for v in verts)
        def proj(co): return ((co.z - a_lo) / (a_hi - a_lo),
                              (co.y - b_lo) / (b_hi - b_lo))
    # ... similar for y, z
    for poly in me.polygons:
        for li in poly.loop_indices:
            v_idx = me.loops[li].vertex_index
            uv[li].uv = proj(verts[v_idx].co)
```

**In the runtime (JS):**
```js
function setPlanarUV1(geom, axis) {
  geom.computeBoundingBox();
  const bb = geom.boundingBox;
  const pos = geom.attributes.position;
  const uv1 = new Float32Array(pos.count * 2);
  for (let i = 0; i < pos.count; i++) {
    const x = pos.getX(i), y = pos.getY(i), z = pos.getZ(i);
    let u, v;
    if (axis === 'x') { u = (z - bb.min.z) / rz; v = (y - bb.min.y) / ry; }
    else if (axis === 'y') { u = (x - bb.min.x) / rx; v = (z - bb.min.z) / rz; }
    else { u = (x - bb.min.x) / rx; v = (y - bb.min.y) / ry; }
    uv1[i*2] = u; uv1[i*2+1] = v;
  }
  geom.setAttribute('uv1', new THREE.BufferAttribute(uv1, 2));
}
```

A `TARGET_AXES` dict maps each surface slug to its axis. Both sides of the pipeline reference the same axis convention.

### 4-winder L-bend fan-from-pivot pattern

For a 90° L-bend stair with 4 winders maintaining consistent stair width:
- Stair sections: lower flight (N straight risers) + 4 winders in a `W × W` square + upper flight (N straight risers)
- Winder zone occupies `x = [0, W]`, `z = [WB_Z0, WB_Z0 + W]` (square)
- Pivot at the SE corner = (W, WB_Z0)
- 5 radial boundaries from pivot at theta = 180°, 157.5°, 135°, 112.5°, 90°
- For W = W (square), theta = 135° hits the NW corner exactly (the diagonal)
- Each winder is a TRIANGLE: apex at pivot, two corners on consecutive boundary radial endpoints
- Risers between adjacent winders are along the radial boundaries (oriented along the angle from pivot)
- Nosing inlay strips run along each winder's leading edge (the boundary CW from its position)

This pattern matches blueprint area exactly: `W × N × TREAD + W × W = total_footprint`. With W=0.9, N=3, TREAD=0.225: `0.6075 + 0.81 = 1.4175 ≈ 1.42 m²` (printed label).

### Shell strip pattern for "geometry only" views

When a user wants to see ONLY the primary geometry of a scene (e.g., the stair) without surrounding context, the strip pattern is:
1. Delete all wall/floor/ceiling/parapet/detail invocations
2. Keep the material declarations (cheap, allows quick re-attachment)
3. Keep dimensional constants that other code references (e.g., `PARAPET_H` used in handrail math)
4. Update vantage button targets to focus on the primary geometry
5. Reduce or remove decorative lighting elements (sky proxy planes) — they appear as floating planes without their hosting walls
6. Keep functional lighting (directionals, hemi, HDRI environment) — these still illuminate the primary geometry

### Coordinate system for the rebuilt stair

- Origin: SW corner of 1F lower-shaft, at 1F floor level (y = 0)
- +X = east (across stair width AND upper-flight ascent direction)
- +Y = up
- +Z = north (lower-flight ascent direction)
- Lower flight: x ∈ [0, STAIR_W=0.9], z ∈ [0, LF_Z_END=0.675], y from 0 to 3*RISE
- Winder zone: x ∈ [0, 0.9], z ∈ [WB_Z0=0.675, WB_Z1=1.575] (0.9 × 0.9 square), y from 3*RISE to 7*RISE
- Upper flight: x ∈ [UF_X0=0.9, UF_X1=2.25] (6*TREAD=1.35 m), z ∈ [SH_Z0=0.675, SH_Z1=1.575] (0.9 m wide), y from 7*RISE to F1H=2.5
