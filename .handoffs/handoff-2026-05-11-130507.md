## Problems encountered and how they were solved

### Problem 1: Room-2 room-map.md compass orientation is internally inconsistent

- **Symptom:** Room-2's `room-map.md` states `window-wall=N, ac-wall=E, closet-wall=W, entrance-wall=S` in the compass section. But the "corners" table lists `corner-ac-closet` and `corner-entrance-window` as adjacent walls. In the stated compass orientation, ac (E) and closet (W) are OPPOSITE walls, not adjacent — so corner-ac-closet shouldn't exist.
- **Root cause:** The compass diagram in room-map.md is wrong. The corner-list and the photos are correct.
- **Fix:** Trusted the corner list + photos. Used the same wall topology as room-1 (window opposite closet, ac opposite entrance) and just ignored the compass diagram. Documented in the room-2 scene block comment.
- **Lesson:** When room-map.md and photos disagree, the photos win. The `unverified items` section of room-map.md flags that compass orientation was "Phase C locked in" — but the diagram itself was sloppy.

### Problem 2: box() helper creates a fresh material per call → PBR maps weren't being applied to all hutch/cabinet surfaces

- **Symptom:** After baking the room-2 hutch painted-wood PBR and creating `matHutch` from the maps, only the surfaces that referenced `matHutch` directly (none — it was just declared) got the PBR. All the visible hutch panels were built via `box(..., 0x9aa6b0, {...})` calls that each construct their OWN flat-color MeshStandardMaterial.
- **Root cause:** The `box(w, h, d, cx, cy, cz, color, extra)` helper at the top of the build function creates a new MeshStandardMaterial per call with the supplied color. Sharing a material across calls requires using `new THREE.Mesh(geometry, sharedMat)` directly.
- **Fix:** Created inline helpers in the affected scopes — `hutchBox(w, h, d, cx, cy, cz)` for room-2 hutch and `woodBox(...)` for room-4 cabinet — that use the shared PBR material. Replaced ~24 box() calls across the two rooms.
- **Lesson:** When converting flat-color surfaces to PBR, audit ALL uses of `box()` (and any other inline color helpers) that need the shared material. A simple "change the matHutch declaration" isn't enough — the call sites have to point at the new material too.

### Problem 3: Wrong wall layout assumption persisted longer than it should have

- **Symptom:** When auditing room-2's photos, I went back and forth multiple times trying to reconcile the camera positions with my coordinate system, getting confused about whether the bed-head was at the entrance corner or the ac corner.
- **Root cause:** I was trying to derive the camera direction from the 01 frame too rigidly. The "01 points at the first-named wall of the corner" convention isn't strict — wide-angle frames show multiple walls at once and the camera may be looking diagonally into the room.
- **Fix:** Stopped trying to derive camera direction algorithmically and just trusted the photo's visible content. If `corner-closet-entrance/01` shows the bi-fold doors AHEAD, the camera is somewhere in the room looking AT the closet-wall, full stop. The exact angle doesn't matter for placing furniture.
- **Lesson:** Use the room-map's tentative camera-position table + visible content of each frame. Don't waste cycles deriving camera trigonometry.

### Problem 4: Closet bi-fold panel overlap with bed-head (room-2)

- **Symptom:** While placing the room-2 bed (head at x=0 against closet-wall, z range [0.85, 1.85]), realized the closet bi-fold occupies z=[0.55, 1.95] at x=0. The bed-head at x=0.05 is essentially RIGHT IN FRONT of part of the bi-fold doors.

Visually the bed nestles in front of the closet — matches photo evidence. The bi-fold doors couldn't open in reality without moving the bed, but that's how the real room is staged.

### Problem 5: Sliding window mullion handle orientation differs between rooms

### Cycles procedural materials → PBR pipeline is reliable

The pattern I established for each PBR bake script:
1. `clear_scene()` + `configure_cycles_optix()` + `add_neutral_world()` (white 1.0-strength background so the bake captures material response, not lighting bias)
2. `make_<material>_material()` — Principled BSDF + Voronoi/Wave/Noise nodes + ColorRamp + Bump → assigned to a single Principled BSDF output
3. `add_plane_for_bake('<slug>_plane', 2.0, 2.0, mat)` — flat 2×2 m plane with the material applied
4. `bake_pass(obj, slug, kind, bake_type)` for each of `(albedo, DIFFUSE)`, `(normal, NORMAL)`, `(roughness, ROUGHNESS)`, `(ao, AO)` — adds an Image Texture node labelled `_bake_target` to the material, sets sRGB or Non-Color colorspace, calls `bpy.ops.object.bake`, saves the image.

This pattern works for any procedural material. Total time per object: 30 sec-1 min on A6000.

### Standalone room sandbox structural template

Every `registerScene('room-N', { build: function(S) { ... } })` follows this structure:

```js
build: function(S) {
  // 1. Room constants
  const RW = ?, RD = ?, RH = 2.50;
  const WT_R = 0.02, FEAT = 0.04, BIAS = 0.003, FRAME_T = 0.07;
  // 2. Wall mapping comment (which wall is at which coordinate)
  // 3. COL palette
  const COL = { floor, ceiling, wall, doorway, frame, ... };
  // 4. Helpers: box, feat, winFrame, pbrMatRN, setUVsByLocal, wallShapeWithHole
  // 5. Procedural ceiling texture (unique random seed per room)
  // 6. Materials: floor PBR, ceiling, wall paint, glass, frosted glass, frame, handle, ...
  // 7. AO loader IIFE (loads room-N-textures/wall_ao/wall_*.png)
  // 8. floor + ceiling meshes
  // 9. 4 walls (2 BoxGeometry, 2 ShapeGeometry with cutouts)
  // 10. Trim: baseboards + crown molding (ZF=0.001 nudge)
  // 11. Windows: sliding window + mullion + chrome handle + frosted privacy window
  // 12. Curtains: 2 fluted bunches + tieback rings + inner sheer
  // 13. Door: doorway-fill + flush trim + slab + 3 hinges + chrome lever
  // 14. Closet: bi-fold panel + seams + recessed pulls OR freestanding storage
  // 15. Coat rack + AC remote + light switch panels
  // 16. AC unit + AC remote-holder
  // 17. Bed: iron frame + bedding + accent pillow
  // 18. Furniture: desk + chair (if present), hutch (if present), shelf (if present), cabinet (if present)
  // 19. Ceiling fixture: cluster pendant OR rattan pendant OR flush mount
  // 20. Phase 5 — Lighting rig (per CLAUDE.md daylight rule based on window orientation)
  // 21. Shadow setup via S.group.traverse, ceiling explicit override
}
```

This template is what should be used for any future standalone room sandbox.

Output is always 4 PNGs per material (`<slug>_albedo.png`, `_normal.png`, `_roughness.png`, `_ao.png`) at 1024² resolution, sRGB for albedo and Non-Color for the rest.

Runtime always loads them via:

```js
function pbrFromBase(base, repU, repV, extras = {}) {
  const loader = new THREE.TextureLoader();
  const map = loader.load(`${base}_albedo.png`);
  map.colorSpace = THREE.SRGBColorSpace;
  const normalMap = loader.load(`${base}_normal.png`);
  const roughnessMap = loader.load(`${base}_roughness.png`);
  const aoMap = loader.load(`${base}_ao.png`);
  const aniso = renderer.capabilities.getMaxAnisotropy();
  for (const t of [map, normalMap, roughnessMap, aoMap]) {
    t.wrapS = THREE.RepeatWrapping;
    t.wrapT = THREE.RepeatWrapping;
    t.repeat.set(repU, repV);
    t.anisotropy = aniso;
  }
  return new THREE.MeshStandardMaterial({
    map, normalMap, roughnessMap, aoMap, aoMapIntensity: 1.0, ...extras,
  });
}
```

### Refactor pattern: `<scope>Box()` helper for shared PBR material

When a furniture section has many `box(w, h, d, cx, cy, cz, color, extra)` calls that need to share a PBR material (because box() creates a fresh material per call), add a tiny inline helper at the top of the scope:

```js
const matFoo = pbrFromBase(...);
const fooBox = (w, h, d, cx, cy, cz) => {
  const m = new THREE.Mesh(new THREE.BoxGeometry(w, h, d), matFoo);
  m.position.set(cx, cy, cz);
  S.group.add(m);
  return m;
};
```

Then replace `box(...)` calls with `fooBox(...)` calls. Used in:
- room-2 hutch: `hutchBox(...)` shares matHutch
- room-4 cabinet: `woodBox(...)` shares matCabWood
