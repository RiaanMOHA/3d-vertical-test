## Problems encountered and how they were solved

### Problem 1 — Watermark "WD-061" tiled into the bake

- **Symptom:** First bake of room-1 produced an albedo PNG with the source image's "WD-061" sample label visible in 5 places across the 2048x2048 output.
- **Root cause:** The source [new-textures/ceiling-woodgrain.jpg](new-textures/ceiling-woodgrain.jpg) has the sample label baked into its bottom-right corner (visible at ~y=1400-1500 of the original 1500x1500). The bake material samples the full image with U via `fract_u` (one plank wide) and V via `sep_uv.Y + plank_hash` (continuously increasing, with a per-plank offset). With `extension = REPEAT` on the image texture node, the bake plane (1m x 1m, tile-sized to fit 5 planks) ends up sampling the full image multiple times. Each plank's hash-shifted V positions place the watermark band at a different vertical offset, producing one watermark per plank that happens to fall in the visible bake window.
- **Fix:** Cropped the source to remove the watermark band. Used Pillow (PIL.Image.crop with box (0, 0, 1500, 1340)) to drop the bottom 160 px. Saved as `new-textures/ceiling-woodgrain-clean.jpg`. Updated all 4 bake scripts via sed to point at the clean version. Re-ran the 4-bake sequence — clean output.
- **Lesson:** When a reference image is provided by the user, ALWAYS scan it for embedded labels / watermarks / colour-card swatches BEFORE feeding it into a bake. The bake will faithfully reproduce whatever is in the source image, including labels you don't intend. Cheap to catch by reading the source image once with the Read tool before writing the bake script; expensive to catch after the bake when 16 PNGs need to be regenerated. Worth a one-line preflight: "is the source image clean enough to be tile-sampled, including its corners?"

### Problem 2 — `magick` and `convert` binaries not installed

- **Symptom:** Tried `magick new-textures/ceiling-woodgrain.jpg -crop ... +repage ...` — exit 127, command not found. Tried `convert` — also not found.
- **Root cause:** ImageMagick is not installed on this Linux box. Memory rule `feedback_imagemagick_repage` references `magick -crop +repage` but assumed availability.
- **Fix:** Python 3's PIL/Pillow is available (`python3 -c "from PIL import Image; print('PIL ok')"` returned ok). Used Pillow to crop instead. `im.crop((0, 0, 1500, 1340))` returns a new image with the bottom 160 px removed, no need for a `+repage` equivalent since Pillow doesn't carry parent-page geometry.
- **Lesson:** Pillow is a viable image-manipulation alternative on this machine when ImageMagick is unavailable. The `+repage` concern doesn't apply to Pillow — its crop returns a clean new image with no parent metadata. For future image manipulation, default to Pillow first, then ImageMagick if Pillow is missing.

### Problem 3 — Estimated 16-minute bake came in at ~2 minutes

- **Symptom:** I told the user the 4 bakes would take ~16 min on A6000 (4 min each, based on the existing pine bake's documented timing). The actual run took ~2 min total.
- **Root cause:** The new woodgrain material is much simpler than the procedural pine bake. The pine bake has: anisotropic Voronoi (large-scale paint patches), TWO stretched noise textures (long brush streaks + fine wear), per-plank tint hash for colour variation (random pine warmth), a multi-stop ColorRamp threshold for paint coverage, plus seam + bump + roughness mixes. That's ~30 nodes of evaluation per sample at 256 samples per pixel across 2048x2048. The woodgrain bake reuses the seam logic but its colour comes from a single image-texture sample plus a tiny per-plank V hash — half the node count, faster per-sample evaluation, and likely better Optix cache behaviour because the image sampler is GPU-resident.
- **Fix:** None needed — the actual time is better. Just calibrating: future image-texture-based bakes can be quoted at ~30-40 seconds each, not 4 minutes. Procedural-material bakes (like the pine) remain in the 1-4 minute range.
- **Lesson:** Bake time is dominated by procedural-material complexity, not by output resolution. Image-textured materials bake fast because the colour evaluation is a single texture lookup. When deciding whether to bake-now or defer, image-texture materials are essentially free to bake.

## Learnings and discoveries

### Image-textured bake pattern (vs procedural-only)

The existing whitewashed_pine bake builds the entire material procedurally (Voronoi + noise + colour mixes). The new woodgrain bake uses an external image as the colour source plus procedural seams + per-plank hash for variation. Both patterns are valid; the image-textured approach is:

- **Faster to write** — the colour comes from the source asset, no Voronoi/noise tuning needed to mimic real wood
- **Faster to bake** — single image sampler vs multi-noise procedural at 256 samples/pixel
- **Easier to art-direct** — change the laminate sample image to swap the look entirely; recipe stays the same
- **More dependent on source quality** — labels, colour casts, JPEG compression artifacts will all tile into the bake (see Problem 1)

For ceiling laminate, mat painted board surfaces, fabric prints — anything where the visual reference is a single tile rather than a "type of material", the image-textured pattern wins.

### Pillow as ImageMagick alternative

This box has Python 3 + PIL but no ImageMagick. Pillow's `Image.crop((left, top, right, bottom))` is the equivalent of `magick -crop WxH+X+Y`. No `+repage` concern. JPEG output via `.save(path, quality=95)` matches ImageMagick's default behaviour for our purposes. For future image prep before bake (cropping watermarks, resizing references, recolouring), Pillow is the path of least resistance on this machine.

### Bake-script duplication via sed is robust enough

For 4 identical scripts that differ in a single constant (`ROOM_ID`) plus a few derived doc-strings, sed with two or three -e patterns is faster than parameterizing one script via environment variable. The downside (any future material change must be applied to all 4 scripts) is manageable because:

- The recipe is identical so any future update is also a 4-file edit (same sed/manual pattern)
- Each script is self-documenting under its own room's name when read by a future session looking at `ozu-test/bake/`
- It matches the "ozu-1 property and room-1 are two separate projects" memory rule semantically — each project owns its bake

### The 1 m x 1 m bake tile + RW/1.0 runtime repeat is the cleanest plank fit

The existing pine bake used a 1.35 m tile with 8 planks (-> 16.875 cm planks) and runtime repeat `RW/1.35`. The decimal in both the tile size and the repeat divisor is mentally noisy. Switching to 1.0 m tile with 5 planks (-> 20 cm planks) and runtime `RW/1.0` is significantly cleaner. 20 cm is also closer to typical real-world laminate plank widths (often 19-22 cm). When designing future ceiling/floor bakes, prefer integer-metre tiles + integer-cm planks unless there's a specific reason to deviate.

## Architecture and design notes

### Image-textured laminate bake pattern (BufferGeometry-style for materials)

For materials where a single reference image captures the look (laminate, tile, fabric prints, painted boards with a hero pattern), use this pattern instead of the fully-procedural Cycles approach:

```python
# Load + sample the reference image
img = bpy.data.images.load(IMG_PATH)
img.colorspace_settings.name = 'sRGB'

# Plank-grid logic (N planks per UV tile, plank axis along U):
plank_map = ShaderNodeMapping(scale=(N_PLANKS, 1.0, 1.0))
sep_uv = SeparateXYZ(plank_map)
fract_u = FRACT(sep_uv.X)           # 0..1 within current plank
plank_idx = FLOOR(sep_uv.X)         # which plank
plank_hash = WhiteNoise(1D, W=plank_idx)  # per-plank random

# Sample image with (fract_u, V + plank_hash) so each plank
# samples a different V band of the same image:
sample_uv = Combine(fract_u, sep_uv.Y + plank_hash.Value)
img_tex = ImageTexture(image=img, vector=sample_uv, extension=REPEAT)

# Plank seam: smoothstep on distance to plank boundary
seam_dist = MIN(fract_u, 1-fract_u) * 2.0
seam_mask = MapRange(SMOOTHSTEP, 0..0.020, value=seam_dist)

# Base color = image, with dark recess at seam
base_color = Mix(seam_mask, RGBA, A=(0.20, 0.18, 0.16), B=img_tex.Color)

# Roughness: laminate base + seam bump
rough = Mix(seam_mask, 0.50, 0.70)

# Bump: image luminance, recessed at seam
img_lum = RGBToBW(img_tex.Color)
bump_height = Mix(seam_mask, img_lum, 0.0)
normal = Bump(strength=0.15, height=bump_height)
```

This bakes ~5-10x faster than a fully-procedural recipe and is easier to art-direct (swap the reference image, recipe stays the same).

### Per-room project independence pattern

When a material is conceptually shared across multiple standalone room projects but each project is supposed to be independent:

1. Write N bake scripts, one per room, named `bake_room{N}_<material>.py`
2. Use a `ROOM_ID = N` constant; derive `ROOT_OUT` from it via f-string
3. Each script outputs to `ozu-test/room-{N}-textures/...` — its OWN project's folder
4. Each `registerScene('room-N')` block in `ozu-test.html` references its OWN folder
5. Recipe can stay identical across the N scripts; sed-replace ROOM_ID + a few doc-string mentions to generate sibling scripts

Trade-off: any future recipe change requires editing N scripts (mitigated by sed + grep verification). Benefit: matches `project_two_separate_projects` rule semantically; future divergence is local to one script.

### Watermark preflight as a hard rule

Before baking any image-textured material, scan the source image for:
- Sample labels / SKU codes (this session's "WD-061")
- Colour cards / swatches
- Logos / brand marks
- Border artifacts from improper crops

If found, crop them out FIRST. The bake will faithfully reproduce them and tile them across the result. Cost of preflight: one `Read` call on the source image. Cost of skipping: full rebake when caught downstream.

### Bake-time budgeting (calibration)

For A6000 + Cycles + OptiX + 2048x2048 + 256 samples + denoise:

- Image-textured material with simple seam + bump: **30-40 seconds per bake**
- Procedural material with 1-2 noise textures + simple mask: **1-2 minutes per bake**
- Procedural material with Voronoi + multi-noise + ColorRamp + per-plank hash (like the existing pine ceiling): **3-5 minutes per bake**

Four passes per object (albedo / normal / roughness / ao) so multiply by 4 if quoting total time. Sequential 4-room bakes overlap GPU warm-up across runs — total wall time is roughly sum-of-bakes minus a few seconds.

### Conventional plank dimensions for ceiling/floor bakes

- Tile size: 1.0 m x 1.0 m (or 1.0 m x 1.5 m for longer plank-direction visibility)
- Plank width: 20 cm (5 planks per metre tile) — typical real-world laminate
- Runtime repeat: `RW/1.0, RD/1.0` (integer divisor, no decimal noise)
- Seam width: 1.5-2% of plank width (smoothstep from 0 at boundary to 1 inside the plank, capped at 0.02 in normalized plank-fraction units)

The older 1.35 m / 8 planks / RW/1.35 pattern from the pine bake works but is harder to reason about; prefer the integer-metre pattern for new bakes unless the source asset specifically requires the 1.35 ratio.
