## Problems encountered and how they were solved

### Problem 1: `SMOOTH_STEP` enum not valid for Math node

- **Symptom:** First bake run aborted with `TypeError: bpy_struct: item.attr = val: enum "SMOOTH_STEP" not found`.
- **Root cause:** Blender 5.1.1's `ShaderNodeMath` doesn't have a SMOOTH_STEP operation. Has SMOOTH_MIN and SMOOTH_MAX, but not smoothstep. SMOOTH_STEP doesn't exist as a Math-node enum value.
- **Fix:** replaced `seam_mask = ShaderNodeMath; operation = 'SMOOTH_STEP'; ...inputs[1]=0, inputs[2]=0.03` with `seam_mask = ShaderNodeMapRange; interpolation_type = 'SMOOTHSTEP'; From Min=0, From Max=0.025; To Min=0, To Max=1`. MapRange with SMOOTHSTEP interpolation is the canonical way to do smooth step in Blender's shader graph.
- **Lesson:** For Blender shader graph smoothstep, always use MapRange node with `interpolation_type='SMOOTHSTEP'`, never `ShaderNodeMath` with non-existent SMOOTH_STEP operation.

### Problem 2: First ceiling bake was too uniform

- **Symptom:** Bake produced soft cream-tan pine planks with subtle horizontal grain. Lacked the bold contrast between paint-heavy and wood-showing areas seen in the photos.
- **Root cause:** Material design had too many overlapping signals (long_streak + voronoi + fine_noise all mixed at 25-35% factors) → averaged out to medium-tone tan with no strong distinction.
- **Fix:** Iterated three times. Final version: anisotropic voronoi (UV coords scaled non-uniformly so cells stretch along plank length) + dominant long-streak noise (0.7 weight) + tight paint_ramp threshold (0.35..0.62). Reduced per-plank tint variation from (0.85..1.10) to (0.92..1.00) so each plank reads similar.
- **Lesson:** When iterating procedural materials in Cycles, change one variable per bake. Resist the urge to tune 5 things at once — too easy to land in unexpected midpoint between two desired looks.

### Problem 3: Pendant linen had no visible weave

- **Symptom:** Linen albedo PNG from prior session was nearly flat cream. User pointed out the shade looked like smooth plastic, not woven fabric.
- **Root cause:** In `make_linen_material`, the `warp.outputs['Color'] * weft.outputs['Color']` combo was wired to the BUMP node only. The colour mix used only a separate fine-noise input. So the weave was visible in normal/bump but invisible in albedo.
- **Fix:** Compute `warp - weft` (SUBTRACT), MapRange to [0..1], use as Factor in a Mix RGBA node with warp_color and weft_color as A/B inputs. This makes pixels where warp is on top show the warp colour, pixels where weft is on top show the weft colour — visible cross-hatch in albedo.
- **Lesson:** Always verify the bake albedo previews before declaring success. If the weave/grain/pattern isn't visible in the albedo PNG, it won't be visible in the runtime render.

### Problem 4: Linen weave too dense at runtime

- **Symptom:** Initial bake at `mp.Scale = (18.0, 22.0)` combined with runtime `pendantMat('linen', 3, 1, ...)` produced ~54 thread cycles around the shade circumference. Visually reads as smooth fabric, not chunky burlap.
- **Root cause:** Calculation error. 18 cycles per tile × repU=3 = 54 visible bands around a ~50cm circumference = way too fine.
- **Fix:** Reduced bake to `mp.Scale = (8.0, 10.0)`, runtime to `pendantMat('linen', 1, 1)`. Now 8 thread cycles around the shade — chunky weave matches the burlap-style fabric in the photos.
- **Lesson:** For PBR baked materials wrapped around small geometry (cylinder shades, cushions), do the visible-cycles math before baking. Aim for 8-15 visible cycles across the typical viewing surface.

### Problem 5: Cap rotated wrong direction

- **Symptom:** Added a top cap to close the cylinder from above. From the user's view the cap appeared dark / didn't read as a closed top — they still saw "into" the cylinder.
- **Root cause:** CircleGeometry default normal is +Z (vertices in XY plane). I rotated `cap.rotation.x = Math.PI / 2`. Using right-hand rule, rotating +π/2 around X axis maps +Z → -Y. So cap normal is -Y (faces DOWN). From above, the camera sees the cap's back face. With DoubleSide, back face uses flipped normal for lighting — effective +Y. But the only light source in that direction is the ceiling (very close above), so the back face is in shadow.
- **Fix:** Changed to `cap.rotation.x = -Math.PI / 2`. Now +Z normal rotates to +Y, cap faces UP. From above the camera sees the lit front face.
- **Lesson:** When rotating a CircleGeometry to act as a cap on a cylinder, the sign of the rotation matters. For "cap facing UP" (visible from above), use `-π/2` (negative). For "cap facing DOWN", use `+π/2`. Memory rule worth adding: when adding caps to closed-bottom or closed-top shades, always set rotation so the cap's lit front face is on the camera side.

## Learnings and discoveries

### Blender 5.1.1 has no SMOOTH_STEP Math op

For smoothstep operations in shader graphs, use `ShaderNodeMapRange` with `interpolation_type = 'SMOOTHSTEP'`. This is the documented approach in modern Blender. Other ops in Math node include `SMOOTH_MIN` and `SMOOTH_MAX` but NOT `SMOOTH_STEP`.

### Procedural plank ceiling iteration: three-shot to converge

Each iteration cycle (write material → bake → preview PNG) took ~2 min on the A6000. To converge on the "long streaks + occasional brown patches" look I needed for the whitewashed pine ceiling, I went through three iterations:

1. **First bake (Phase 2):** mp.Scale = (40, 60), too uniform stripes only. Lots of fine grain but no large paint patches.
2. **Second bake (Phase 6):** voro.Scale = 6 + tight ramp, produced leopard spots (round patches).
3. **Third bake (Phase 7):** anisotropic voronoi (UV coords scaled 0.4×3.5 to stretch cells along plank), voronoi weight reduced to 0.3, streak weight 0.7. Final result has long horizontal sweeps with subtle voronoi-shaped boundaries → matches photo aesthetic.

**Useful pattern for procedural material iteration:** if cells from `ShaderNodeTexVoronoi` look too uniform/round, scale the UV input non-uniformly via a Mapping node BEFORE feeding to voronoi. This stretches the cells along whatever axis you scaled, producing organic anisotropic shapes.

### CircleGeometry rotation for caps

For a cap-on-cylinder fixture in three.js:
- CircleGeometry default: vertices in XY plane, normal +Z
- To make cap face UP (+Y), use `cap.rotation.x = -Math.PI / 2`
- To make cap face DOWN (-Y), use `cap.rotation.x = +Math.PI / 2`

I confused myself by getting the sign wrong. Worth memorising or writing into a helper function.

### Brass with metallic=1.0 in a confined space

A `MeshStandardMaterial` (or PBR brass) with `metalness: 1.0` and no environment to reflect renders as **pitch black**. This is correct PBR behaviour — pure metals have no diffuse component, only specular reflection of environment. If there's nothing for the metal to reflect (e.g. pendant tucked against the ceiling with no HDRI environment passing the ceiling), the metal looks black.

This bit me in Phase 12. The "black ring" I thought was the brass collar would have been correct, but the actual cause was different. Worth keeping in mind for any pendant/wall-mount/recessed fixture: a metal-1.0 material near a non-reflective surround will render dark. To brighten it: lower metalness, increase roughness, or ensure HDRI environment is visible to the surface.

### `pbrFromBase` helper is now in all 4 room sandboxes

Each room sandbox has a `pbrFromBase(base, repU, repV, extras = {})` declared right after `pbrMatR<N>` (jpg-based for external Poly Haven textures). For NEW Cycles-baked materials (4-PNG suffix: `_albedo.png`, `_normal.png`, `_roughness.png`, `_ao.png`), always use `pbrFromBase`.

Convention established this session and prior:
- 2 levels of nesting: `<object>/<material>/`
- Filename: `<material>_<kind>.png`
- Full base path passed to pbrFromBase including the filename prefix (e.g. `'ozu-test/room-1-textures/ceiling/whitewashed_pine/whitewashed_pine'`)

### Lights toggle has a `?? 0` fallback that lets per-room baseline emissive opt-in

The lights toggle code at lines 7919 and 7936 reads:

```js
S.lampMaterial.emissiveIntensity = on ? S.lampOnIntensity : (S.lampOffIntensity ?? 0);
```

If a room sandbox sets `S.lampOffIntensity`, the shade glows at that intensity when lights are off. If not set, defaults to 0 (full dark when off — current behaviour for rooms 2/3/4). This is opt-in per room, so future room work can choose whether to enable baseline glow.

### User views the ceiling fixtures from INSIDE the room

Important context I missed for ~2 fix iterations: in the room-1/2/3/4 sandboxes, the OrbitControls default camera is INSIDE the room. The user navigates by orbiting around the room interior. Top-down views of the pendant are looking UP from below the fixture, not down from above the ceiling. This affects geometry decisions (cap orientation, what to make visible/hide) and lighting decisions (where light needs to reach).

## Architecture and design notes

### Whitewashed pine ceiling material approach

Procedural Cycles graph that splits the surface into 50/50 wood-showing vs paint-covered via a strongly directional mask:

1. **Plank grid (UV-based)**: Mapping node scales V by 8 (N_PLANKS), then `fract(V) → within-plank coord`, `floor(V) → plank index`. Seam mask via MapRange-SMOOTHSTEP over distance-to-nearest-seam.
2. **Wood layer**:
   - Stretched noise (UV scaled 4×60) gives long horizontal grain
   - Pine colour mix between sienna (0.46, 0.30, 0.17) and dark walnut (0.26, 0.15, 0.07) by grain factor
   - Per-plank tint hash (white noise on plank index) multiplied in via Mix MULTIPLY (kept subtle, 0.92..1.00)
3. **Paint mask**:
   - Anisotropic voronoi (UV pre-scaled 0.4×3.5) gives cells stretched along plank
   - Long stretched noise (UV scaled 0.6×25) gives directional brush streaks
   - paint_mix = 30% voronoi + 70% streaks (streaks dominate)
   - ColorRamp threshold at 0.35..0.62 → ~50% paint coverage with soft fade
4. **Paint colour layer**:
   - Cream (0.95, 0.91, 0.83) mottled toward weathered grey-brown (0.75, 0.68, 0.58) via streak fac
5. **Final mix**:
   - wood_or_paint = mix(pine_per_plank, paint_color, paint_ramp_factor)
   - seam_color = mix(dark_seam (0.06, 0.04, 0.02), wood_or_paint, seam_mask)
6. **Roughness**: pine 0.78, paint 0.92, mixed by paint_ramp
7. **Bump**: grain_noise + fine_noise (50/50), seams recessed, strength 0.55

Same material is BAKED ONCE and reused across all 4 rooms via `pbrFromBase('ozu-test/room-1-textures/ceiling/whitewashed_pine/whitewashed_pine', RW/1.35, RD/1.35)`.

### Coarse linen weave material approach (lampshade)

Procedural Cycles graph producing visible cross-hatch in albedo (the big change from prior bake):

1. **Mapping**: UV scaled (8.0, 10.0, 1.0) for ~8 cycles around × ~10 cycles along (chunky burlap density)
2. **Two Wave nodes**:
   - warp = TexWave BANDS direction='X', scale=1.0, distortion=0.15, SIN profile
   - weft = TexWave BANDS direction='Y', scale=1.0, distortion=0.15, SIN profile
3. **For BUMP**: `combo = warp + weft` (ADD), strength 0.5
4. **For ALBEDO**: `diff = warp - weft` (SUBTRACT) → MapRange[-1..1 → 0..1] → factor for mix between weft_color (when diff<0) and warp_color (when diff>0)
5. **Colours**: warp bright cream (0.95, 0.88, 0.72), weft deep tan (0.62, 0.50, 0.34) — 30% darker for visible distinction
6. **Roughness**: flat 0.95

The trick that makes the weave visible in albedo is computing `warp - weft` (the difference, not the multiply), then remapping to [0..1] so pixels where warp > weft show the warp colour and vice versa. This produces a clean tartan/gingham pattern from two perpendicular SIN-profile bands.
