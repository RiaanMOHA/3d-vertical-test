## Architecture and design notes

### Room-1 dedicated scene — locked baseline as of this session

The `registerScene('room-1', …)` block in `ozu-test.html` should be treated as a **versioned reference**: it matches the April 22 / v4 layout exactly + has PBR textures restored. Future modifications to this block require explicit user approval. Mass edits / refactors / cleanups should treat it as off-limits unless the user includes it in scope.

### Two-flag QA cull pattern

The QA tool uses `_qaCulled` (view-mode) + `_qaIsolated` (zone-isolation) as orthogonal flags on each mesh. `_qaOrigVisible` is set on first cull and restored only when both flags are clear. This enables stacking isolate + top/iso angles without side-effects. Pattern can be extended to a third flag if needed (e.g., per-room highlight).

### Per-scene FOV via `S.fov`

`registerScene` configs now optionally include `fov: <number>`. `switchScene` applies it: `camera.fov = S.fov ?? 60; camera.updateProjectionMatrix();`. Only room-1 currently uses it (FOV 70 per v4). Other scenes default to 60.

### Texture URL resolution

The dev server serves the project root at `localhost:8080/`. The HTML is at `localhost:8080/ozu-test.html`. Relative texture URLs from the HTML resolve against `localhost:8080/`. The room-1 PBR loader uses `ozu-test/room-1-textures/<slug>/<slug>_<map>.jpg` which resolves to `localhost:8080/ozu-test/room-1-textures/...`. Files exist at `/Users/riaan/3d-vertical-test/ozu-test/room-1-textures/...`.

### Three.js r128 API (encoding vs colorSpace)

The project uses three.js r128 (from 2021). r128 uses `texture.encoding = THREE.sRGBEncoding` and `renderer.outputEncoding = THREE.sRGBEncoding`. The newer `colorSpace` / `SRGBColorSpace` API was added in r152+ and does NOT exist in r128. v4's source used `outputColorSpace = THREE.SRGBColorSpace` which would error in r128 — the migration adapted to r128's older API.

This session's three layout pivots (un-rotated → re-rotated → un-rotated) corroded trust badly. Future sessions: when the user gives an explicit anchor (a date, a commit, a file), use that AS-IS. Don't try to "interpret" or "improve". If something seems off, ASK before deviating.
