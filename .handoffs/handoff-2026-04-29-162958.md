### Problem 1: Initial misread of 1F stair shaft N-S length

- **Symptom.** Read blueprint chain segment "1,350" on the 1F left edge and assumed it was the stair shaft N-S length. Flagged as "1,350 not 1,600 per memory rule".
- **Root cause.** The chain segments correspond to grid-line positions, not necessarily room boundaries. The "1,350" segment is the height of the closet/storage zone above the stair, not the stair shaft itself.
- **Fix.** Re-checked the blueprint's labeled stair area: **1.42 ㎡**. With width 0.9 m, length = 1.58 m. Memory rule's 1.60 is approximately correct. Retracted the flag with strikethrough in global-coords.md and updated stairs 1F entry to use page-y=2700..4300, code-z=2900..4500.
- **Lesson.** Chain segments ≠ room dimensions. Always verify against the blueprint's labeled room AREA and divide by the known wall-to-wall dimension when computing the orthogonal length.

### Problem 2: 2F toilet placed wrong in global-coords.md

## Learnings and discoveries

### Stair shaft area label = 1.42 ㎡, length = 1.58 m

The blueprint labels the 1F stair shaft as **1.42 ㎡**. With the standard width 0.9 m, the N-S length = 1.42/0.9 = **1.58 m**. Memory rule's 1.60 is approximately correct (within rounding error).

### Building's north wall has a jog

The 1F building has a recessed entry at the genkan area. The porch is OUTSIDE the chain (north of page-y=0) on the west half, but on the east half (washroom/laundry) the chain starts directly at the building's north exterior wall. So:
- page-x=0..1800 (genkan column): porch at page-y<0, building interior at page-y=0..900 (1F genkan + wet rooms)
- page-x=4500..6300 (laundry column): no porch, building interior at page-y=0..2700 (2700-deep laundry)

### Central 900-mm column on 2F has stacked sub-zones

The middle column (page-x=2700..3600) on 2F has multiple zones stacked top-to-bottom:
- page-y=0..1350: 2F toilet (north wall exterior)
- page-y=1350..2700: closets (room-1 west closet + room-2 east closet, accessed from the bedrooms)
- page-y=2700..3600: corridor's main strip (zone A)
- page-y=3600..7200: closets between room-3 and room-4

### Corridor zone A has a complex shape (not a clean rectangle)

The 2F corridor's bounding box is page-x=0..6300, page-y=2700..3600 (full middle strip), but the actual occupied area (3.04 ㎡) is much smaller because of stair shaft (NW), closets, and toilet (which sticks up into the top row). The corridor has an "arm" extending NORTH from the main strip up to the toilet door at z=5850.

### Kitchen depth: 2,100 not 1,800

## Architecture and design notes

### Phase C global-coords.md format (established this session)

Each room entry has:
- Header line (room id, page label, area, dimensions)
- Overview text (any noteworthy features or warnings)
- Page footprint + code footprint (one line each)
- 4-row markdown table: `named wall | exterior/interior | page side | code coord | shares with`
- Shared-wall checks block (verify cross-room consistency)

Plus a global cross-validation table at the end (19 rows) and a flags-for-follow-up list with strikethrough for retracted flags.

### Two-tier chip pattern

Top row: parents (no `parent` field). Sub-row: children of currently-active parent. Logic:
1. Render parents in topRow.
2. When parent is clicked: if it has children, populate subRow + show; else hide subRow.
3. When child is clicked: just move camera, leave subRow visible.
4. CSS: `#view-chips { display: flex; flex-direction: column; align-items: center; gap: 6px }`; `.chip-row { display: flex; gap: 6px }`; `.view-chip { white-space: nowrap }` (uniform height).

This pattern would extend cleanly to a third tier if needed (e.g., room → corner cameras).

### Chip data model: parent/child relationship

```js
{ id: '1f', label: '1F', pos: [...], tgt: [...] }                    // parent
{ id: 'kitchen', label: 'kitchen', parent: '1f', pos: [...], tgt: [...] }  // child of 1F
```

The viewpoints array holds both flat. Render logic groups by `parent` field. Top-level chips have NO `parent` field. This is more flexible than nested arrays (a chip can change parent without restructuring the array).

### Bounding-box coordinates for non-rectangular zones

Three rooms use bounding-box wall conventions instead of literal geometry:
- corridor-1 (1F: L-shape combining genkan + corridor strip)
- corridor-2-toilet-2-f Zone A (2F: cross-shaped corridor with arms to all 4 bedrooms)
- stairs (1F + 2F: L-shape stair shaft, 90° bend at the winders)

For these, the named walls describe the box envelope, not literal continuous surfaces. The `shares with` column flags partial matches (e.g., a wall is exterior on part of its run and interior on another part).

### HTML rooms array supports multiple rows per folder

When a folder contains multiple physical zones (corridor-1 has genkan + corridor proper + storage; corridor-2-toilet-2-f has toilet + corridor), the `rooms` array can have multiple rows with the same `name` field. Walk-mode label simply shows the folder name regardless of which sub-zone the user is in. This avoids needing sub-zone names in the user-visible label while preserving distinct collision boxes for the build/render code.
