## Problems encountered and how they were solved

### Problem 1: Bedroom paint coverage gaps

**Symptom**: User said "ALL THE BEDROOMS room-1 room-2 room-3 room-4 MUST HAVE WALL COLOR = #afa299 / NO EXCUSES NO EXCEPTIONS" — meaning cream patches were still visible somewhere on bedroom walls.

**Root cause**: Two separate gap sources:
1. The original `addBedroomWallPaint` cut paint at the full wall height for any door or window x-range. So transom (above door, y>2.0), sill (below window, y<wY0), and lintel (above window, y>wY1) areas were unpainted even though the wall was solid there.
2. The `addRoomTrim` helper cut crown molding at door x-ranges, leaving a 5 cm cream strip at the top of each bedroom doorway between the painted transom area and the ceiling.

**Fix**: Two-part. (1) Refactored `addBedroomWallPaint` into `addWallPaint2F` + `addRoomPaint2F`, using Y-band logic so cuts apply only inside the Y range that intersects the opening. (2) Modified `addRoomTrim` to skip door cuts on the crown band only (keep them on baseboard).

**Lesson**: When the user says "all walls must be X colour", literally means EVERY pixel — not "most of the wall surface". Trim and paint helpers must be 2D-aware (x AND y) for the result to look complete.

### Problem 2: Bedroom paint colour test (#2596be → #afa299)

**Symptom**: User asked for `#2596be` (bright blue-teal), then "sorry the wall color is #afa299" (warm grey-taupe).

**Root cause**: The first colour was almost certainly a deliberate test by the user to verify the colour-change reached the right meshes. After confirming the change worked, they specified the actual target colour.

**Lesson**: When the user picks a clearly non-residential colour, treat it as a test, not a final spec. Make the change quickly so the user can verify visually, then expect a follow-up correction with the real value.

### Problem 3: F1_CEIL boundary trade-off

**Symptom**: Two competing fixes for the same boundary:
- Phase L: extending F1_CEIL #2's z1 from 3.60 to 3.65 fixed the room-4 door tan-strip leak.
- Phase O: had to revert because the upper-flight stair (at z=[3.60, 4.50]) needs that area to be a hole, not ceiling.

**Root cause**: The wall at z=3.60 has thickness 0.10 m, so its back face is at z=3.65. The 1F ceiling boundary at z=3.60 leaves a 5 cm strip uncovered for any wall structure that extends past z=3.60. But the upper flight stair occupies the same 5 cm strip (since UZ0=3.60 too).

**Resolution**: reverted F1_CEIL boundary to z=3.60. Tan-strip bug may return. User had previously said "we will ignore the fix" so this is acceptable.

**Lesson**: F1_CEIL boundaries and upper-flight z extents are coupled — changing one requires the other to match. The tan-strip bug at the room-4 door's underside cannot be fixed with F1_CEIL changes alone because the upper flight overlaps the same area; the proper fix would be to trim the door panel's z extent or move the door slightly south.

### Problem 4: Stair geometry conflict between blueprint annotation and photo

**Symptom**: Blueprint annotation says tread depth = 225 mm (踏面225), but the photo (stairs-17) shows winders that look like a square 0.90 × 0.90 at the corner — which would force lower-flight treads to 0.14 m (steep, contradicting the annotation).

**Root cause**: True ambiguity. Photo perspective makes winder size hard to measure. Blueprint annotation may be a regulatory minimum, not actual geometry. Or the 1F shaft is bigger than 1.60 m (the bottom step's nosing extends into the LDK).

**Resolution**: Committed to the blueprint-annotation interpretation: 5 × 0.225 m = 1.125 m lower flight, winder zone 0.475 m wide, NOT a square. User may push back if photo-square winders are what they wanted.

**Lesson**: When the user says "ask me if you dont understand", they may not actually be ready to engage with technical geometry questions. Try one plain-language attempt with simple choices (A vs B with one-line consequences each), then commit to one interpretation if they say "I dont understand" again.

### Problem 5: Multiple file-reload errors during edit

**Symptom**: Multiple `File has been modified since read` errors during Edit tool calls. Forced me to re-Read the file and retry the edit.

**Root cause**: Linter or external watcher modifying the file during my Edit calls. Common pattern: I made one edit, didn't re-read before the next, the file changed externally, next edit failed.

**Fix**: Re-Read the affected lines just before each Edit. No real loss but slowed the session down.

**Lesson**: After a long editing session, expect linter modifications to break the edit chain. Re-Read frequently, especially before edits that target shared structures (like the bedroom paint helper which was modified by both me and the linter).

## Learnings and discoveries

- **"I dont understand" = stop asking technical questions, just commit to one interpretation.** When the user gave this response to my 3-question check on stair geometry, the right move was to pick one and build it, not to keep asking.
- **Vivid test colours** (like `#2596be` for bedroom walls) are almost always a verification probe, not a final spec. Treat them as tests and expect a correction.
- **"Audit your codebase AGAIN"** in CAPS = the user has patiently waited for me to find ALL issues, not just the first one. Spawn a thorough mental audit (or actual audit agent). Don't ship after fixing only one of the visible problems.
- **Plain-language explanations of dev concepts**: I explained Gaussian Splat (capture real rooms with phone), WebGPU (newer browser engine, mostly invisible to user), and QA bug (tan strip showing where ceiling should be) in plain terms. ### Three.js / rendering facts

- **Per-mesh material clones are not necessary** for procedural canvas textures with global repeat. A single `creamSidingTex()` shared across all cream cladding meshes gives consistent course count if the wall heights are uniform (2.50 m per floor). Different segment widths only show different horizontal seam alignment, which is barely visible on a 60-course wall.
- **`tex.repeat` is per-material when material is shared.** To get per-mesh repeat scaling, the texture must be cloned and the clone's repeat set, with the clone owned by a per-mesh material instance. Done correctly in `pbrMat` (one set of texture clones per call).
- **Three.js r184 still has `THREE.SRGBColorSpace`** as the modern colour space constant. `tex.colorSpace = THREE.SRGBColorSpace` is required for diffuse textures to render at the correct gamma.

## Architecture and design notes

### Y-band wall-paint strategy (NEW this session, key for the bedroom-paint fix)

`addWallPaint2F` enumerates all unique Y boundaries from doors (y=[yFloor, yFloor+DH=2.0]) and windows (y=[yFloor+w.y0, yFloor+w.y1]), filters to the paint Y range [yFloor+0.07, yFloor+ceilH-0.05], sorts ascending, and creates one paint band per consecutive Y-pair. For each band, an x-cut applies only if the cut's y range intersects the band's y range. Result: paint covers transoms + sills + lintels (solid wall regions) without floating in door openings or window glass.

This pattern can also be used for the eventual fix to `addWallTrim` — currently it cuts both baseboard and crown identically, but should distinguish closed-door cuts (only baseboard cut) from archway cuts (both cut).

### PBR floor texture pipeline

`pbrMat(slug, repU, repV, extras)` returns a `MeshStandardMaterial` with `map` (sRGB) + `normalMap` + `roughnessMap` loaded from `ozu-test/room-1-textures/<slug>/<slug>_diff|_nor_gl|_rough.jpg`. Per call:
1. Three textures cloned (per-mesh repeat scaling).
2. `wrapS/wrapT = RepeatWrapping`.
3. `repeat.set(repU, repV)` — caller passes `dx * density` and `dz * density` from `makeFloor`.
4. `anisotropy = renderer.capabilities.getMaxAnisotropy()`.
5. Material constructor: `{ map, normalMap, roughnessMap, ...extras }`. The `color` field in extras tints the diffuse map (multiplicative).

To extend: download additional Poly Haven CC0 sets to `ozu-test/room-1-textures/<slug>/`, file naming `<slug>_diff.jpg`, `<slug>_nor_gl.jpg`, `<slug>_rough.jpg` (all required). Then any `pbrMat('<slug>', ...)` call works.

### Cream cladding texture (procedural)

`creamSidingTex()` returns a 64×256 px `THREE.CanvasTexture`:
- Cream `#e8e3d9` base.
- 1-pixel `rgba(0,0,0,0.10)` line every 32 px (8 lines per canvas).
- `wrapS/wrapT = RepeatWrapping`, `anisotropy = 8`, `colorSpace = SRGBColorSpace`.
- Default `repeat.set(9, 8)`.

Applied globally to `matUpper` (exterior) and `matUpperExt` (interior). Wall heights 2.50 m → ~62 horizontal courses per floor at 40 mm spacing.
