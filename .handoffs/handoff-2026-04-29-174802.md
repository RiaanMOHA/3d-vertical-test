## Problems encountered and how they were solved

### Problem 1: ozu-test.html too large for Read tool

- **Symptom.** `Read` on `ozu-test.html` returned `InputValidationError: File content (343917 tokens) exceeds maximum allowed tokens (25000)`. Even slicing with `offset=20, limit=60` failed (still too large because the file is dense with inline three.js + base64-ish data).
- **Root cause.** The HTML inlines all of three.js r128 plus all 3D geometry data → very large token count.
- **Fix.** Read targeted line-ranges via `awk 'NR>=A && NR<=B'` over Bash. That bypasses the Read tool's token limit since the slice is small.
- **Lesson.** When `Read` complains about size on `ozu-test.html`, jump straight to `awk` ranges. Don't keep retrying smaller `Read` slices — they all fail because the harness reads the whole file before slicing.

### Problem 2: Hidden pre-existing collision-box bugs surfaced by Phase C

- **Symptom.** Audit found washroom collision box was 0.60 m too tall, plus corridor-1 has uncovered strips and an out-of-bbox storage box.
- **Root cause.** The collision-box geometry predates the Phase C global-coords work. Prior session this week renamed boxes to match folder names but DID NOT update bounds. Phase C established the canonical room footprints, which now expose the geometric drift.
- **Fix.** Not applied (user invoked `/handoff` before responding to the offered fix). The one-line fix is `z1: 4.80` → `z1: 5.40` on `ozu-test.html:610`. The two minor issues (corridor gaps, 2F corridor bleed) need re-modeling with multiple boxes per zone.

## Architecture and design notes

### `ozu-test.html` Read-tool workaround

The HTML file is too large for the Read tool — even a small `offset/limit` slice fails because the harness loads the entire file before slicing. Use `awk 'NR>=A && NR<=B' ozu-test.html` (or `sed -n 'A,Bp'`) via Bash for any read of this file. Future sessions: jump straight to awk; don't waste retries on Read.

### Verification methodology for chip + collision-box audits

The pattern that worked this session:
1. Read all viewpoints from `ozu-test.html` viewpoints array
2. For each viewpoint, look up the corresponding room's "code footprint" line in `global-coords.md`
3. Compute the room center from the code footprint (mid-x, mid-z) and compare against the viewpoint's `tgt`
4. For collision boxes: compare each box's `x1/z1/x2/z2` against the room's code footprint — they should match (or be a known sub-zone of a multi-box folder like corridor-1)

This audit takes ~15 minutes for all 14 chips + ~15 collision boxes. Worth running again after any Phase D geometry changes.

### Phase D will likely re-trigger geometry audits

When Phase D rebuilds LDK + bedrooms with detailed geometry, the collision-box bounds may need to grow/shrink to match new walls. Plan to re-audit after each room's Phase D rebuild.
