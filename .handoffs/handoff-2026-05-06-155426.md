## Problems encountered and how they were solved

### 1. Stale line numbers in ozu-test.html citations (across all 6 narrative docs)

**Symptom:** Every numeric `ozu-test.html line N` citation pointed to wrong content.

**Root cause:** The file was edited (probably by the Phase 7.x detail passes adding ~25-30 lines of code) after my initial docs were written. Original citations were captured at one snapshot of the file, then the file moved on.

**Fix:** Replaced all numeric line citations with grep-friendly identifiers: `search ozu-test.html for "name: 'room-1'"` instead of `ozu-test.html line 889`. The grep target is the inline comment or string literal that's stable across refactors.

**Avoid in future:** Never cite ozu-test.html (or any actively edited file) by line number. Always cite by a grep-able pattern that won't drift.

### 2. addBedroomWallPaint vs addRoomPaint2F naming mismatch

**Symptom:** Master plan refers to a helper as `addBedroomWallPaint`. Actual code calls it `addRoomPaint2F`.

**Root cause:** Master plan was written from memory of intent, code was written/renamed during implementation, master plan never updated.

**Fix:** Documented the mismatch as a gap in `flow-ozu-1-rendering.md`. Always cite the code name, not the plan name, when the user will act on it.

**Avoid in future:** Source-of-truth hierarchy: code > plan when names disagree. Verify any helper name against `grep -n "function <name>" ozu-test.html` before citing.

### 3. /askme skill misfit for non-dev user with strong intent

**Symptom:** I asked clarifying questions; user got frustrated, said "explain what this is" then "NONONONONONON".

**Root cause:** The /askme skill instructs me to keep asking until requirements are fully clear. For this user, that loop is itself the friction. The user often has a clearer intent than my questions assume; they want me to commit and produce, not re-elicit.

**Fix:** Stopped asking after 2-3 attempts and committed to my best interpretation. User redirected once ("not just room-1, also Ozu-1") which was easy to fix.

**Avoid in future:** With this user, if my first question gets a non-answer, my second question is already too many. Commit to interpretation, state it briefly, produce, let them redirect via the diff.

### 4. Sequential file writes vs parallel writes

**Symptom:** I wrote `flow-room-1-full.md` first, user interrupted "and?" Wrote it again, same response. Frustrated user.

**Root cause:** When the user asks for N deliverables, they expect all N produced together, not sequentially with progress reports between.

**Fix:** All multi-file deliverables in this session went out as parallel tool calls in a single message after that.

**Avoid in future:** "I need 3 docs" means "send all 3 in one message", not "produce 1, ask if it's okay, produce 2, ..."

## Architecture and design notes

### Folder structure decision

Two folders at project root (`flow-room-1/` and `flow-ozu-1/`), parallel to existing folders like `ozu-test/` and `room-1-ONLY-v5-feasibility/`. Each is self-contained.

Alternative considered and rejected: a single `flows/` folder holding both sets. Rejected because the user explicitly framed them as two separate things ("room-1 is the separate project" + "the entire ozu-1 flow standardized") and the shared-glossary trick covers most of the duplication concern.

### Doc-set shape

Each folder has:
- 1 entry-point prompt (`claude-prompt.md`) — imperative, phase-by-phase, references the rest
- 1 full narrative + master recipe (`*-full.md`)
- 2 decoupled deep-dive narratives (`*-layout.md`, `*-rendering.md`)
- 1 glossary (`glossary.md`)
- 0-2 sub-procedures (only the Ozu-1 folder has `blueprint-reading.md` and `furniture-placement.md`; room-1 references them via `../flow-ozu-1/`)

The decoupling between layout and rendering was a hard requirement from the user. Each can be re-run independently if you want to redo just placement or just look.

### Citation strategy

Decided this session: cite ozu-test.html by grep-friendly identifier, never by line number. Examples:
- `search ozu-test.html for "name: 'room-1'"` instead of `ozu-test.html line 1003`
- `search ozu-test.html for the comment "room-1 引違 11909"` instead of a line number

This is robust against the file being edited because the inline comment or string literal stays put even when the file is reorganised.

### Standardisation strategy

Same skeleton in both folders so a reader who knows one folder can navigate the other instantly. The standardised playbook flow:

1. User drops new property assets in `<property>/blueprints/`, `<property>/interior-images/<room>/corner-<id>/`, `<property>/exterior-images/`.
2. User hands `flow-ozu-1/claude-prompt.md` (or `flow-room-1/claude-prompt.md` for sandbox work) to Claude.
3. Claude reads all 5 docs in the folder, scaffolds a new HTML file from `ozu-test.html`, runs phase 0 (scaffold) → phase 1 (docs) → phase 2 (layout) → phase 3 (rendering).
4. User reviews at every phase boundary.

The bottleneck for a true "drop in and run" experience that we have NOT addressed: the scaffold step still requires `ozu-test.html` as a template. A `template-skeleton.html` extracted from it would close that gap (listed in remaining work).

### Decoupled layout vs rendering

Layout doc covers: blueprint reading, room bounds, outer wall geometry, F1_WIN/F2_WIN arrays, wall cuts around windows, doors, floors, ceilings, stairs, furniture, trim, viewpoints. No materials, no lights.

Rendering doc covers: tone mapping, env maps, shadows, glass, materials, post-processing, PBR textures, per-room paint, fixtures' visual treatment. No geometry, no placement.
