## Learnings and discoveries

- **Inlining vendor code from three.js examples is fragile.** Many example files reference globals defined in other example files (`THREE.SMAAEdgesShader`, `THREE.RectAreaLightUniformsLib`, etc.). Inlining one without its dependencies causes a deferred crash that only fires when the dependent code path runs. Future approach: search the inlined file for `THREE.X` references, ensure each one is either in the bundle or inlined separately.
- **`renderer.capabilities.isWebGL2`** is more reliable than `instanceof WebGL2RenderingContext` for detecting WebGL2 (some browsers/contexts fail the instanceof check while still being WebGL2).
- **`WebGLMultisampleRenderTarget` in three.js r128** accepts samples via `.samples = N` after construction OR via `{samples: N}` options object. Both work. Pass it to `new EffectComposer(renderer, rt)` to get MSAA on the offscreen render target. Helpful when SMAA alone leaves visible aliasing.
- **`MeshPhysicalMaterial.transmission` does NOT blur scene geometry** in r128. Roughness only affects env-map refraction. To obscure a real plane behind the glass, use opacity-based translucency or a layered overlay technique. (Newer three.js versions improve this; r128 doesn't.)
- **`MeshBasicMaterial { toneMapped: false }`** keeps a texture at its native brightness regardless of `renderer.toneMapping`. Useful for backdrop planes that should look "outside the room" — they shouldn't be dimmed by the room's cinematic colour grading.
- **`#dock > button[hidden]` needs explicit `display: none`** because `#dock > button { display: inline-flex }` has higher specificity than the browser-default `[hidden]` rule.
- **User cadence rules (reinforced):**
  - One UI/visual change at a time. Never batch.
  - Screenshots are the fastest feedback loop; long text proposals get ignored.
  - "USE THE GPU" / "use the coordinates" likely means "use real-world data" but the user's own exterior photos are NOT a substitute for neighbour-view imagery. Don't auto-substitute.
  - "STICK TO THE PLAN" means continue without asking — but only after at least one user confirmation that the current direction is correct.
- **Inline `git -c user.name=... -c user.email=... commit`** is a clean way to commit on a fresh machine without modifying global git config. Respects the safety protocol.

## Architecture and design notes

**iOS-HIG dock control architecture (this session's enhancement).**
The dock at the bottom of the screen hosts ALL major UI controls. The original CSS named them by ID (`#views-btn`). Today's refactor uses **structural selectors**:
- `#dock > button { ... }` — applies to any button placed directly inside `#dock`.
- `#dock > button.active` — active state.
- `#dock > button[hidden] { display: none }` — honours JS `.hidden = true`.
- Same selectors used in mobile + tablet+ media queries.

**Hard rule (from this session's memory): UI styles must be generic, never name-scoped.** Never write `#views-btn, #lights-btn { ... }`. Add a class or a structural selector. New dock controls must inherit styling automatically — adding a `#new-btn` to a CSS list is the broken pattern.

**Vendor-code inlining checklist (lesson from this session).**
When inlining a three.js example file:
1. Search the file for `THREE.X.uniforms` / `THREE.X.something` references where `THREE.X` is NOT defined in the same file.
2. For every such `THREE.X`, locate the source file (usually a sibling like `XShader.js` or `XUniformsLib.js`) and inline that too.
3. Splice as a new `<script>` block AFTER the three.js main bundle but BEFORE the project script, so all `THREE.*` symbols are defined in time.
4. Verify with a hard refresh + an action that triggers the dependent code path. Don't trust "looks fine" without exercising.

**Wall-with-hole geometry pattern.**
For room-1's window-wall and ac-wall, the previous 4-segment `BoxGeometry` approach produced visible seams. New approach:
1. `THREE.Shape` with rectangular outer outline.
2. `THREE.Path` with rectangular hole, pushed to `shape.holes`.
3. `THREE.ShapeGeometry(shape)` produces a flat 2D mesh with the hole.
4. Position + rotate to face the room interior.
5. Material set to `THREE.DoubleSide` so the flat plane is visible from outside the room too (the orbit camera default is OUTSIDE the cube).

This eliminates segment seams entirely. Cost: walls have no thickness now (they're flat planes). Acceptable because (a) wA/wC are still BoxGeometry with thickness, (b) the wB/wD outer face was never visually meaningful anyway — it's covered by the backdrop planes from outside view.

**Frosted glass — opacity not transmission (in r128).**
Three.js r128's `MeshPhysicalMaterial.transmission` only blurs the environment map, not scene geometry. To obscure a backdrop plane behind a "frosted" pane, use plain `MeshStandardMaterial` with `transparent: true, opacity: 0.93`. The 7% see-through suggests the buildings as faint shapes; the 93% opacity reads as "frosted privacy glass". Don't try to push transmission roughness higher in this version of three.js.
