#### Bug — 1F overview blocked by ceiling

User reported: clicking the **1F** chip should give a top-down look-into-the-rooms view but the new 1F ceiling now blocked it. (Mac-path screenshot — couldn't access from Linux.)

Investigation: `applyQAView` with mode `'iso'` is what the floor-overview chips use. It calls:
- `isolateZone(S, room)` — hides anything whose center is outside the bbox + `UPPER_Y_PAD = -0.05` padding (so anything at `y > bbox.y2 - 0.05` is hidden).
- `cullAboveY(S, room.y2)` — hides anything with `bottomY >= cullY - 0.001`.

For 1F isolation: bbox y2=2.5, so isolateZone hides items whose center y > 2.45. My 1F ceiling at center y=2.43 (top=2.45, bottom=2.41) — is INSIDE the bbox, stays visible. cullAboveY(2.5) needs bottomY >= 2.499; my bottomY=2.41 isn't caught either.

For 2F isolation: bbox y2=5.0, so anything at center y > 4.95 hidden. My 2F ceiling center y=4.98 — already gets hidden by isolateZone. ✓ already correct.

Fix: tag-and-cull pattern. Two edits:

1. Modified `makeCeiling` to tag the mesh:
   ```js
   m.userData._isCeiling = true;
   m.userData._ceilingFloor = (yTop > F1H + 0.1) ? '2f' : '1f';
   ```
2. Modified the chip click handler (line ~5895) — after `isolateZone(S, room)` and the existing `applyQAView(S, room, 'iso')` call for `1f`/`2f`, added a traversal that hides the floor's own ceiling using the existing `_qaIsolated`/`_qaOrigVisible` flags (so `clearQACull` un-hides it correctly when the user picks a different view):
   ```js
   S.group.traverse(obj => {
     if (obj.isMesh && obj.userData._isCeiling && obj.userData._ceilingFloor === v.id) {
       if (obj.userData._qaOrigVisible === undefined) obj.userData._qaOrigVisible = obj.visible;

   });
   ```

- **Lesson:** The interior scene has TWO orthogonal cull systems running together for floor-overviews (`isolateZone` for spatial bbox, `cullAboveY` for top-down clipping). New objects need to participate in one of them to hide correctly during isolation.

## Learnings and discoveries

### Codebase patterns

- The interior scene's `build` function is built on a small set of helpers: `makeFloor`, `makeWall` (which auto-builds 2-layer cladding when `outerSign` and a non-`wallMat` material is passed), `wallX`/`wallZ` (which split a wall around gap arrays for windows/doors), `addWinFlex` (window with sill/lintel + glass), `addDoor` (panel + transom + handles/hinges), `furn` (a/b/c/d corner-style box helper). Adding new geometry fits cleanly into this idiom by either extending an existing helper or writing a sibling helper next to it.
- `F1_ROOMS`/`F2_ROOMS` (floor zones with material per room) are the canonical "rooms exist here" lists. `F1_WIN_*`/`F2_WIN_*` and `F1_DOORS`/`F2_DOORS` are the analogues for windows and doors. Adding a new architectural feature usually means extending one of these arrays.
- The 2F has a deliberate hole at `x=4.725..W, z=3.60..4.50` for the upper stair flight to rise through. Constants `SX0..SX1, SZ0..SZ1` hold this. New geometry covering full floor footprint must wrap around this hole or it will block the stairs.
- The QA view system uses two cull layers: `isolateZone(S, bbox)` for spatial isolation (hides anything outside the bbox + pads), `cullAboveY(S, cullY)` for top-down clipping. Both write to `userData._qaCulled`/`_qaIsolated`/`_qaOrigVisible` and are cleared by `clearQACull(S)` on view change. New geometry that should hide during certain views must participate in one of these.

### Geometry conventions

- `WT = 0.10` wall thickness. Walls are slabs centered on their nominal coordinate (so a wall at `x=2.70` actually occupies `x=2.65..2.75`). Anything mounted "on the wall" should be inset slightly from the slab face: e.g., for a feature on the toilet's east wall (code-x=2.70), the toilet-interior face is at `x=2.75`; mount the feature body at `x≈2.78` (3cm proud) so it's clearly visible without intersecting the wall slab.
- `FLOOR_T = 0.05` floor thickness. `makeFloor` positions the slab so its TOP is at the given `yBase`. Hence 2F floor (`yBase=F1H=2.5`) occupies `y=2.45..2.50`.
- For ceiling slabs, used `CEIL_T = 0.04` and a `yTop` parameter that defines the TOP of the slab (so the slab visually sits just under the structural floor/roof above).

### Real-world ↔ code coordinate convention

- Per `blueprints/global-coords.md`: page-LEFT (small page-x) → code-large-x (X is mirrored). Page-TOP (small page-y) → code-large-z. North = page-top of blueprint.
- So real-world WEST = code-large-x (e.g., x=6.30 = building's west exterior). Real-world EAST = code-small-x (x=0). Real-world NORTH = code-large-z (z=D=7.20). Real-world SOUTH = code-small-z (z=0).

## Architecture and design notes

### Plan-organization architecture (established this session)

Three-tier plan model:

1. **Project-scope plans** live in `ozu-test/` (close to source assets). The Ozu-1 master plan is the daily working document. It uses Phase numbers 1–8.
2. **Room-1 standalone sandbox plans** also live in `ozu-test/` but are scope-locked via `ROOM-1 ONLY—` filename prefix and explicit scope banner. They use Phase letters A–G to avoid collision with the master plan's numbers. Two plans currently: rendering plan (broad roadmap) + cutting-edge plan (focused quality pass = sub-plan of rendering).
3. **One-off research investigations** live at the project root in their own clearly-named folder (e.g. `room-1-ONLY-v5-feasibility/`). They have a README banner. They produce notes, not code. They explicitly do NOT modify any active plan or scene.

Superseded plans go to `ozu-test/archived/` with a SUPERSEDED banner inside. Use `git mv` so history is preserved.

### Ceiling cull-during-isolation pattern (established this session)

Pattern for new geometry that should hide during specific QA views:

1. Tag the mesh with descriptive `userData._...` fields when creating it.
2. In the chip click handler (line ~5895 area), after `isolateZone(S, room)` and `applyQAView(S, room, mode)`, add a targeted traversal that hides matching tagged objects using the existing `_qaIsolated`/`_qaOrigVisible` flags.
3. The existing `clearQACull(S)` already handles un-hiding on view change — no new clean-up code needed.

This is preferable to extending `isolateZone` itself (which has a one-size-fits-all bbox check) because different object classes (ceilings, glass, decoration) may need different cull behaviors per view mode.

### Door type rendering (established this session)

`addDoor(axis, axisCoord, a, b, yBase, ceilH, mat, type)` now branches on `type`:
- `'hinged'` (default): lever handles on both faces at 75% along width + 3 dark hinge cubes (5c5c5c, metalness 0.6) on the opposite (`a`-side) edge at 0.04 inset, vertically distributed at top/mid/bottom.
- `'bi-fold'`: vertical center seam (8a7a66 darker recessed strip, slightly proud of the panel face on both sides) + 2 thin vertical chrome finger-pulls per face, one each side of the seam at 18% offset, near top of door (DH * 0.85).

Closet bi-folds in F2_DOORS use `closetDoorMat` (white) + type 'bi-fold'. The new laundry-washroom door also uses these. All other doors stay on `doorMat` (wood-tone) + default hinged type.
