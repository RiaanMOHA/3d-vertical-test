## Learnings and discoveries

### The room-1 sandbox uses `pbrMatR1`, not the global `pbrMat`
There are TWO PBR helpers in `ozu-test.html`. The global `pbrMat()` (line 611-626) loads from `ozu-test/room-1-textures/<slug>/<slug>_{diff,nor_gl,rough}.jpg`. The room-1 scene uses `pbrMatR1` (a separate function inside `registerScene('room-1', ...)`). They share the same texture folder but have different internal logic. When wiring new maps in for room-1, edit `pbrMatR1`, not the global one.

### `RoundedBoxGeometry` UV mapping differs from `BoxGeometry`
The vendored `vendor/three/examples/jsm/geometries/RoundedBoxGeometry.js` has its own UV computation that handles the rounded arcs. Existing PBR materials with explicit `texture.repeat` set will tile differently on rounded boxes than on box geometries. So far this hasn't caused a visible issue because the rounding radius is small (5-25mm) and the wood texture is forgiving, but if we ever switch to a more sensitive texture (e.g. a precise tile pattern), expect to need per-mesh UV adjustments.

### Three.js minified bundle drops `UniformsLib`
The `three.module.min.js` bundle minifier strips internal symbols. Any addon that depends on `UniformsLib` (notably `RectAreaLightUniformsLib`) errors at import time. The full LTC re-enable requires either:
1. Vendoring an unminified WebGL build of three.js (`three.module.js`)
2. Switching to WebGPU + `RectAreaLightTexturesLib` + `RectAreaLightNode.setLTC()` (works but the renderer hangs on user's browser, see Problem 1)
3. Living without LTC and accepting the dimmer un-LUT'd RectAreaLight fallback

Currently option 3 is in effect (RectAreaLight LTC disabled).

### The Street View driveway photo as scene.background causes pixelation
`new THREE.TextureLoader().load('ozu-test/streetview/driveway-backdrop.jpg', ...)` followed by `scene.background = texture` stretches the photo to fill the screen at the photo's native resolution. On a high-DPI display the pixelation is visible. Fix would be either a higher-res source image OR proper texture filter settings (`minFilter = LinearMipmapLinearFilter`, `anisotropy = max`, `generateMipmaps = true` if power-of-2).

## Architecture and design notes

### The cutting-edge default applies to ALL future object work
This is now a hard rule (saved as `feedback_cutting_edge_and_a6000_for_every_object.md`). Every future object pass — chair, desk, shelf, kitchen, laundry, anything — requires:
1. A6000 Cycles bake (AO + lightmap + normal at minimum)
2. Photo-driven PBR (diff + normal + roughness sourced from actual room photos)
3. Postprocessing pipeline running (GTAO + SMAA + bloom)
4. HDRI IBL feeding the materials
5. Absolute-current 2026 rendering techniques where they fit

Runtime-only geometry tweaks (RoundedBoxGeometry, repositioning, per-mesh material tweaks) explicitly do NOT satisfy this rule on their own. They're a part of the work but never the whole.

### Plans for this user must be plain-language-first
Every plan, phase, deliverable, and update needs to lead with the visual / behavioural outcome in plain English. Technical name in parens only if it adds clarity (often it doesn't). Concrete example:

❌ Bad: "Phase 1 — wire up GTAO + SMAA + UnrealBloom in EffectComposer with PCSS shadows and HDRI IBL on all room-1 PBR materials."

✅ Good: "Phase 1 — turn on the extra rendering quality features that are downloaded but not running yet. Three things switch on: softer edges on furniture, gentle darkening in corners (under desks, where walls meet), and a warm glow around the pendant lights when they're on."

### Review checkpoints between phases are mandatory
Per `feedback_review_before_continuing.md`, no chained execution. Pattern:
- Phase X →
- I report what's done →
- "You'll see: [specific visual change]" →
- "Reload and tell me how it looks" →
- User reviews + approves →
- Phase X+1

This is explicit, not implicit. Phases that don't have a "you'll see" + "reload and tell me" exit are wrong.

### Fan out parallel agents for any work that's per-object or per-material
The 10 room-1 objects are independent for purposes of bake scripts and PBR map generation. One agent per object (or per ~2 objects) running in parallel is the right shape. Saving this also avoids the rule-11 violation ("no artificial constraints, full power always").

### `*-test` sandboxes (room-1, kitchen-test, laundry-test) are desktop-first
Per `feedback_max_desktop_quality_always.md`. Don't propose mobile-lite paths for these. The production parent app (gktk-prototype) will eventually need mobile coverage but the sandboxes themselves aren't where that work happens.

### registerScene('room-1', ...) is unlocked ONLY when user types "room-1"
Memory rule `project_room1_is_separate_project.md`. User typed it twice this session ("we work on room-1", and references like "room-1 box"). Stays unlocked for the rest of this session and any future session where the user types it again. In a NEW session, it locks again until the user types it.
