### Phase C-8 — Bug round 3: room-1 eye height "too high"; laundry & living-dining "still looking down"
User: "the eye-height is too high for room-1, revert that. the laundry-test and the living-dining room scenes STILL SHOW top down view" (`qa-32.png` living+dining, `qa-33.png` laundry — both showed mostly wood floor).

**Diagnosis (laundry / living-dining):** these files use a slightly different inline OrbitControls than kitchen. Read `laundry-test.html` lines 215–286. Found the `_update()` method:
```js
_update() {
  const offset = new THREE.Vector3().subVectors(this.cam.position, this.target);
  if (this.spherical.radius === 0) {
    this.spherical.setFromVector3(offset);
  } else {
    offset.setFromSpherical(this.spherical);   // ← uses CACHED spherical from constructor
  }
  this.cam.position.copy(this.target).add(offset);
  this.cam.lookAt(this.target);
}
```

The constructor calls `_update()` once with the original camera/target. That captures `this.spherical` with the original DOWNWARD-tilted polar angle. When my code later sets `target.y = camera.y`, the spherical is NOT recomputed. Any subsequent `_update()` call (or in living-dining the very first interaction) goes to the `else` branch and re-applies the cached downward tilt — camera shifts upward and re-tilts down to match the new target Y.

**Fix for laundry / living-dining:**
```js
controls.target.setY(camera.position.y);
controls.spherical.radius = 0;   // forces _update to recompute spherical from current offset
controls._update();
```

When `spherical.radius === 0`, the `_update` takes the if-branch which `setFromVector3(offset)` — recomputes spherical from the NEW (horizontal) offset. Then camera.position stays unchanged and lookAt(target) makes the camera look horizontally.

**Fix for kitchen:** kitchen has a slightly different OrbitControls — has `_updateSph()` helper. Used `orbit._updateSph()` to recompute, then existing `orbit.update()` applies cleanly.

**Fix for room-1:** reverted target Y from 1.60 back to 1.0 (so it looks slightly down at room centre — matches the view the user said was "OK" before the eye-height pass).

## Problems encountered and how they were solved

### Problem 1: Cross-frame CSS injection is unreliable (Phase C-5)
**Symptom:** Source files' own nav UI (`#dock`, `#back-link`, `#entry-hint`) was visible in the journey iframe even though the journey file tried to inject `<style>` blocks via `frame.contentDocument.head`.
**Root cause:** Timing. The iframe's `load` event fires before my listener can attach for the very first iframe (which already finished loading by the time the IIFE ran). Even with a fallback (`if (readyState === 'complete') injectHideCSS(frame)`), CSS specificity / order-of-application made the rules unreliable.
**Fix:** Source-file-driven detection instead of parent-driven injection. Each source file has an inline `<script>` at the top of `<head>` that reads `?journey=1` and sets `<html class="journey-mode">`. The source file's own `<style>` block has `.journey-mode <selectors> { display: none !important; }` rules. Now the rules are part of the source file's own stylesheet — applied synchronously and reliably with first paint.
**Lesson:** prefer pull-side (target file detects state) over push-side (parent injects styles) for iframe coordination.

### Problem 2: Camera at exterior orbit pos when entering room-1 step (Phase C-6)
**Symptom:** Step 2 (room-1 in ozu-test.html?scene=room-1) showed the room-1 box from OUTSIDE, floating over a street-view background.
**Root cause:** `switchScene('room-1')` calls `orbit.setFrom(S.orbitPos, S.orbitTarget)`. Room-1's `orbitPos` is `(6.5, 4.5, 6.5)` — deliberately exterior, because the standalone UX is "user is on exterior scene, clicks 'room 1' chip, camera flies INTO the room." For the journey, we want to start INSIDE.
**Fix:** added a journey-mode handler that runs AFTER switchScene to call `orbit.setFrom(...)` again with the inside-the-room position (fpStart + room centre target).
**Lesson:** when a scene was designed for one entry flow, document the camera trajectory; reusing the scene from a different entry context requires explicit re-positioning.

### Problem 3: OrbitControls cached spherical phi caused recurring downward tilt (Phase C-8 / C-9)
**Symptom:** After running `controls.target.setY(camera.position.y)` to level the gaze, the camera STILL looked down.
**Root cause:** the inline OrbitControls in laundry/living-dining caches `this.spherical` (radius + phi + theta) in the constructor based on the original camera/target offset. The cached phi reflects the original DOWNWARD tilt. On the next `_update()` call, the `else` branch uses `offset.setFromSpherical(this.spherical)` which re-applies the cached downward phi — camera moves up and re-tilts down to look at the (now higher) target.
**Fix:** set `controls.spherical.radius = 0` to flip `_update()` into the if-branch (`spherical.setFromVector3(offset)`) which recomputes spherical from the CURRENT (now horizontal) offset. Then `controls._update()`.

For kitchen (different OrbitControls class): call `orbit._updateSph()` which is its equivalent of the recompute helper.

**Lesson:** changing target/position on an OrbitControls AFTER construction without resetting the cached spherical is silently broken. Always reset the cache.

### Problem 4: Laundry OrbitControls constructor moves camera.position to (0.90, 1.85, 1.50) (Phase C-9)
**Symptom:** Even after fixing the spherical cache, laundry's view was wrong in a different way.
**Root cause:** The laundry OrbitControls constructor calls `this._update()` ONCE. At that point, `this.spherical = new THREE.Spherical()` has its defaults `(radius=1, phi=0, theta=0)`. The `_update` runs through the `else` branch (radius is 1, not 0), executing `offset.setFromSpherical(default)` → offset becomes `(0, 1, 0)` → camera.position = target + (0,1,0) = (0.90, 1.85, 1.50). The original camera.position.set(2.40, 1.55, 2.30) is OVERWRITTEN by the constructor.

So by the time my code runs (line 284, right after `const controls = ...`), `camera.position.y` is already 1.85, not 1.55. Calling `controls.target.setY(camera.position.y)` set target.y to 1.85. Then offset = camera - target = (0,0,0). Then spherical.setFromVector3((0,0,0)) → radius=0. Camera stays at (0.90, 1.85, 1.50). lookAt(0.90, 1.85, 1.50) = camera looking at itself = undefined view (we got floor view).

**Fix:** explicitly hardcode camera.position.set AND controls.target.set in journey-mode, so we don't rely on reading any post-constructor state.

**Lesson:** the laundry-test.html OrbitControls has a real bug — the constructor's `this._update()` should be a no-op or should detect-and-skip the move. For standalone laundry-test.html, the user happens not to notice because they immediately interact and the cached spherical gets overwritten on touch. For the journey, we land at the unfixed state.

This bug ALSO exists in living-dining-test.html (same OrbitControls pattern). It does NOT exist in kitchen-test.html (different OrbitControls class).

### Problem 5: Five-iframe architecture caused jaggy movement (Phase C-9)
**Symptom:** "moving around in these 3d environments, ESPECIALLY the laundry feels very jaggedy and unresponsive"
**Root cause:** All 5 iframes were preloaded at startup, all running their own three.js renderers (including post-processing chains: GTAO + bloom + SMAA in kitchen, bloom + output in laundry/living-dining). Browsers throttle hidden iframes but don't fully pause them. 5 active GPU pipelines competing.
**Fix:** refactor to single iframe with src swap on step change. Only one renderer at a time. Loading spinner during iframe load.
**Trade-off:** ~1–2 s load time per step transition. Browser caches HTML and HDRI assets, so re-visiting a step is faster.
**Lesson:** "preload everything for instant transitions" is the wrong default for heavy WebGL pages. The CPU/GPU cost of keeping idle three.js scenes alive far outweighs the load-time savings.

## Learnings and discoveries

### iPad HIG numbers that matter for full-screen step transitions
- Full-screen step transition duration: **400–600 ms**. On iPhone equivalent would be 300–400 ms — the iPad's larger canvas needs more time for the eye to follow the motion across the longer distance.
- **Asymmetry rule:** exits should be 10–20% faster than entrances. UIKit conventions reflect this — ease-in for dismissals, ease-out for presentations.
- Default ease curves:
  - Ease-out (presentations): `cubic-bezier(0.0, 0.0, 0.2, 1)`
  - Ease-in (dismissals): `cubic-bezier(0.4, 0, 1, 1)`
- Touch targets: 44×44 pt default minimum; for premium pitch UI use 60×60+.
- Type sizes for iPad viewing distance (~3 ft): body 19–22 pt, hero 64–96 pt, CTA 56 pt tall.
- Standalone Add-to-Home-Screen ONLY works in Safari on iPadOS. Chrome ignores `apple-mobile-web-app-capable` and keeps its toolbar.

### ozu-test.html has two completely different "viewpoint" systems

### URL-param coordination across same-origin iframes is the cleanest pattern
For the journey, each source file gets `?journey=1` (and ozu-test additionally gets `?scene=room-1` for step 2). Source files detect this in an inline `<script>` in `<head>` (synchronous, runs before any rendering) and apply the journey mode via a CSS class. This is far cleaner and more reliable than:
- postMessage from parent to iframe (timing issues, needs message listeners in source files)
- Cross-frame CSS/DOM injection (timing, specificity issues, race conditions)
- iframe attribute mods like `sandbox` (breaks WebGL)

### Three.js camera coordinate system on `lookAt`
When `camera.lookAt(target)` with default world up `(0,1,0)`, and camera looks in the world +Z direction (target has higher Z than camera):
- Camera's local +X axis = world **−X** (because `right = up × backward` where backward = camera-to-(-target))
- Therefore world +X appears on the **LEFT** of the screen
- World −X appears on the **RIGHT** of the screen

This is the opposite of what naive intuition suggests. When laying out scenes, if you want an "east wall on left" view, your camera must face +Z. Sanity-checked this against the laundry geometry to match `qa-34.png`.

## Architecture and design notes

### Journey-mode pattern: pull-side detection via URL param + CSS class
**Decision:** each source HTML file detects `?journey=1` itself via a synchronous `<script>` in `<head>`, applies `<html class="journey-mode">`, and references that class in its own `<style>`.

**Rejected alternatives:**
- **postMessage from parent to iframe:** requires message listeners in each source file. Timing issues (must wait for iframe to be ready). Pure JS — no benefit over the inline script approach.
- **Cross-frame CSS injection** (`frame.contentDocument.head.appendChild(style)`): race condition with iframe load events, CSS order-of-application issues, fragile across browser versions.
- **`?journey=1` only with a parent-injected stylesheet:** still needs parent to wait for load, still fragile.

The inline-script pattern is **synchronous**, **survives any load timing**, and is **trivially copyable** to other source files (just paste the line into `<head>`). It's the cleanest cross-iframe coordination primitive for static HTML.

### Single iframe over multi iframe
**Decision:** one `<iframe id="journey-frame">` whose `src` is swapped per step.

**Rejected alternative:** 5 iframes preloaded, show/hide. Initial intuition was "preloaded iframes give instant transitions"; reality is each iframe runs its three.js scene continuously (browser throttles but doesn't pause), so 5 iframes = 5 active renderers = GPU contention = jagged frame rate. User explicitly reported the jaggedness, refactor solved it.

**Trade-off accepted:** ~1–2 s load time per step transition. Mitigated by browser caching the HTML and HDRI assets after first load (subsequent visits to the same step are fast). Hidden behind the fade-to-black + loading spinner.

### Step navigation primitives
`goToStep(targetStep)` is the single source of truth for navigation. `advance()` and `goBack()` are thin wrappers that call `goToStep(currentStep ± 1)`. This makes it easy to add features like:
- Jump-to-step (clicking a dot)
- Restart-from-end-screen
- Direct deep-link to a step via URL hash (future enhancement)

### Camera-coordination pattern across source files
Each source file's journey-mode block follows this template:
```js
const controls = new OrbitControls(camera, renderer.domElement);
if (document.documentElement.classList.contains('journey-mode')) {
  // 1. Hardcode camera.position (do NOT rely on the original .set value being preserved)
  camera.position.set(X, Y, Z);
  // 2. Hardcode controls.target
  controls.target.set(X, Y, Z);
  // 3. Reset cached spherical
  controls.spherical.radius = 0;   // for laundry/living-dining
  // OR: orbit._updateSph();        // for kitchen
  // 4. Apply
  controls._update();   // for laundry/living-dining
  // OR: orbit.update();             // for kitchen
}
```

For `ozu-test.html` the equivalent is in the post-`switchScene` block:
```js
if (new URLSearchParams(location.search).has('journey')) {
  if (_urlScene === 'room-1') {
    orbit.setFrom(new THREE.Vector3(0.50, 1.60, 0.50), new THREE.Vector3(1.35, 1.0, 1.35));
  } else {
    orbit.setFrom(new THREE.Vector3(12, 1.60, 14), new THREE.Vector3(3.15, 1.60, 3.6));
  }
}
```

(ozu-test.html uses a different `OrbitControls` API with a `setFrom` helper that internally resets the spherical correctly — so no manual reset needed.)
