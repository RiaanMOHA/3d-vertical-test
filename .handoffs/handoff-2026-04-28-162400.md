### LDK has 6 cameras, not 4 — template extension needed

Room-1's template assumes 4 corner cameras. The LDK has 6: 3 in `living-dining/living/{a,b,c}/` and 3 in `living-dining/dining/{a,b,c}/`. 4 sit at the 4 corners of the LDK rectangle; the other 2 (`living/c` and `dining/c`) sit mid-way along the south garden-wall.

Proposed naming convention for non-corner positions: `<wall-name>-mid-<half>` (e.g., `garden-wall-mid-west`, `garden-wall-mid-east`). This extends the room-1 template without breaking the corner-naming rule for actual corners.

### LDK is one open room, photos split it into 2 folders

Architecturally the LDK is a single open space with no internal walls between living, dining, and kitchen zones — only a half-height kitchen counter (L=2,550 mm) divides the kitchen visually. The user's photo organisation splits this into TWO folders: `living-dining/` (covers the LDK's living + dining zones, 6 cameras) and `kitchen/` (covers the kitchen zone, 4 cameras).

So the LDK gets TWO map files, not one. Each describes the walls bounding *its* zone:
- `living-dining/room-map.md` walls: kitchen-wall (north, with the half-height counter pass-through), garden-wall (south), brick-wall (east), stairs-wall (west)
- `kitchen/room-map.md` walls: counter-wall (south, the same partition as living-dining's kitchen-wall but viewed from the kitchen side), fridge-wall (north), window-wall (east), entry-wall (west)

The same physical partition (LDK ↔ kitchen) is `kitchen-wall` from the LDK side and `counter-wall` from the kitchen side. Different finishes on the two faces (brick on LDK side, white tile on kitchen side). This is fine and even useful — but it means the global-coords reconciliation in Phase C must match these two walls to the same blueprint coordinate.

## Architecture and design notes

### The 7-phase plan structure

The plan was reorganised this session from 6 phases (F0–F5) to 7 phases (A–G). The key change: split "F0 — map authoring + photo rename" into two distinct phases (A — source-of-truth setup; B — author maps). Phase A produces the blueprint/identity oracle that Phase B then references room-by-room. Without Phase A, Phase B has no anchor for "which photo folder = which blueprint room", which is the question that took the prior session multiple turns to resolve.

Each phase has:
- explicit input
- explicit steps (numbered, action-shaped)
- a single artifact (file or scene state)
- an exit criterion (user verifies)
- a list of failure modes the phase guards against

This shape is meant to be self-binding: Claude cannot claim a phase done unless the artifact exists and the user has signed off. If a phase fails or stalls, the failure surfaces immediately rather than getting buried in "all phases done" optimism.

### The room-map.md template, slightly extended

Per-room map files follow the room-1 template in this order:
1. `## overview` — what the room is, its dimensions, materials
2. `## walls` — each wall with feature name, opposite declaration
3. `## adjacencies` — derivable from opposite pairs but listed for clarity
4. `## corners` — table of corner-WALL_A-WALL_B (alphabetical pair)
5. `## room layout (top-down)` — ASCII art schematic
6. `## furniture anchors` — corner-anchored, not coordinate-anchored
7. `## panorama sweep direction` — clockwise from above, sequence 01 starts
8. `## folder structure` — current state of photo folders
9. `## proposed rename` — bash script to rename letter-coded folders to corner-feature-feature
10. `## unverified items` — explicit list of assumptions
11. `## usage notes for claude code` — how to read and use the map

Living-dining adds a `## camera-position mapping` section between "corners" and "panorama sweep direction" because it has 6 cameras (4 corner + 2 mid-wall) that don't map 1:1 to corners. This section explains the colour↔folder relationship and the mid-wall convention for non-corner positions.

### `room-map-photos.md` companion file

Per the room-1 template, every map has a companion `room-map-photos.md` listing which panorama image numbers from which corner sweeps show each named wall. Used in Phase D for material sampling and verification. Format:

```
### <wall-name> (description of features)

| current path | image numbers | notes |
| ... |

best <feature> reference: <path>/<numbers>
```

Plus a `## what this confirms` section showing the photo evidence supports the adjacency model declared in `room-map.md`. This is the **photo-side verification** of the map's claims — if the photos contradict the map, one of them is wrong.
