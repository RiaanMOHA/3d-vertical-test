## Problems encountered and how they were solved

### Problem 1: `ozu-test.html` too large to read in one Read call

**Symptom.** Initial `Read` call on `ozu-test.html` failed with "File content (700.5KB) exceeds maximum allowed size (256KB)." Even with `offset=1, limit=200` it failed: "exceeds maximum allowed tokens (25000)" — for just 200 lines.

**Root cause.** Line 66 is one 603,352-character line containing the inlined three.js r128 library (~600 KB on a single line, no line breaks). Any read window that includes line 66 hits the token limit.

**Fix.** `awk 'length > 1000 {print "Line", NR, "length:", length}'` confirmed line 66 was the only super-long line. Read in 5 chunks bracketing line 66: 1-65, 67-600, 667-1166, 1167-1666, 1667-2185. Total ~2,184 readable lines outside the inlined library.

**Lesson.** For projects with inlined libraries, scan for super-long single lines first via `awk 'length > 1000'` before attempting full-file reads. The line-range chunking pattern works around the token limit cleanly.

### Problem 2: User correction mid-flight on test.html semantic

**Symptom.** Audit flagged `test.html` + `test/` as "abandoned" / "dead old prototype" based on git log showing they were untouched since the initial commit. User pushed back: "this project has a playground and playground/prototypes pages ON PURPOSE -> I dont want to touch them".

The user's mental model is "here's my main project, here's a place to experiment that I don't want to risk", not "here's old code I forgot to clean up".

**Fix.** Saved permanent memory rule `project_test_html_is_playground.md`. Updated `MEMORY.md`. Dropped item 1 from the plan. Owned the "dead old prototype" framing mistake without deflecting when user called it out.

**Lesson.** Git inactivity is a weak signal for "abandoned". Ask the user before flagging untouched files for removal, especially when the project has a clear "main" project alongside other artifacts. The cleanup audit should bias toward "ask before delete" for any file that's not literally an obvious stray temp/scratch file.

### Problem 3: `/cleanup` Phase 3 verification doesn't fit no-build projects

**Symptom.** The cleanup skill spec runs `npx tsc --noEmit`, `npx eslint .`, `npm run build`, `npm test -- --run` after each change and auto-reverts on first failure. None of these exist in this project (no tsc config, no eslint config, no build script, no test script).

**Root cause.** The skill assumes a project with at least one of these tools. This project intentionally has none — the runtime IS the HTML file, no build pipeline.

**Fix.** Substituted appropriate per-change sanity checks: `node -e "JSON.parse(...)"` for the JSON edit, no check needed for the markdown file. Skipped the literal verification commands and explained to user that they don't apply here.

**Lesson.** When applying generic skill specs to no-build projects, replace the framework-specific verification step with a relevant sanity check for the actual change. Don't skip verification entirely; just make it match the project's actual tooling (which here is "does the file still parse?").

## Learnings and discoveries

### Cleanup skill auto-stash is the biggest hidden-loss risk for non-developer users

The skill's Phase 0 auto-stash is well-intentioned (creates a clean starting point) but creates a classic non-developer trap: their work appears to vanish from the file tree until someone runs `git stash pop`. For a user with months of uncommitted work, this could feel catastrophic even though everything is recoverable.

**The mitigation:** commit before running /cleanup, so the stash step has nothing to stash. This is now my default approach for any user-with-uncommitted-work + cleanup combo.

### The cleanup skill's verification step doesn't fit no-build projects

The skill assumes tsc/eslint/build/test exist. For projects with none, the literal Phase 3 verification would auto-revert every change. I substituted JSON syntax checking and noted this as a Problem above.

### test.html and test/ are the project's playground (NEW PROJECT MEMORY)

Captured as a permanent memory rule. Untouched git history was a misread. Future cleanup audits must NOT flag these for removal.

### CLAUDE.md complements, doesn't replace, the per-project memory system

CLAUDE.md at the project root captures stack/structure/commands/off-limits — the WHAT of the project. The memory system at `~/.claude/projects/-Users-riaan-3d-vertical-test/memory/` captures user preferences, past corrections, project-specific quirks — the HOW the user collaborates and what they've taught me before. They sit at different layers and the new CLAUDE.md ends with a pointer to memory so any session reading CLAUDE.md knows where the rest of the context lives.

### git fast-forward merge from cleanup branch is a clean way to apply audited changes

When the cleanup branch is a linear descendant of main (which it always is, because we branched off main and never updated main), `git merge --ff-only` brings the cleanup commits onto main without creating a merge commit. The branch can then be deleted, leaving a clean linear history.

### Reading files in bracketed chunks works around the token limit for files with inlined libraries

For files with one super-long inlined library line (like three.js inlined into HTML), use `awk 'length > 1000'` to find the line first, then read in chunks bracketing it. 5 chunks of 500 lines each covers a 2,200-line file cleanly without hitting either the 256KB limit or the 25,000 token limit.
