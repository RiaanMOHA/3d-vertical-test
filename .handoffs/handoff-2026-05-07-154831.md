## Learnings and discoveries

### About the codebase

- **Walls were intentionally on `MeshBasicMaterial` to lock the colour to `#afa299`.** This was a prior decision, NOT a bug. Any "fix the wall lighting" suggestion that switches them back to a lit material would re-litigate that decision and likely be rejected.
- **`registerScene('room-1', ...)` reuses the existing `matWall_x0..matWall_zD` material instances per wall** — they're already 4 separate materials, so attaching per-wall textures is a one-line change per material, no refactor needed.
- **`wallShapeWithHole(...)` (lines 3296-3311) is a local helper inside the room-1 build function**, not exported. Both wB and wD use it; only the size + hole coords differ.
- **ShapeGeometry's default UVs use the shape's bounding box** (UV.x = (vert.x - bb.minX) / bb.sizeX, UV.y = (vert.y - bb.minY) / bb.sizeY). Verified mathematically — the bake's UVs match this for wB but not wD because of the rotation difference between the two walls.
- **`renderer.capabilities.getMaxAnisotropy()`** is in scope inside the `registerScene` build function — used by other room-1 textures (e.g. `ceilTexR1.anisotropy = ...` at line 3233).
- **Floor and ceiling use `MeshStandardMaterial` with PBR maps already** (`matFloorR1` for `wood_floor`, `matCeilR1` for the procedural plank texture). Adding AO on those needs `aoMap` + a second UV channel (`geometry.setAttribute('uv1', ...)` in r184). Different approach from the walls' `material.map = aoTex` multiply trick.
- **`ozu-test/room-1-textures/`** is the canonical location for room-1 textures (existing subfolders: `dark_wood/`, `wood_floor/`). Adding `wall_ao/` fits the convention.
- **The `vendor/three/examples/jsm/postprocessing/` directory is currently UNTRACKED in git** (per the session-start `git status`). It contains GTAOPass.js, EffectComposer.js, etc. So if a future session wants to use GTAO at runtime, the files are already on disk — no fresh download needed.

### About Blender 5.x + Cycles for AO baking

- **Blender 5.1.1 (2026-04-14) is the current stable** as of May 2026. Released about 3 weeks ago.
- **OptiX backend works on RTX A6000** without extra config beyond `prefs.compute_device_type = 'OPTIX'` and `prefs.refresh_devices()`.
- **`CUDA_VISIBLE_DEVICES=1` is honored by Blender** — it physically hides the other GPU from the OptiX/CUDA enumeration, so the bake cannot accidentally touch GPU 0 even if it tried.
- **Bake type `'AO'` does NOT need `use_ambient_occlusion = True`** in Blender 5.x. Just call `bpy.ops.object.bake(type='AO', use_clear=True, margin=8)`. The world's `light_settings.distance` controls AO falloff (currently 0.6 m for tight contact-darkening at corners).
- **`Material.use_nodes` triggers a deprecation warning** ("expected to be removed in Blender 6.0"). Still works fine in 5.1; will need updating later. Not blocking.
- **Bake outputs to the IMAGE TEXTURE NODE that is `selected = True` AND `nodes.active = node`** in the active object's material's node tree. Both flags must be set; selected alone isn't enough.
- **A 1024×1024 PNG bake at 256 samples on the A6000 takes ~3-5 seconds per surface** — total ~25 seconds for 6 surfaces.
- **PNG output via `image.filepath_raw + image.save()`** (as opposed to `image.save_render(...)`) is the simplest pattern and respects `colorspace_settings.name = 'Non-Color'` for AO data.

### About three.js r184 + AO

- **MeshBasicMaterial.map is multiplied by material.color per pixel** in the standard shader path. So `color = #afa299, map = grayscale_AO` gives `final_color = #afa299 × ao_factor` per pixel. Wall middles (AO ≈ 1.0) read as exactly the paint colour; corners (AO < 1.0) darken proportionally. This was the load-bearing trick for preserving the colour-lock.
- **Textures used as DATA (not colour images) need `colorSpace = THREE.NoColorSpace`** in r184. Linear data, no sRGB conversion. AO maps, normal maps, roughness maps, etc.
- **`geometry.setAttribute('uv', new THREE.BufferAttribute(uvs, 2))` overrides defaults entirely.** No need to delete the old uv attribute first.
- **For BoxGeometry, the same UV attribute applies to all 6 faces simultaneously** (because it's a single index buffer). For walls where only the inside face is visible, this is fine — the outside face shows whatever the formula evaluates to and isn't normally seen.
- **WebGPU + iOS coverage: NO migration path right now (May 2026).** Safari 26 / iOS 26 enabled WebGPU by default but iPhone SE 1/2 cannot upgrade to iOS 26 — the project's iOS coverage rule (`feedback_ios_all_breakpoints.md`) precludes it. Revisit in late 2027+.

## Architecture and design notes

### AO baking pipeline (new this session)

**Pattern: parametric-rebuild + path-trace + texture-multiply.**

The room-1 walls are a procedurally-built 3D scene with no source glTF or UV unwrap. To add AO, the standard glTF + Cycles bake pipeline doesn't apply directly. The approach taken is:

1. **In Blender (Python):** rebuild the same 6 surfaces parametrically using identical constants. Each surface is a flat plane (no thickness — Blender doesn't need it for AO purposes). Two have window holes. UVs are written explicitly as `(a/u_len, b/v_len)` per parametric position.
2. **Bake in Cycles with OptiX:** each surface in turn becomes the active mesh; the others remain in the scene as occluders. Cycles' AO bake type traces rays from each pixel of the active surface's UV-space → finds occlusions from the other 5 surfaces → writes the AO factor to the bake image.
3. **Save 6 grayscale PNGs to `ozu-test/room-1-textures/wall_ao/`.**
4. **In three.js:** load the 4 wall AOs with `colorSpace = NoColorSpace`. Attach as `material.map` on the existing `MeshBasicMaterial` instances. The shader multiplies `material.color × map` per pixel automatically. Wall middles (AO ≈ 1.0) get full paint colour; corners (AO < 1.0) darken.
5. **UV alignment:** custom UV overrides on the existing wall meshes via `setUVsByLocal(geometry, uvFn)`. Each formula maps the wall's local-space vertex position to the same parametric (a, b) coords used by the bake script. wA, wC, wD need overrides; wB's default ShapeGeometry UVs already match.

**Why this beats runtime AO (GTAOPass / SSAO):**
- Path-traced AO sees concave geometry that screen-space methods can't.
- Zero runtime cost — purely a texture sample.
- Preserves the wall colour-lock perfectly (multiply, not light-tint).
- Works identically on iPhone SE through iPad Pro.
- Engages the remote A6000, which the user explicitly demanded.

**Why this beats per-vertex / shader-formula AO:**
- Path-traced rays produce TRUE corner darkening that captures the actual occlusion geometry.
- Future-proof for adding furniture as occluders (phase 2).
- Quality is gated by sample count + ray distance, both knobs in the bake script.

**Trade-off accepted:**
- One-time bake step required when room geometry changes.
- Walls now have GPU memory cost: 4 × 1024×1024×1 byte = ~4 MB GPU memory. Negligible.
- Walls' outside faces show a mirrored AO pattern (the BoxGeometry shares one UV attribute across all 6 faces). Outside view of the standalone room-1 was already cosmetic; not a regression in practice.

### Why thin parametric surfaces in Blender, not the actual ozu-test.html geometry

The ozu-test.html walls have 0.02 m thickness (`WT_R = 0.02`). For AO of the inside-room view, that thickness is irrelevant — only the room-facing face matters. Building the bake's reference room as flat planes avoids the complication of which face of a thick box to bake from, and produces UVs that align directly with the bake's parametric layout.

### Why a dedicated `wall_ao/` subfolder vs. mixed into `room-1-textures/`

Per existing project convention, `room-1-textures/` already has subfolders per material set: `wood_floor/`, `dark_wood/`. Adding `wall_ao/` as a sibling subfolder slots cleanly into that pattern without polluting the top-level dir.

### Why script lives at `ozu-test/bake/bake_room1_ao.py`

`ozu-test/` is the canonical assets dir for the Ozu-1 + room-1 projects. `bake/` is a NEW subdirectory for build/bake scripts. If future bakes are added (e.g. lightmap, normal map, furniture bakes), they all live under `bake/`. Output destinations for those would be similarly under `room-1-textures/` or wherever each asset belongs. Bake scripts are tooling, not runtime — kept separate from the served HTML/JS.

### Why the user-facing CSS / HTML wasn't touched

The fix is invisible to the user except in the rendered 3D scene. No new dock buttons, no new chips, no viewport changes. Pure quality improvement.
