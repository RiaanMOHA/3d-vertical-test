## Learnings and discoveries

- **`MeshBasicMaterial` with `toneMapped: false` is the only way to lock a surface to a literal hex value in three.js.** Any PBR material is *required* by the shading model to be tinted by the lights striking it. The user wanting "this wall must be exactly #afa299 regardless of lighting" can't be satisfied any other way without making all lights perfectly neutral white at perfectly balanced intensities (which destroys the cinematic feel).
- **Three.js r184 RectAreaLight needs the LTC textures library**, which is a separate file (`RectAreaLightTexturesLib.js`) imported by `RectAreaLightUniformsLib.js`. Both must be vendored. The r128-era inline-the-source approach doesn't apply.
- **`scene.background = HDRITexture` + opaque room walls = "real outside view through windows" for free.** No need for backdrop planes. The walls themselves opaquely occlude the background everywhere except at the window openings, so the camera sees the HDRI through the windows naturally. As the camera orbits, the visible HDRI portion shifts naturally because the background lives at infinity.
- **Polyhaven only has 4 Japan-tagged HDRIs** (3 gardens + Nagoya wall path). For property-specific real-location panoramic data, free options are limited; you need either a paid Google Maps Street View API key, a Mapillary account, or your own captured imagery.
- **The user reads visual variation as "different colours" even when the paint hex is shared.** Cinematic asymmetric lighting (sun on one wall, cool fill on the perpendicular one) tints walls differently. The user's mental model is "paint colour" not "physically rendered colour" — they want the wall pixels to match the chosen hex value literally.
- **Lights ON / OFF as a diagnostic.** When the 4 PointLights at intensity 4.0 each are on, they wash out asymmetric lighting; when off, the directional + env map asymmetries become visible. The user noticing "colors all match only when I turn on the lights" was the key clue that pointed me at the asymmetric directional sun and the sky HDRI as tinting sources.
- **The procedural plaster + warm-taupe wall texture I built was rejected.** User said "no revert that / continue." Don't try this approach again unless they ask — they want flat colour locked, not procedural texture.
- **Property location is Ōzu, Kumamoto, Japan** (32.91°N, 130.85°E). The project name `ozu-test` finally has a documented coordinate.
- **Polyhaven JSON API at `https://api.polyhaven.com/assets?type=hdris` is enumerable from the command line** — useful for searching the entire HDRI catalog by tags/name. About 700 HDRIs total.
- **The user invokes `/handoff` mid-task as a checkpoint, not just end-of-session.** Same pattern as previous handoffs.

## Architecture and design notes

- **Walls are now flat-coloured (`MeshBasicMaterial`), not PBR.** This is a deliberate departure from the rest of the room (floor, ceiling, furniture, glass, AC, closet, door, etc. are all `MeshStandardMaterial` or `MeshPhysicalMaterial`). The reason is captured in code comments at the wall construct: user requirement that all four walls render at exactly `#afa299` regardless of light tinting. Any future change that adds a `map` or wants per-orientation shading on walls breaks this lock.
- **`scene.background` carries the through-window view in room-1.** This is a clean architectural pattern: the room walls themselves opaquely occlude the background everywhere, except at the geometric window openings where the camera ray exits the room and hits the background "at infinity." No backdrop planes needed. As the camera orbits, the visible portion of the HDRI shifts naturally with the view direction.
- **Two separate HDRIs** for environment vs background: the **puresky** version (`scene.environment`) gives a clean blue-sky lighting calibration that matches the room's tone-mapping setup; the **full** version (`scene.background`) has ground/buildings/trees so the through-window view looks like an actual outdoor scene. The two are decoupled — swapping one doesn't affect the other.
- **RectAreaLight does NOT cast shadows in three.js.** The directional sun is what casts the floor shadow, the rect light is the area-of-emission contribution. This is by design per the cutting-edge plan; don't try to enable `castShadow` on the RectAreaLight (won't work).
- **Per-scene `scene.background` switch.** `switchScene` chooses background based on `id`: room-1 gets the HDRI texture, every other scene gets a flat `THREE.Color(S.bg)`. Clean separation; future scenes can opt into HDRI backgrounds by adding their own conditional.
- **CSS vignette is independent of the WebGL pipeline.** It's a `::after` pseudo-element on the `#app` container with a radial-gradient background, toggled via a `vignette` class. No EffectComposer, no shader pass, no render-target costs, zero risk to anti-aliasing. If we ever do introduce DoF later, the CSS vignette stays out of the way.
