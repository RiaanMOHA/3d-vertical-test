## Learnings and discoveries

- **Audit methodology that worked.** For each piece of furniture: (1) read the room-map.md corner table to find which corners show that item; (2) read the frame-01 photo of each corner that mentions the item; (3) read 1–2 mid-sweep frames if the frame-01 view is ambiguous; (4) read the matching code block; (5) anchor unknown positions to visually identifiable features whose code coords are known (window-wall curtain at x=RW, etc.). This is the workflow for room-3 and room-4 next session.
- **`corner-ac-window/05.webp` is the key frame for the ac-wall x-position question.** It's a mid-sweep frame from the window-wall corner of the ac-wall, looking back across the room toward the closet-wall end. In this frame both the AC and the frosted window are visible on the ac-wall at different x positions, which lets you read their relative order on the wall. Use this kind of frame for room-3 and room-4 ac-wall verification too.
- **Code comments at `ozu-test.html:2409` are a forensic record of past QA passes.** Future sessions can grep for `qa-` in code comments to find which screenshots motivated which fixes. Useful when triaging "is this issue still current?".
- **The `box()` and `feat()` helper gotcha is in CLAUDE.md but worth re-emphasising.** `feat()` takes either a Material instance or a color. When converting flat-color features to PBR-textured features, you have to pass a Material instance, not a color — otherwise it builds a fresh `MeshStandardMaterial` per call from the color. The AC body in room-2 already uses `feat('z', RD, -1, {...}, matAC)` correctly (passing the material). When fixing the AC x-position, don't accidentally swap `matAC` for a color.
- **room-2's "hutch" is the "tall freestanding piece" in room-map.md.** The room-map flags this as "wardrobe / shelving / bulkhead? phase D to identify". The code commits to "grey-blue painted hutch with cabinet base + open shelves + arched top" — this is a decision that has been made. Do not re-open it.

## Architecture and design notes

**No architectural changes this session.** The audit methodology is the only new pattern:

**Furniture-placement audit methodology (room-2, repeatable for room-3 + room-4):**

1. Read `interior-images/{room}/room-map.md` — gives you wall name → wall feature mapping + corner table + furniture-anchor narrative. The narrative usually pins each item to a corner ("AC near corner-ac-closet"), which is the spec.
2. Read `interior-images/{room}/room-map-photos.md` — gives you the photo → feature index, telling you which photo to read for each item.
3. Read the 4 frame-01 photos (one per corner) and 1–2 mid-sweep frames if the frame-01 angle is ambiguous for the item you care about. The mid-sweep frames are critical for resolving x-vs-z position questions on the same wall (e.g. "is the AC on the closet-wall end or the window-wall end of the ac-wall?").
4. Read the `registerScene('{room}', ...)` block in `ozu-test.html`.
5. Build a code-vs-photo comparison table. For each item: (item, code x-range, code z-range, code y-range, photo support, verdict).
6. For each "wrong" verdict, identify the proposed new coords and the photo evidence.
7. Report to the user. Do not fix until the user authorises.

**Key constraint on the audit:** the room-2 `room-map.md` and `global-coords.md` disagree on compass orientation. **Follow the code convention** (window↔closet opposite on x-axis, ac↔entrance opposite on z-axis). Do not reorganise the room based on compass.

**Key constraint on PBR-textured features:** when fixing positions, do not break the `feat('z', RD, -1, {...}, matAC)` pattern where `matAC` is a shared PBR material. The `feat()` helper accepts either a Material instance or a color; if you accidentally pass a color (e.g. `0xffffff`), it will construct a fresh flat-color material per call and the PBR textures will silently disappear. See `CLAUDE.md` section "`box()` helper gotcha".
