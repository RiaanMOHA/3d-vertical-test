## Problems encountered and how they were solved

### Problem 1: `toilet-1-f/a/` folder content didn't match the room

- **Symptom.** Read `toilet-1-f/a/toilet-1-f-a-1.webp` and saw dark grey-brick wallpaper on the left + 4-panel flat closet doors with chrome handles on the right + a hardwood floor and a textured ceiling. The wall-to-wall distance was clearly larger than the 0.9 m × 1.8 m toilet footprint. This contradicted the prior session's tentative interpretation that `a/` was "the larger sweep capturing both the corridor approach AND the inside of the toilet."
- **Root cause.** The photographer / user filed corridor-1 photos under `toilet-1-f/a/`, possibly because the photos were taken during a single walk-through that captured both the corridor approach to the toilet door AND the inside of the toilet. Or the `a/` folder is purely corridor content that happened to be mistaken for "toilet approach" by the prior session. Either way, the content is corridor-1 (brick on east + closet panels on west + taupe column/jamb), not toilet interior.
- **Fix.** Verified by reading `a-10` (also corridor content) + cross-checking against `b-1`, `b-5`, `b-13` (which DO show toilet interior — interior brick wall, toilet bowl + lid, white doorframe with corridor brick visible through the open door). Updated `toilet-1-f/room-map.md` and `room-map-photos.md` to flag `a/` as corridor content. Did NOT move/rename the folder — that's destructive; just documented the finding so future sessions know.
- **Lesson.** When a photo's content doesn't match the expected room, READ MORE FRAMES from that folder before assuming. Wall-to-wall distance is a quick sanity check for small rooms (toilet 0.9 m, washroom 1.8 m). If the visible distance exceeds the room's footprint, the photo is from outside or in a different room.

### Problem 2: Toilet door type was wrong (folding vs hinged)

- **Symptom.** The toilet-1-f map's door-wall description said "2-panel folding door 折戸" based on `toilet-1-f/a/01`. But `a/01` is corridor content (closet panels + corridor wall), so the inference was based on the wrong photo entirely. The actual toilet door visible in `b/01` is a single white panel with chrome hinges visible on the right side of the frame — a HINGED door (開き).
- **Root cause.** Inference chained off the wrong photo. The "4 flat panels with chrome handles" visible in `a/01` are corridor closet doors (sliding/bypass), not the toilet entrance door. The toilet's actual door is shown in `b/01` (closed, with chrome hinges) and `b/05` + `b/13` (swung open, with corridor brick visible through).
- **Fix.** Updated `door-wall` description in `toilet-1-f/room-map.md` to "single hinged door 開き" with photo evidence cited (`b/01`, `b/05`, `b/13`). Phase E will re-confirm via blueprint arc.
- **Lesson.** Per the door-arc convention: smooth single curve = hinged 開き, zigzag = folding 折戸, two parallel offset lines = sliding 引違. When inferring door type from a photo, verify the photo is actually showing the door in question. Cross-check with multiple frames if the room has a single door.

### Problem 3: First blueprint crop for stair area was too far south

- **Symptom.** Cropped `1f-real.png -crop 800x900+700+1500` and got the LDK area (kitchen counter L=2550, sofa, dining furniture) instead of the stair shaft. Wasted one crop attempt.
- **Root cause.** Eyeballed the y-offset. The 1F stair shaft is in the middle (between corridor north and LDK south), not at the bottom. Y=1500 was past the stair shaft and into the LDK.
- **Fix.** Generated a half-size overview (`1f-half.png` at 1000×1550) for orientation, identified the stair shaft mid-panel area, then re-cropped at `+300+700` with 1100×1200 dimensions. Result was correct.
- **Lesson.** Per memory rule `feedback_no_excuses_blueprint.md`: render at 400 DPI for measurements, never eyeball. When a crop misses, generate a low-res overview first to find the correct area, THEN do the full-resolution crop. Saves wasted crop iterations.

### Problem 4: Stair photo capture format is unique (flat list, no sub-folders)

- **Symptom.** Listed `interior-images/stairs/` and saw 27 flat webp files, no a/b/c/d sub-folders. This is the only room with this format.
- **Root cause.** The stair is a sequential walking sequence — you walk from 1F bottom to 2F top (or descent), taking photos as you go. There's no natural "4-corner" framing; the 4-corner template doesn't apply.
- **Fix.** Wrote the map with a feature-based index instead of a corner-based one. Used bounding-box wall names (west / east / north / south) for the 3D envelope, with an explicit note that they're template names not panorama positions.
- **Lesson.** Stair shafts and other 3D structures (mezzanines, lofts, multi-floor voids) need a different mapping convention from rectangular rooms. The 4-corner template is a heuristic for 4-cornered rooms; non-rectangular and 3D-structural rooms need bespoke treatment. Pattern-document this for future projects with similar geometry.

## Architecture and design notes

### Bounding-box wall convention for non-rectangular rooms

Pattern established this session: rooms that aren't 4-cornered rectangles use the 4-walls + 4-corners template, but with explicit notes that the walls and corners are template names representing the bounding-box envelope, NOT the actual room geometry. This applies to:
- `corridor-1` (L-shape transit space — first non-rectangular room)
- `stairs` (3D L-shape stair shaft spanning 2 floors — second non-rectangular room)
- Future rooms that may need similar treatment (e.g., if any 2F bedroom has a closet alcove that breaks the rectangle)

The convention's purpose: keep downstream consistency in the 3D code (every room has 4 walls + 4 corners) while honestly documenting the geometric reality. Phase D rebuild can then map the bounding-box walls onto the actual L-shape or 3D structure with custom geometry.

### The QA-as-I-go workflow (carried over from prior session)

Per user direction (prior session):
1. **Author** the `room-map.md` + `room-map-photos.md` from blueprint + photos + annotated jpeg.
2. **QA against blueprint first**: re-render at 400 DPI; check walls / doors / windows / dimensions / letter positions.
3. **THEN QA against photos**: open at least one photo per corner / feature; verify each wall feature in the map appears in the relevant photos.
4. **Fix anything QA caught** (in-place edits).
5. **Sign off** → list files touched, STOP per "always review firsts" rule, wait for user.

This session's QA pass on the stairs map caught: the stair entry from LDK is OPEN (no door — confirmed via stairs-21, stairs-27); the handrail bends with chrome elbow (confirmed via stairs-7); the 13-riser count (5+2 winders+6) matches the blueprint step numbering; the materials match the house palette.

### Photo-content reasoning when annotations are ambiguous

When the annotated blueprint can't unambiguously assign each photo folder to a corner (because the annotation marks don't form a clean 4-corner pattern, e.g., corridor-1's pink A/A2/B/C), fall back to photo-content reasoning:
- What walls are visible in each frame?
- What features (brick, panels, door) define each wall?
- What direction is the camera facing based on the visible walls?
- Cross-check by reading at least 2 frames per corner (start + end where possible).

Mark the result as TENTATIVE with explicit confidence indicators (TENTATIVE / locked / TBD) so phase D knows what to re-verify.

`toilet-1-f/a/` = corridor content despite the folder name.
