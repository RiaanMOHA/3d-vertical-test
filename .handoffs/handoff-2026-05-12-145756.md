### Phase 4 — Fix the winder geometry

Rewrote `makeWinder()` in [stairs-test.html](stairs-test.html) using explicit `BufferGeometry`:

```js
function makeWinder(verts2D, yTop, mat) {
  const yBot = yTop - TREAD_T;
  const positions = new Float32Array([
    verts2D[0][0], yTop, verts2D[0][1],   /* 0 — top a */
    verts2D[1][0], yTop, verts2D[1][1],   /* 1 — top b */
    verts2D[2][0], yTop, verts2D[2][1],   /* 2 — top c */
    verts2D[0][0], yBot, verts2D[0][1],   /* 3 — bot a */
    verts2D[1][0], yBot, verts2D[1][1],   /* 4 — bot b */
    verts2D[2][0], yBot, verts2D[2][1],   /* 5 — bot c */
  ]);
  const indices = [
    0, 1, 2,                     /* top, normal +Y */
    3, 5, 4,                     /* bottom, normal -Y */
    0, 4, 1,  0, 3, 4,           /* side a-b */
    1, 4, 5,  1, 5, 2,           /* side b-c */
    2, 3, 0,  2, 5, 3,           /* side c-a */
  ];
  const geo = new THREE.BufferGeometry();
  geo.setAttribute('position', new THREE.BufferAttribute(positions, 3));
  geo.setIndex(indices);
  geo.computeVertexNormals();
  const m = new THREE.Mesh(geo, mat);
  m.castShadow = true; m.receiveShadow = true;
  scene.add(m);
  return m;
}
```

Corrected indices, then verified each side's outward normal via cross product to ensure no triangle had an inverted face.

## Learnings and discoveries

### `ExtrudeGeometry + rotateX` is hazardous for XZ-plane shapes

When you have a shape defined in 2D using world (x, z) coords and want to extrude it to a thin prism in the XZ plane, the obvious `ExtrudeGeometry(shape, { depth: T }) + rotateX(-π/2)` path mirrors the z coordinate and flips the prism upside-down. The cleanest pattern is explicit `BufferGeometry`:

```js
const positions = new Float32Array([
  ...verts.map(([x, z]) => [x, yTop, z]).flat(),  // top face
  ...verts.map(([x, z]) => [x, yBot, z]).flat(),  // bottom face
]);
const indices = [
  /* top, normal +Y */ 0, 1, 2,
  /* bottom, normal -Y */ N, N+2, N+1,  // reversed
  /* side faces — derive winding via cross product */
];
const geo = new THREE.BufferGeometry();
geo.setAttribute('position', new THREE.BufferAttribute(positions, 3));
geo.setIndex(indices);
geo.computeVertexNormals();
```

### Cross-product winding verification

For any triangle `(A, B, C)`, the cross product `(B-A) × (C-A)` gives a vector in the direction the right-hand-rule normal points. If you want the triangle's front face to point in direction `N`, the cross product must point in direction `N`. Calculate once per face — it's faster than reasoning about CW/CCW conventions in arbitrary planes.

For the XZ plane viewed from +Y in Three.js, the natural "+X right, +Z up-on-screen" convention has CCW polygons giving `+Y` normals. But this depends on the camera's `up` vector; the cross product is unambiguous regardless.

### X-mirror affects winder vertex ORDER, not just positions

Stairs-test winder 4 order `[PIVOT, P_SW, P_W_157]` is CCW from above in world-natural coords. The ozu-test equivalent in X-mirrored code, `[PIVOT, OUT_0, OUT_22]`, is CW from above because the mirror flips one axis. To get CCW in the mirrored frame, reverse the order: `[PIVOT, OUT_22, OUT_0]`. Same for all four winders.

## Architecture and design notes

### Winder triangular prism pattern (BufferGeometry)

For thin triangular treads in the XZ plane, use explicit BufferGeometry rather than ExtrudeGeometry + rotateX. Pattern:

```js
function makeWinder(verts2D, yTop, mat) {
  const yBot = yTop - TREAD_T;
  const positions = new Float32Array([
    /* top: 0,1,2 */
    verts2D[0][0], yTop, verts2D[0][1],
    verts2D[1][0], yTop, verts2D[1][1],
    verts2D[2][0], yTop, verts2D[2][1],
    /* bottom: 3,4,5 */
    verts2D[0][0], yBot, verts2D[0][1],
    verts2D[1][0], yBot, verts2D[1][1],
    verts2D[2][0], yBot, verts2D[2][1],
  ]);
  const indices = [
    0, 1, 2,                          /* top, +Y normal */
    3, 5, 4,                          /* bottom, -Y normal */
    0, 4, 1,  0, 3, 4,                /* side a-b */
    1, 4, 5,  1, 5, 2,                /* side b-c */
    2, 3, 0,  2, 5, 3,                /* side c-a */
  ];
  const geo = new THREE.BufferGeometry();
  geo.setAttribute('position', new THREE.BufferAttribute(positions, 3));
  geo.setIndex(indices);
  geo.computeVertexNormals();
  return new THREE.Mesh(geo, mat);
}
```

`verts2D` order must be CCW from above when the triangle is viewed from +Y. Verify via `(B-A) × (C-A)` — should give a +Y vector. If you're in the X-mirrored ozu-test frame, the same logical order may yield -Y; reverse the second and third vertices.

### Skirting baseboard pattern (sloped + flat helpers)

For thin white skirting strips tracing wall-meeting edges:

```js
const SKIRT_H = 0.080;          // height perpendicular to slope
const SKIRT_T = 0.015;          // thickness offset from wall
const matSkirt = new THREE.MeshStandardMaterial({ color: 0xfafaf0, roughness: 0.70 });

// Sloped skirt on wall at x=const (YZ plane slope)
function slopedSkirtX(x, sign, y0, z0, y1, z1) {
  const dz = z1 - z0, dy = y1 - y0;
  const length = Math.hypot(dz, dy);
  const angle = Math.atan2(dy, dz);
  const m = new THREE.Mesh(new THREE.BoxGeometry(SKIRT_T, SKIRT_H, length), matSkirt);
  m.position.set(
    x + sign * SKIRT_T / 2,
    (y0 + y1) / 2 + Math.cos(angle) * SKIRT_H / 2,
    (z0 + z1) / 2 - Math.sin(angle) * SKIRT_H / 2
  );
  m.rotation.x = -angle;
  scene.add(m);
}
// + slopedSkirtZ (XY plane slope), flatSkirtX, flatSkirtZ
```

`sign = +1` means skirt projects in +X from a wall whose surface is at x=const with the room at x>wall. `sign = -1` projects in -X. The perpendicular-to-slope offset uses `(-sin, cos)` in the (slope-axis, height-axis) plane.

### Coordinate frame translation (stairs-test → ozu-test)

Stairs-test sandbox uses world-natural conventions: `+X = east`, `+Z = north`, origin at SW corner of lower-flight shaft.

Ozu-test applies the blueprint X-mirror: `+X = real-world west`, `-X = real-world east`, `+Z = north`. Origin at the SW corner of the building (real-world; in code that's the south-east-most corner).

Mapping (for the stair shaft specifically):
- Lower flight in stairs-test: `x ∈ [0, STAIR_W=0.9], z ∈ [0, 3*TREAD=0.675]`
- Lower flight in ozu-test: `x ∈ [LX0=5.40, LX1=W=6.30], z ∈ [LZ0=2.90, LZ0+3*TREAD=3.575]`
- Stairs-test pivot at (0.9, 0.675) maps to ozu-test (LX0=5.40, LZ1=3.575)
- Upper flight in stairs-test extends +X from x=0.9 to x=2.25
- Upper flight in ozu-test extends -X from x=LX0=5.40 to x=4.05

Winder vertex order: stairs-test uses `(PIVOT, OUT_earlier, OUT_later)` CCW from above (e.g. `(PIVOT, P_SW, P_W_157)`). Ozu-test uses `(PIVOT, OUT_later, OUT_earlier)` because the mirror flips one axis and the cross product sign with it.
