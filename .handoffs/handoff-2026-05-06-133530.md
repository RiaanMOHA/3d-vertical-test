## Learnings and discoveries

### Codebase patterns

- **`registerScene('interior', ...)` block boundaries**: starts at line ~867, ends way down past line 3000. All interior code is in this single closure. Helpers defined inside (wallX, wallZ, makeWall, makeFloor, makeCeiling, addDoor, addWinFlex, addRoomTrim, addBedroomWallPaint) only available within the closure. New bedroom-paint helper added at line ~1465 was scope-correct.

- **F1_CEIL hole carving requires matching 2F floor coverage**: when the 1F ceiling has a hole, the 2F floor underside above that hole becomes visible from below. F2_ROOMS room-4 covers x=[3.60, W], z=[0, 3.60]. F1_CEIL had a hole at x=[5.40, W], z=[2.90, 4.50]. The intersection (x=[5.40, 6.30], z=[2.90, 3.60]) caused floor underside to show through. Lesson: changes to F1_CEIL or F2_ROOMS should always cross-check the other.

- **Trim and paint depth constants**: `WT = 0.10` (wall thickness), `trimD = 0.012` (door casing + baseboard depth), `paintD = 0.005` (bedroom wall paint depth). Both trim and paint sit on the room-interior face of the wall, offset by their half-depth. To avoid Z-fighting, paint Y range must NOT overlap trim Y range.

- **Procedural plank texture (`plankTex(baseHex, plankCount, seed)`)**: returns `THREE.CanvasTexture` directly (not wrapped). Sets `wrapS = wrapT = RepeatWrapping` and `anisotropy = 8` internally. Existing usage examples: `FLOORS.ldk`, `FLOORS.corridor`, `FLOORS.stairs`, `FLOORS.room4`, `FLOORS.room`. New `FLOORS.toilet` added this session.

- **`addDoor` casing block runs for ALL door types** (after the bi-fold/hinged branch), which means the front door also got casing + 2 jambs + header on each face. The custom front door I built later for Phase 7.9 had to manually add the casing block since it bypasses `addDoor`.

- **Door type fallthrough sealed**: `addDoor` now has explicit `if/else if/else` chain for bi-fold, hinged (default), sliding, archway, and unknown-type warning. Sliding renders track + finger pulls; archway renders just a console.warn (panel still drawn — needs future panel-skip refactor).

### Rendering / three.js facts

- **HDRI loads asynchronously** and replaces the procedural fallback ~0.5–1 s after page load. To avoid hue flash, the fallback's per-face colours should match the HDRI's average tone. For kloppenheim_06_puresky_2k.hdr, that's cool sky-blue palette (top: 0xb8d0e8, sides: 0xc8d4e0, bottom: 0x8a8478).

- **Stair shaft hole = upper flight footprint**: F1_CEIL hole and F2_ROOMS hole must match. For this house: only x=[4.725, W], z=[3.60, 4.50] should be hole-d. Lower flight at z=[2.90, 3.60] does NOT need a hole — the 1F ceiling can sit above it (head clearance is tight at i=2 but acceptable, ~1.82 m).

- **Procedural fallback env is built lazily** — the function `_buildFallbackEnvMap` is only called when scene.environment is needed and `_envLoaded` is false. PMREM-prefiltered.

## Architecture and design notes

### Trim + paint layer system (NEW this session)

Rooms are now assembled in three concentric layers:
1. **Wall** (built by `wallX/wallZ/makeWall`) — full-height structural wall material `wallMat` cream `0xeeeae3`.
2. **Paint overlay** (`addBedroomWallPaint`) — 5 mm thin BoxGeometry on the interior face, in the Y range BETWEEN baseboard and crown bands, with door + window x-cutouts. Bedroom-specific (taupe-grey).
3. **Trim bands** (`addRoomTrim`) — 12 mm thick BoxGeometry at floor (baseboard, 70 mm tall) and ceiling (crown, 50 mm tall), proud of the wall surface (so they sit visually on top of paint).

Z-fighting avoided by: trim and paint are at different Y ranges; trim sticks out further in Z than paint; paint is inset just past wall surface.

For door casings: separate per-door mechanism inside `addDoor`. Two faces of the wall × 2 jambs + 1 head = 6 strips per door. `casD = 0.012, casW = 0.07`.

### F1_CEIL geometry rule

The 1F ceiling must have a hole where AND ONLY where the upper flight rises through it. Currently:
```
[ {0, 0, W, 2.90}, {0, 2.90, W, 3.60}, {0, 3.60, 4.725, 4.50}, {0, 4.50, W, D} ]
```
Hole at x=[4.725, W], z=[3.60, 4.50] = upper-flight footprint. Lower flight at z<3.60 has a ceiling above it (clearance ~1.82 m at the top tread is acceptable for the bottom three steps).

If F2 floor coverage of room-4 is changed in the future, F1_CEIL must be re-checked to ensure no underside is exposed through any ceiling hole.

### Bedroom paint, door, and window cutout chains

`addBedroomWallPaint` accepts a `gapsBySide` object: `{ south, north, west, east }` each an array of `{a, b}` window objects. Door cuts are auto-derived from the `doorList` (F2_DOORS) by checking which doors have axis matching the wall side. Window cuts must be passed explicitly because windows aren't in F2_DOORS.

For each side, the function:
1. Filters doorList for doors on that side (axis matches + c value within 0.05 of the edge).
2. Concatenates with explicit window gaps.
3. Calls `_subtractRanges` to compute remaining segments.
4. Places one box per segment.

This is reusable for any future room paint job (LDK, corridors) — just pass the right gaps.

### `addDoor` branch chain (NEW this session)

```
type === 'bi-fold'    → seam + finger pulls (existing)
type === 'hinged' || !type  → lever handles + 3 hinges (default, existing)
type === 'sliding'    → top track + recessed finger pulls (NEW)
type === 'archway'    → console.warn (panel still drawn — needs panel-skip refactor) (NEW)
unknown               → console.warn ("pass 'hinged' | 'bi-fold' | 'sliding' | 'archway'") (NEW)
```

The casing block at the top of `addDoor` (jambs + header on each face) runs for ALL types — including the archway warning case. For a real archway (no panel, no casing), the casing block would also need the same panel-skip treatment.
