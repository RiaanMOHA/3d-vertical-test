## Problems encountered and how they were solved

### Problem 1 — Memory rule contradicted blueprint

- **Symptom:** Memory `project_stair_must_be_l_shape.md` (4 days old) said "5 + landing + 6 = 11 risers". Code + room-map + photos all said "5 + 2 winders + 6 = 13 risers". Past sessions kept rebuilding/changing the L-bend.

- **Fix:** Rendered `ozu-1-blueprint.pdf` at 400 DPI via `pdftoppm -r 400`, cropped 1F + 2F panels via PIL Image.crop, and READ the actual riser numbers (1-5 on 1F, 8-13 on 2F, fan pattern at L-bend = winders not landing). Updated memory to "5 + 2 winders + 6 (13 risers)" with explicit "Memory rule was OUTDATED" citation.
- **Lesson:** Stale memory files are dangerous. When memory contradicts current code + room-map + photos, render the SOURCE OF TRUTH (blueprint at 400 DPI per memory rule `feedback_no_excuses_blueprint.md`) and trust that.

### Problem 2 — Brush stroke `mix` node interface in Blender 5.1.1

- **Symptom:** Initial `make_leather_material` reference patterns from `bake_room1_chair.py` use the new ShaderNodeMix node with `data_type='RGBA'` and `inputs['A']`/`inputs['B']`. Same pattern works in Blender 5.x; just wanted to flag for future scripts.
- **Resolution:** Used the same pattern in all 5 PBR scripts. All ran cleanly on Blender 5.1.1 OPTIX backend.

### Problem 3 — Initial agent reports about handrail were partly wrong

But my own careful read of `stairs-5/6/7/12/25` shows the joints are brushed-metal cylindrical FERRULES (sleeves), not painted-wood elbows. ## Learnings and discoveries

### Brushed-metal ferrules are the correct fix for the L-bend handrail

This codebase had been treating the L-bend handrail joint as either a chrome torus (current ozu-test.html) or a white-painted wood elbow (room-map.md / Phase 0 agents). Both were wrong. The actual photos show **brushed-metal cylindrical FERRULES (sleeves)** that wrap the rail at every joint — appearing both at the L-bend AND at intermediate scarf joints in long straight runs. Future stair work in any context should use the ferrule, not a torus or an elbow.

### The bulkhead step in the ceiling matters visually

The whitewashed plank ceiling above the upper flight is only above the upper flight + L-bend. Above the lower flight, the ceiling is plain TAUPE-painted (just the underside of the 2F floor structure). The transition is a vertical bulkhead step at the boundary. Without modelling this step, the area reads as "unfinished" — the plank ceiling alone or the taupe ceiling alone both look wrong.

### Stair-test sandbox dimensions vs master scene

The master scene has the 2F shaft extending 0.675m WEST of the lower shaft (x=4.725..6.30 vs 5.40..6.30). For the sandbox I used 0.45m west extension instead, because 6 upper risers × 0.225m tread depth = 1.35m of run + 0.225m landing = 1.575m total upper shaft length, and the lower shaft east edge is at the same x as the upper flight east edge, so upper flight extends west by exactly 0.225m × 5 = 1.125m? No wait, that's wrong. Let me rethink — actually used UF_X_WEST = UF_X_EAST - 6 × TREAD = 0.90 - 1.35 = -0.45. So upper flight west extension is 0.45m beyond lower shaft west edge (x=0). The 2F shaft footprint x=[-0.45, 0.90] is 1.35m wide, slightly less than the master scene's 1.575m. The remaining 0.225m of "landing" is implied as the 2F floor west of step 13. **This sandbox dimension differs from master scene by 0.225m** — needs reconciliation in Phase 4 if porting back.

### Existing sandbox bake pattern was reusable but boilerplate-heavy

Each PBR bake script duplicates ~120 lines of boilerplate (clear_scene, configure_cycles_optix, add_neutral_world, add_plane_for_bake, add_bake_target_node, bake_pass, bake_all_for, main). Authoring 7 scripts × 200-300 lines = ~1700 lines, of which ~840 is boilerplate. A future refactor to extract a shared `_common.py` would save effort, but Blender's --background --python doesn't natively support sibling imports without sys.path manipulation. Accepted the duplication.

### Per-mesh uv2 + lightMap channel setup is the hardest part of the bake pipeline

The PBR material maps swap is straightforward (load texture, clone for repeat, MeshStandardMaterial with map+normalMap+roughnessMap). The room AO + lightmap maps require:
- Each Blender-baked surface had a smart UV unwrap (Blender does it automatically), but at runtime each three.js mesh ALSO needs a uv2 attribute matching the bake's UVs.
- For BoxGeometry, the default UV channel is UV0 = standard cube unwrap. To use the bake, you need to manually compute uv2 by mapping each face's vertex position back to the smart-UV layout.
- Alternative (used by laundry-test): bake to a SINGLE FACE per material with KNOWN UV mapping (e.g. simple plane), then the runtime `setLightmapUV1` helper rewrites uv1 with a custom worldToUv function.
- For stair-test Phase 3 I used Blender's smart_uv_project for AO + lightmap, which means runtime swap requires manually computing uv2 to match. Deferred to Phase 4.

### Kumamoto rule application for window-less shafts

The CLAUDE.md daylight rule talks about south/east/west/north windows. The stair shaft has NO direct window. The rule still applies: treat the OPENINGS (top exit + bottom exit) as window-equivalent. Light enters as cool diffuse (no direct sun in the shaft because corridor walls scatter it before reaching the shaft). Used `0xe0e8f4` + `0xdfe6ef` cool tints for both directional + RectAreaLights. No warm 5500K tones anywhere.

## Architecture and design notes

### Stair-test sandbox pattern (continues kitchen-test/laundry-test/living-dining-test convention)

Each sandbox is a self-contained `*-test.html` + `*-test/` folder pair. Phases:
- **Phase 0**: full photo audit (no code, output to chat)
- **Phase 1**: geometry-first scaffold with flat colors, all castShadow/receiveShadow, structural elements only
- **Phase 2**: full Kumamoto lighting rig per CLAUDE.md daylight rule + post-processing
- **Phase 3**: A6000 Cycles bakes per material + per-surface AO/lightmap; runtime swap from flat colors to PBR maps
- **Phase 4**: photo-paired final polish + decide whether to port back to ozu-test.html master scene

The kitchen-test, laundry-test, and now stair-test all follow this sequence.

### Why stair-test instead of fixing master scene

The user has been struggling with the stair for many sessions. Each fix in `ozu-test.html` layered on previous fixes, accumulating workarounds. The `polygonOffset` bug from the previous session was a great example — months of geometric tweaks didn't fix what was actually a single material flag.

Sandbox approach breaks the cycle by:
1. Isolating the stair from the master scene (no risk of breaking other things)
2. Allowing full PBR + bake workflow per CLAUDE.md cutting-edge rendering rule (master plan rule says no bake; sandbox rule says yes bake)
3. Forcing vantage discipline (the 5 vantage buttons match real photo angles, so visual comparison is direct)
4. Letting the geometry be wrong and fixed in isolation before any port-back

### Stair-test local coordinate system

Origin at SW corner of 1F lower shaft, 1F floor level. +X = east, +Y = up, +Z = north (lower flight ascent direction).

This is a TRANSLATED (not rotated) version of master scene coords: master `x=5.40..6.30, z=2.90..4.50` maps to sandbox `x=0..0.90, z=0..1.60`. Master `x=4.725..6.30, z=3.60..4.50` (2F shaft) maps to sandbox `x=-0.45..0.90, z=0.70..1.60` — note the sandbox uses `UF_X_WEST = UF_X_EAST - 6 × TREAD = -0.45` instead of master's `4.725` which would correspond to `-0.675`. The 0.225m discrepancy is the "landing area" beyond step 13 — sandbox doesn't model it, master does.

### PBR material wiring pattern (Phase 3)

```
const pbrMaple = loadPbrSet('treads', 'light_maple');  // {albedo, normal, rough}
const matWoodTread = pbrMat(pbrMaple, [2.0, 1.0]);     // clones with repeat
```

Each PBR set is loaded ONCE per slug (4 sRGB/Non-Color-tagged textures with anisotropy + repeat wrapping). Then `pbrMat()` clones each texture with per-material repeat. This avoids duplicate texture loads while letting different meshes use different repeat values.

### Room AO + lightmap deferred wiring

`stair-test/textures/ao/*.png` and `lightmap/*.png` are baked but NOT wired in Phase 3. Wiring requires:
1. Per-mesh uv2 attribute matching Blender's smart_uv_project bake layout (or rebake with controlled UVs)
2. `material.aoMap = ...; material.aoMap.channel = 1;` for AO
3. `material.lightMap = ...; material.lightMap.channel = 1;` for lightmap (replaces AO since lightmap subsumes AO per laundry-test pattern)

The laundry-test pattern uses `setLightmapUV1(mesh, faceAxis, faceSign, worldToUv)` to manually rewrite uv1 with a custom mapping function — this works well for rectangular wall surfaces but is awkward for compound geometry like winders. Phase 4 should either rebake with simple-rectangle UVs OR write a per-mesh uv2 generator.

### Why brushed-metal ferrule, not torus or elbow, at L-bend

Photos `stairs-5/6/7/12/25` clearly show a brushed-metal cylindrical SLEEVE wrapping the rail at every joint. This is a standard fitting in Japanese residential stair handrails — pre-fab metal ferrules join short painted-wood rail segments. The current ozu-test.html stair uses TorusGeometry (donut shape) which is geometrically wrong (a torus has a hole through the middle, but a ferrule is a solid sleeve). The Phase 0 dispatch agents misidentified this as a "white-painted elbow" — also wrong.

The fix in stair-test is `makeFerrule()`: a short cylinder wrapping the rail axis, oriented via Quaternion alignment. The rail itself is multiple painted-wood segments joined by these ferrules.
